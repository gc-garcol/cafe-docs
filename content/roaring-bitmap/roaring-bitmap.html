Roaring Bitmap

A compressed set of 32-bit integers. Split every number into a high half and a low half, then store each chunk in whichever container is smallest: a sorted array, a bitmap, or a list of runs.

1. The problem

  
A plain bitmap is great for sets of integers. One bit per possible value, and union is a bitwise OR. But a bitmap over 32-bit IDs needs 512 MB even if it holds three numbers. A sorted array of 4-byte integers is small for sparse data and large for dense data.

  
Neither wins everywhere, and real data is usually a mix: some dense clusters, some empty stretches, some long runs of consecutive IDs.






  
2. The idea: two levels

  
Split each 32-bit value in two. The high 16 bits are the key and pick a chunk. The low 16 bits are stored inside that chunk. Only chunks that hold at least one value exist, so empty ranges cost nothing.

  
key = x >>> 16          // which chunk
low = x & 0xFFFF       // position inside it, 0..65535

  
The keys are kept in a small sorted array, so finding a chunk is a binary search.

  
Each chunk picks its own representation. That is where the compression comes from.






  
3. Three containers

  
A chunk holds up to 65,536 low values. Each container below stores the same set in a different way.

  

    
ContainerSizeBest when

    
      
Array2 × cardinality bytesSparse, up to 4096 values

      
Bitmap8192 bytes, fixedDense, more than 4096 values

      
Run2 + 4 × runs bytesLong stretches of consecutive values

    
  

  
The 4096 cutoff is where the two main forms cost the same: 4096 values × 2 bytes = 8192 bytes. Past that point the bitmap is never larger, so an array that grows beyond 4096 values converts to a bitmap, and a bitmap that shrinks to 4096 or fewer converts back.

  
Run containers store pairs of (start, length). They are chosen when you call runOptimize(), which compares sizes and keeps the smallest. The demo above applies that choice after every change.






  
4. Add and contains

  
function add(rb, x) {
  const key = x >>> 16, low = x & 0xFFFF;
  let c = rb.get(key);
  if (!c) rb.set(key, c = new ArrayContainer());
  c.add(low);
  if (c instanceof ArrayContainer && c.size > 4096)
    rb.set(key, c.toBitmap());
}

function contains(rb, x) {
  const c = rb.get(x >>> 16);
  return c !== undefined && c.contains(x & 0xFFFF);
}

  
Contains is a lookup of the chunk, then one probe: a binary search in an array, a bit test in a bitmap, or a binary search over runs.






  
5. Set operations

  
Union, intersection, and difference work chunk by chunk. Keys are sorted, so two bitmaps are merged like two sorted lists. Chunks that appear in only one side are skipped for intersection and copied for union.

  
When both containers are bitmaps, the work is 1024 word-level operations on 64-bit words, which modern CPUs run with SIMD. This is why Roaring is often faster than plain compressed formats while using similar space.

  
// AND of two bitmap containers
for (let i = 0; i < 1024; i++) out[i] = a[i] & b[i];






  
6. Cost

  

    
Contains
O(log n)
Binary search over keys, then one probe in the container.

    
Per chunk
≤ 8 KB
No container is larger than a flat bitmap of its chunk.

    
Union / AND
O(n)
Linear in the number of chunks and container sizes.

  






  
7. Where it shows up

  
    
    
  • Search engines: posting lists of document IDs, combined with AND and OR.
    • 
    
  • Databases and analytics: bitmap indexes in Lucene, Elasticsearch, Druid, Pinot, and ClickHouse.
    • 
    
  • Data processing: Spark, Hive, and Git use it for sets of row or object IDs.
    • 
    
  • Feature flags and audiences: one bitmap per segment, intersected on demand.
    • 
  

  
It fits best when IDs are integers that you intersect and union often. If your data is a few random values spread across the whole range, a sorted array can be smaller. For approximate membership with no deletes of exact values, see Bloom filters instead.
