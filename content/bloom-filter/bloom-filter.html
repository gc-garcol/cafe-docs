Bloom Filter

A tiny bit array that answers "have I seen this before?" using a fraction of the memory of a real set. It never misses an item you added, but it sometimes says yes to one you did not.

Try the machine first

This filter has 32 bits and 3 hash functions. Add a word and it lights three bits. Check a word and it looks at the same three bits. If any of them is off, the word is definitely new. If all are on, the word is only probably there. Add a few words, then check one you never added.

1. The idea

  
A normal set stores every item, so it needs memory proportional to the items and their size. A Bloom filter stores only bits. To add an item, run it through k hash functions and set the bit at each of the k positions. To ask about an item, hash it the same way and read those bits.

  
    
    
  • Any probed bit is 0: the item was never added. This answer is always right.
    • 
    
  • All probed bits are 1: the item was probably added. Other items may have set those same bits by chance.
    • 
  

  
No false negatives. Some false positives. You pick how many.






  
2. The code

  
Real filters do not need k independent hash functions. Two hashes are enough. Combine them as h1 + i × h2 to get as many positions as you want. This is called double hashing, and Fig 1 uses it.

  
class Bloom {
  constructor(m, k) {
    this.m = m; this.k = k;
    this.bits = new Uint8Array(m);
  }
  positions(item) {
    const h1 = hash1(item), h2 = hash2(item) | 1;
    return Array.from({ length: this.k }, (_, i) => (h1 + i * h2) % this.m);
  }
  add(item) {
    for (const p of this.positions(item)) this.bits[p] = 1;
  }
  mightContain(item) {
    return this.positions(item).every(p => this.bits[p] === 1);
  }
}

  
There is no remove. Clearing a bit could erase evidence for other items that share it, and that would create false negatives.






  
3. How wrong can it be?

  
After inserting n items into m bits with k hashes, a given bit is still 0 with probability about e-kn/m. A false positive needs all k probed bits to be 1:

  
p ≈ (1 - e-kn/m)k

  
More items push the rate up. More bits push it down. For a target rate p and expected count n, size the filter like this:

  
m = -n · ln(p) / (ln 2)²     // bits
k = (m / n) · ln 2           // hash functions

  
For a 1% false positive rate that is about 9.6 bits and 7 hashes per item, whatever the item size. The live readout under Fig 1 uses the first formula.

5. Where it shows up

  
    
    
  • Databases such as LSM-tree stores keep one per file to skip disk reads for keys that are not there.
    • 
    
  • Caches use it to avoid storing items that were requested only once.
    • 
    
  • Crawlers and safe-browsing checks test "seen this URL?" or "known bad URL?" with a small local filter before a slow lookup.
    • 
    
  • Distributed systems send a filter instead of a full key list to compare what two nodes have.
    • 
  

  
A good rule: use it when a false "yes" only costs one extra, slower lookup, and a false "no" would be a bug.
