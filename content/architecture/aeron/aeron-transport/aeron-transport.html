Aeron Transport

The messaging layer under everything else in Aeron. Publishers write into a shared memory log buffer, a media driver moves it over UDP or IPC, and subscribers read it by position.

#aeron#messaging#low latency#log buffer

Try the log buffer first

A publication writes messages into a ring of three terms. Offer appends a message. Send lets the driver's Sender move data onto the wire. Poll lets a subscriber read it. When the publisher gets too far ahead of the Sender, an offer is refused. That is back-pressure.

Each cell is one message. Real frames are bytes, aligned to 32.

1. The model

  
Aeron is a message transport. An application uses a publication to send and a subscription to receive. The two meet on a channel and a stream. Between them sits the media driver, which does the real work of moving bytes.

  
The application and the driver share memory. The client writes into a file-backed buffer and the driver reads it, so the hot path needs no system call and no copy between processes.

  
The log buffer is the heart of Aeron. Everything else moves or watches it.






  
2. Terms and positions

  
Each publication owns a log buffer split into three equal terms. A writer fills one term, then rotates to the next. Three terms let one be active, one be cleaned and ready, and one be draining to the reader.

  
A position is a 64-bit byte count since the stream began. It is the same on both ends. From a position you can compute where you are:

  
termCount  = position / termLength
termOffset = position % termLength
termIndex  = termCount % 3        // which of the three buffers

  
Three positions matter. The publisher position is how far the application has written. The sender position is how far the driver has sent. The subscriber position is how far a reader has consumed. The gaps between them are the queue.

  
The publisher may only run ahead of the sender by a window, by default half a term. Past that, an offer fails with a back-pressure result and the caller retries.






  
3. The media driver

  

    
Conductor
Handles commands from clients, creates and cleans up resources, detects loss.

    
Sender
Reads publication buffers and sends frames over UDP.

    
Receiver
Reads UDP frames and rebuilds the stream in an image buffer.

  

  
Clients talk to the Conductor through a command ring buffer in shared memory. Counters in shared memory expose positions and health, so monitoring tools can read them without asking the driver.






  
4. IPC and network

  

    
KindPath of a message

    
      
IPCPublisher writes the log buffer. A subscriber on the same machine reads that same buffer. No Sender or Receiver.

      
NetworkPublisher writes the log buffer. The Sender sends UDP. The Receiver rebuilds a copy, the image. A subscriber reads the image.

    
  

  
The image is a replica of the publication buffer. When it is caught up the data part is identical.






  
5. Threading modes

  
The driver has three agents. The threading mode decides how they map to threads.

  

    
ModeThreadsUse

    
      
DEDICATED3, one per agentThe default. Lowest latency when cores are free.

      
SHARED_NETWORK2Sender and Receiver share a thread.

      
SHARED1All agents on one thread.

      
INVOKER0Your code calls the duty cycle. Good for limited CPU.

    
  

  
Fewer threads cost little with few streams. With tens of streams or more, dedicated threads give more throughput. Match the idle strategy to the mode, since a thread that spins burns a core.






  
6. Offering and polling

  
A publisher calls offer and checks the result. A subscriber calls poll with a handler, and gets any fragments that are ready.

  
long result = publication.offer(buffer, 0, length);
if (result < 0) {
  // BACK_PRESSURED, NOT_CONNECTED, ADMIN_ACTION: retry or back off
}

int fragments = subscription.poll(handler, 10);
if (fragments == 0) idleStrategy.idle();

  
A negative result is normal flow, not an error. Aeron never blocks the caller. It reports the state and lets the application choose how to wait.
