Aeron Cluster

A framework for fault-tolerant services built as replicated state machines. Clients send commands in, one leader puts them in a single order, and every node applies that same log to reach the same state.

#aeron#cluster#raft#consensus

Try the cluster first

Three nodes hold a copy of the log. Send bid makes the leader append a command and replicate it. An entry turns solid once a majority has it, and only then does the service apply it. Crash a node and see what still works. Crash the leader and the others elect a new one.

Each bid is one log entry. The service keeps the best bid.

1. The idea

  
A service that must not lose data cannot live on one machine. Aeron Cluster keeps several copies. Clients send commands, called ingress. The cluster merges them into one ordered log, and each node runs the same service code over that log. Replies go back to the client as egress.

  
It uses the Raft consensus algorithm with a strong leader. The leader decides the order and copies the log to the followers. The system keeps working while a majority of nodes, n / 2 + 1, is available, and it behaves as if there were one copy.

  
Same starting state, same ordered inputs, same code: same result on every node.






  
2. Components of a node

  
Aeron Cluster is made from parts that already exist in Aeron. A node needs one of each. They talk over IPC, so they can share a process or run in separate ones.


  

  

    
Consensus Module
The key part. It orders client messages, coordinates recording and acknowledgement across nodes, and hands entries to the services.

    
Archive
Raft is a log replication protocol, so the log has to be stored. Aeron Archive records it, and snapshots too.

    
Clustered Service
Your application logic. A node can run one or more services in the container.

  






  
3. How a command flows

  
    
    
  • A client connects and sends a command. A follower redirects it to the leader.
    • 
    
  • The leader's Consensus Module appends the command to the log and the Archive records it.
    • 
    
  • Followers receive the log, record it, and report how far they have got.
    • 
    
  • Once a majority has recorded an entry, it is committed.
    • 
    
  • Services consume the log only up to the committed position, then reply on egress.
    • 
  

  
Services never see an entry that could still be lost. This is why the dashed entries in the demo are not applied.






  
4. Determinism

  
Replication and recovery are the same problem. A stopped node returns to its state by starting from a known state, then replaying the ordered log. That works only if the service is deterministic: the same inputs must give the same results every time.

  

    
PitfallWhat to do instead

    
      
Wall-clock timestampsUse the time the cluster supplies with each message

      
Random numbersAvoid them, or take a seed from the initial state or a message

      
Reading config filesSend configuration changes in as messages

      
Iterating hash mapsUse an ordered collection, or sort before use

    
  






  
5. Snapshots and recovery

  
Replaying a log from the beginning of time is slow. A snapshot is the service state as of one log position. To recover, a node loads the latest snapshot and replays the log from that point.

  
The Archive records snapshots, so another node can fetch them from it. No shared file system is needed. Pick the snapshot interval from the message volume, the speed of your logic, and the recovery time you can accept. If replaying a day takes two hours, a snapshot every 30 minutes is a sensible choice.






  
6. Elections and quorum

  
When the leader fails, the remaining nodes hold an election. The new leader comes from the members with the most up-to-date log, and a new term begins. Try it in the demo: crash the leader and watch which node takes over.

  
    
    
  • With a majority up, the cluster keeps committing.
    • 
    
  • Without a majority there is no leader and no new commits. Entries wait until nodes return.
    • 
    
  • Use 3 or 5 nodes. Two nodes work, but both must agree, so one failure stops progress until you reconfigure by hand.
    • 
  






  
7. Writing a clustered service

  
You implement the ClusteredService interface. The container calls it with lifecycle events and messages. This sketch shows the shape only, and the real signatures have more parameters.

  
class AuctionService implements ClusteredService {
  // load state before any message arrives
  onStart(cluster, snapshotImage) { /* read the snapshot into state */ }

  // every committed log entry, in order, on every node
  onSessionMessage(session, timestamp, buffer) {
    const bid = decode(buffer);
    if (bid.price > best.price) best = bid;
    session.offer(encode(best));          // egress to the client
  }

  onTakeSnapshot(publication) { /* write state out */ }
}

  
The timestamp comes from the cluster, which keeps the service deterministic.






  
8. Ways to run it

  

    
ModeUse

    
      
Single nodeDevelopment, debugging, or when one sequenced and archived log is enough

      
Appointed leaderThe leader is set in configuration. A failure needs a manual change, so it is not recommended

      
Automatic electionsThe default. The cluster elects a leader from the most up-to-date members

    
  

  
Aeron Cluster also provides reliable distributed timers, messaging between services, and backup to a remote data centre.
