1. Principals and policies

  
IAM answers one question: may this principal do this action on this resource? Principals are users, groups and roles. A policy is a JSON document with statements.


{
  "Effect": "Allow",
  "Action": "s3:GetObject",
  "Resource": "arn:aws:s3:::shop/*"
}






  
2. How a decision is made

  
    
    
  1. Everything starts as an implicit deny.
    2. 
    
  2. If any statement that matches says Deny, the answer is deny. Nothing overrides it.
    3. 
    
  3. Otherwise, if any matching statement says Allow, the answer is allow.
    4. 
    
  4. If nothing matches, the implicit deny stands.
    5. 
  

  
Wildcards in Action and Resource let one statement cover many requests. Permissions boundaries, SCPs and session policies can only narrow what is allowed.






  
3. Roles over long-lived keys

  
A role has no password or key. A service or person assumes it and gets short-lived credentials. An EC2 instance or Lambda function runs with an attached role, so no secret is stored in code. Roles also give access across accounts.






  
4. Least privilege

  
    
    
  • Grant only the actions and resources a job needs. Start narrow and widen on evidence.
    • 
    
  • Use groups or roles, not per-user policies.
    • 
    
  • Do not use the root user for daily work. Protect it with MFA.
