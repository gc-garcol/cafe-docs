1. ReplicaSet

  
A ReplicaSet keeps a set number of identical Pods running. It selects Pods by label and creates or deletes Pods until the count matches. You rarely write one directly, because a Deployment owns it.







  
2. Deployment

  
A Deployment manages ReplicaSets and so manages change. A new image makes a new ReplicaSet. The old one is scaled down but kept, which is what makes rollback possible.


kubectl create deployment web --image=web:1.0 --replicas=4
kubectl scale deploy/web --replicas=6






  
3. StatefulSet

  
For apps that need identity. Pods get stable names (db-0, db-1), start and stop in order, and each keeps its own volume across restarts. A headless Service gives each Pod a stable DNS name. Use it for databases and brokers.







  
4. DaemonSet

  
Runs one Pod on every node, or on a chosen set of nodes. New nodes get the Pod automatically. Typical uses are log collectors, monitoring agents and CNI plugins.







  
5. Job / CronJob

  
A Job runs Pods until a set number complete, retrying failures up to backoffLimit. It can run Pods in parallel. A CronJob creates a Job on a cron schedule.


schedule: "0 2 * * *"       # every day at 02:00
concurrencyPolicy: Forbid






  
6. Init / Sidecar Container

  
    
    
  • Init containers run to completion, one at a time, before the app starts. Use them for migrations or waiting on a dependency.
    • 
    
  • Sidecars run beside the app for the life of the Pod, for example a log shipper or a proxy. Native sidecars are init containers with restartPolicy: Always, so they start first and stop last.
    • 
  






  
7. Rolling Update / Rollback

  
The default strategy replaces Pods in small steps. maxSurge allows extra Pods above the desired count. maxUnavailable allows fewer ready Pods than desired. A readiness probe decides when a new Pod counts, so a broken version stalls while old Pods keep serving.


kubectl rollout status deploy/web
kubectl rollout history deploy/web
kubectl rollout undo deploy/web
