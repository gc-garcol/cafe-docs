1. Cluster architecture

  
A cluster is a set of machines that Kubernetes treats as one pool. One half, the control plane, decides what should run. The other half, the worker nodes, runs it.

  
Every part is reached through one REST API. That is why the same model works for a laptop and for thousands of nodes.

3. Pod / Namespace

  
A Pod is the smallest unit you deploy. Its containers share one IP address, one set of ports and optional volumes. Pods are disposable. A replaced Pod gets a new IP.

  
A Namespace is a named scope inside a cluster. Names only need to be unique within one. Namespaces also carry quotas, RBAC rules and policies. Clusters start with default, kube-system, kube-public and kube-node-lease.







  
4. Labels / Selectors

  
Labels are key-value pairs on any object, such as app=web. They carry no meaning by themselves. Selectors pick objects by label. Services, ReplicaSets and NetworkPolicies all find their Pods this way.

  
Equality selectors use app=web. Set-based selectors use env in (prod, staging).


kubectl get pods -l app=web,tier!=cache
kubectl label pod web-1 env=prod






  
5. kubectl

  
kubectl is the command line client for the API server. It reads connection details and credentials from a kubeconfig file, which can hold several contexts.


kubectl get pods -n kube-system
kubectl describe pod web-1      # state and recent events
kubectl logs web-1 -c app
kubectl exec -it web-1 -- sh
kubectl diff -f deploy.yaml     # preview a change
kubectl apply -f deploy.yaml






  
6. YAML Manifest

  
Every object is written as a manifest with four top-level fields.

  
    
    
  • apiVersion and kind say what type of object it is.
    • 
    
  • metadata holds the name, namespace and labels.
    • 
    
  • spec is the desired state. The cluster adds status, the observed state.
    • 
  
apiVersion: v1
kind: Pod
metadata:
  name: web
  labels: {app: web}
spec:
  containers:
    - name: app
      image: nginx:1.27






  
7. Desired State / Reconciliation


Declare what you want. Controllers keep making it true.

  
A controller watches objects of its kind, compares spec with the real world, and acts on the difference. It repeats forever, so a crashed Pod is replaced with no human step. This is the reconciliation loop, and it is the pattern behind every feature in Kubernetes.

  
Components never call each other. Each one watches the API server and writes its result back, which keeps every part replaceable.
