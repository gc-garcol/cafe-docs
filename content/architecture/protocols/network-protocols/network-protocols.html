1. The layer map

Each protocol solves one problem and hands the rest to the layer above or below. IP moves packets between hosts with no promises. TCP and UDP add ports. TCP also adds a reliable, ordered byte stream. QUIC rebuilds that reliability on top of UDP. HTTP, gRPC and FIX are application protocols that give the bytes a meaning.

The cost of a new connection is mostly handshake round trips. If a stack needs $h$ round trips of setup before it can send a request, the first response byte arrives after about

$$T_{\text{first byte}} \approx (h + 1)\cdot \text{RTT}$$

On a 100 ms intercontinental link, one saved round trip is 100 ms saved on every new connection. That is why TLS 1.3, QUIC and connection reuse matter more than raw bandwidth for small requests.

2. UDP

UDP (RFC 768) is IP plus ports and a checksum. Its header is 8 bytes: source port, destination port, length and checksum. There is no connection, no acknowledgment, no retransmission and no ordering. A datagram arrives once, arrives twice, arrives out of order, or does not arrive at all.

What it does keep is message boundaries. One send becomes one datagram, and the receiver reads it whole. It also supports multicast, so one packet can reach many subscribers, which is how exchanges publish market data.

  • Pick it when late data is worthless (voice, game state, live prices), when you want your own reliability scheme (QUIC, Aeron), or for tiny request and response exchanges (DNS).
  • You own loss handling, pacing, congestion control and packet size. Keep datagrams under the path MTU, around 1200 to 1472 bytes of payload, to avoid IP fragmentation.

3. TCP

TCP (RFC 9293) turns lossy packets into a reliable, ordered byte stream between two endpoints. Its header is 20 to 60 bytes. Every byte has a sequence number, and the receiver acknowledges the highest contiguous byte it has.

Handshake

SYN, SYN-ACK, ACK. One round trip before data. Data can ride on the final ACK.

Reliability

Lost segments are resent after a timeout, or sooner after three duplicate ACKs (fast retransmit).

Two windows

The receive window protects the receiver. The congestion window protects the network.

The sender may have at most the smaller of the two windows unacknowledged. One window is sent per round trip, so throughput is capped by

$$\text{throughput} \le \frac{\min(\text{cwnd},\ \text{rwnd})}{\text{RTT}}$$

To fill a link you need a window at least the size of the bandwidth-delay product, $\text{BDP} = \text{bandwidth} \times \text{RTT}$. A 1 Gbit/s link with 50 ms RTT needs about 6 MB in flight. Congestion control (slow start, then CUBIC or BBR) grows the window until it sees loss or rising delay.

Details that bite in production

  • Nagle and delayed ACK. Nagle holds small writes until earlier data is acknowledged, and the peer may delay its ACK. Together they add tens of milliseconds. Low-latency systems set TCP_NODELAY.
  • Head-of-line blocking. One lost segment stalls every byte behind it, even bytes that already arrived. See section 7.
  • TIME_WAIT. The side that closes first keeps the connection state for twice the maximum segment lifetime. Many short connections can exhaust ports. Reuse connections.
  • Keepalive and idle timeouts. Load balancers and NATs drop idle flows silently. Send application heartbeats or enable keepalive.
  • No message boundaries. TCP is a stream. Every protocol above it needs framing: a length prefix, a delimiter, or a header with a length field.

4. TLS

TLS (version 1.3 is RFC 8446) adds encryption, integrity and server authentication on top of a reliable stream. It sits under HTTPS, gRPC, wss://, MQTT over 8883 and most FIX links. QUIC uses the same TLS 1.3 handshake but carries it in its own packets.

Handshake

Client and server agree a key with ephemeral Diffie-Hellman. The server proves its identity with a certificate chain and a signature.

Record layer

Data is cut into records of up to 16 KB, each encrypted and authenticated with an AEAD cipher such as AES-GCM or ChaCha20-Poly1305.

Extensions

SNI names the host so one IP can serve many sites. ALPN picks the application protocol: h2, http/1.1 or h3.

  • TLS 1.3 vs 1.2. 1.3 needs one round trip instead of two, drops RSA key exchange and old ciphers, and encrypts the certificate. Every new connection gets forward secrecy.
  • Resumption. A pre-shared key from an earlier session skips the certificate check. With 0-RTT the client sends data in its first flight, at the risk of replay.
  • Mutual TLS. The client also presents a certificate. Service meshes use mTLS so every service call is authenticated in both directions.
  • Where to end TLS. At the load balancer is simple and lets it route on HTTP. End to end keeps traffic encrypted inside the network. Many systems do both: terminate, then re-encrypt.

5. HTTP/1.1

HTTP/1.1 (semantics in RFC 9110, wire format in RFC 9112) is text over TCP. A request is a request line, headers, a blank line and an optional body. Connections are persistent by default, so many requests can reuse one TCP and TLS handshake.

GET /orders/42 HTTP/1.1
Host: api.example.com
Accept: application/json

HTTP/1.1 200 OK
Content-Type: application/json
Content-Length: 27

{"id":42,"status":"FILLED"}

One connection carries one response at a time. Pipelining exists but is effectively unused, since a slow response blocks the ones behind it. Browsers work around this by opening about six connections per origin. Bodies are framed by Content-Length or by chunked transfer encoding. The Upgrade header turns a connection into a WebSocket for two-way messages (section 10).

6. HTTP/2

HTTP/2 (RFC 9113) keeps HTTP semantics (methods, status codes, headers) and changes the wire format. Everything is a binary frame with a 9-byte header: 24-bit length, 8-bit type, 8-bit flags and a 31-bit stream id.

  • Streams and multiplexing. Each request and response is a stream. Frames of many streams interleave on one TCP connection, so one connection replaces six. Client streams use odd ids.
  • HPACK header compression (RFC 7541). A static table plus a per-connection dynamic table means repeated headers cost a byte or two.
  • Flow control per stream and per connection, with WINDOW_UPDATE frames. The initial window is 65,535 bytes.
  • Frame types: DATA, HEADERS, SETTINGS, WINDOW_UPDATE, RST_STREAM, PING, GOAWAY and a few more. RST_STREAM cancels one request without closing the connection.
  • Negotiation. TLS ALPN with the token h2. Server push is defined but browsers have removed it, so do not design around it.

HTTP/2 fixed head-of-line blocking at the HTTP layer and moved it down into TCP.

7. Head-of-line blocking

Three responses A, B and C are sent as four packets each. Click packets to lose them. A lost packet is resent and arrives 8 ticks late. Compare when each response is fully delivered to the application.

HTTP/1.1 here uses one connection, so responses go one after another. HTTP/2 interleaves them on one TCP stream. HTTP/3 interleaves them on independent QUIC streams.

TCP must hand bytes to the application in order. When packet B2 is lost, TCP holds back A3, C2 and everything else behind it, even though they arrived. QUIC knows which stream each frame belongs to, so it only holds back stream B.

8. QUIC

QUIC (RFC 9000) is a reliable, multiplexed, encrypted transport built on UDP, usually on port 443. It runs in user space, so it can evolve without kernel upgrades.

TLS 1.3 inside

Transport and crypto handshakes are one. New connections take 1 RTT, resumed ones can send data in 0 RTT.

Independent streams

Loss on one stream does not stall the others. No head-of-line blocking across streams.

Connection IDs

A connection survives an IP change, such as Wi-Fi to cellular, because it is not keyed by the address 4-tuple.

  • Better loss recovery (RFC 9002). Packet numbers never repeat, even for resent data, so RTT samples are never ambiguous.
  • Encrypted headers. Almost everything past the first bytes is encrypted and authenticated. Middleboxes cannot inspect or ossify it.
  • 0-RTT has a cost. Early data can be replayed by an attacker. Only send idempotent requests in 0-RTT.
  • Anti-amplification. Before the client address is validated, a server sends at most three times what it received. Client Initial packets are padded to 1200 bytes.
  • Trade-offs. More CPU per byte than kernel TCP with offloads. Some networks block or throttle UDP, so clients keep a TCP fallback.

9. HTTP/3

HTTP/3 (RFC 9114) is HTTP mapped onto QUIC. Each request uses its own bidirectional QUIC stream, and control data uses unidirectional streams. Stream multiplexing and flow control move into QUIC, so the HTTP/3 framing layer is thinner than HTTP/2.

  • QPACK (RFC 9204) replaces HPACK. HPACK assumes frames arrive in order, which QUIC streams do not guarantee across each other.
  • Discovery. A client first connects over TCP and sees an Alt-Svc: h3=":443" header, or finds an HTTPS DNS record, then switches to QUIC with ALPN h3.
  • Where it helps. High RTT, packet loss and moving clients. On a clean data center network the gain over HTTP/2 is small.

10. Real-time web: polling, SSE, WebSocket, WebTransport

Plain HTTP is request and response: the server cannot speak first. Four techniques get updates to a browser as they happen. They differ in direction, framing and what the network in between has to support.

Server-sent events

SSE is defined in the WHATWG HTML standard. The server answers a normal GET with Content-Type: text/event-stream and never ends the body. Each event is a few field: value lines followed by a blank line.

: comment lines like this one keep idle proxies from closing the stream
retry: 3000

event: price
id: 1042
data: {"sym":"AAPL","px":187.25}

const es = new EventSource('/prices');
es.addEventListener('price', e => render(JSON.parse(e.data)));
// After a drop the browser reconnects and sends Last-Event-ID: 1043
  • Strengths. Plain HTTP, so it passes proxies, uses normal auth cookies, and works with HTTP/2 multiplexing. Reconnect and resume come for free.
  • Limits. One direction and text only. EventSource cannot set custom headers, so token auth often uses fetch with a streamed body instead. On HTTP/1.1 each stream holds one of the browser's six connections per origin.
  • Watch for buffering. A proxy or compression layer that buffers the response delays every event. Disable buffering for the stream route.

WebSocket

WebSocket (RFC 6455) starts as an HTTP/1.1 request and then switches the TCP connection to its own framing. The server proves it understood the upgrade by hashing the client's key with a fixed GUID.

GET /stream HTTP/1.1
Host: api.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNhbXBsZSBub25jZQ==
Sec-WebSocket-Version: 13
Origin: https://app.example.com

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBiTxaQ9kYGzzhZRbK+xOo=
// accept = base64( SHA-1( key + "258EAFA5-E914-47DA-95CA-C5AB0DC85B11" ) )

After the 101, each message is one or more frames. The header is 2 to 14 bytes: a FIN bit, an opcode, a mask bit, a 7-bit length that can grow to 16 or 64 bits, and a 4-byte masking key on frames from the client. Build one below.

Repeat the text to push the length past 125 bytes (16-bit length) and past 65,535 bytes (64-bit length).

  • Opcodes. 0x1 text, 0x2 binary, 0x0 continuation, and the control frames 0x8 close, 0x9 ping, 0xA pong.
  • Why mask. Client frames are XORed with a random key so a hostile page cannot craft bytes that confuse a caching proxy. It is not encryption. Use wss:// for that.
  • Close codes. 1000 normal, 1001 going away, 1011 server error. 1006 means the connection died without a close frame; it is never sent on the wire.
  • You build the rest. Message types, request ids, acknowledgments, reconnect with backoff, resubscribe after reconnect and heartbeats are all application work. Libraries such as Socket.IO add some of it with their own protocol.
  • Operations. Check the Origin header to stop cross-site WebSocket hijacking. Connections are long-lived and stateful, so plan for draining on deploys and for idle timeouts on load balancers. WebSocket also runs over HTTP/2 (RFC 8441) and HTTP/3 (RFC 9220) with extended CONNECT.

WebTransport

WebTransport is a W3C browser API over an HTTP/3 session, with an HTTP/2 fallback in progress at the IETF. One session gives many independent reliable streams, so there is no head-of-line blocking between them, plus unreliable datagrams for data that is stale once late, such as game state. Browser support is still growing, so check it before you depend on it, and keep a WebSocket fallback.

11. gRPC

gRPC is an RPC framework on top of HTTP/2. You define services and messages in Protocol Buffers, and code generators build typed clients and servers in many languages.

service Orders {
  rpc Place (Order) returns (Ack);                // unary
  rpc Watch (Filter) returns (stream Fill);       // server streaming
  rpc Upload (stream Order) returns (Summary);    // client streaming
  rpc Trade (stream Order) returns (stream Fill);  // bidirectional
}

On the wire, a call is an HTTP/2 POST to /package.Service/Method with content-type: application/grpc. Each message gets a 5-byte prefix: one compressed flag byte and a 4-byte big-endian length. The result travels in HTTP trailers.

HEADERS   :method POST  :path /shop.Orders/Place  grpc-timeout 200m
DATA      00 | 00 00 00 1d | <29 bytes of protobuf>
HEADERS   :status 200   (response headers)
DATA      00 | 00 00 00 08 | <8 bytes of protobuf>
HEADERS   grpc-status 0  grpc-message ""   (trailers)
  • Status codes are separate from HTTP status: 0 OK, 4 DEADLINE_EXCEEDED, 5 NOT_FOUND, 14 UNAVAILABLE and so on. Retry only on codes that are safe to retry.
  • Deadlines propagate in grpc-timeout. Always set one, so a stuck downstream call fails fast instead of piling up.
  • Load balancing. One long-lived HTTP/2 connection carries every call, so an L4 load balancer pins a client to one backend. Use an L7 proxy (Envoy, a service mesh) or client-side balancing.
  • Browsers cannot read HTTP/2 trailers through fetch, so they use gRPC-Web through a proxy.

12. MQTT and AMQP

Both are broker protocols. Producers and consumers never talk to each other directly; they connect to a broker that stores and routes messages. They solve different problems.

MQTT

MQTT (OASIS, versions 3.1.1 and 5.0) is a small publish and subscribe protocol for devices on weak networks. The fixed header is as small as 2 bytes. Clients publish to topics such as plant/3/line/7/temp and subscribe with wildcards: + matches one level, # matches the rest.

QoSGuaranteePackets
0At most once. Fire and forget.PUBLISH
1At least once. Duplicates possible.PUBLISH, PUBACK
2Exactly once between two hops.PUBLISH, PUBREC, PUBREL, PUBCOMP
  • Retained messages. The broker keeps the last message on a topic and hands it to new subscribers, so a dashboard sees the current state at once.
  • Last Will. A client registers a message the broker publishes if the client disappears without a clean disconnect.
  • Sessions and keep-alive. A persistent session queues messages while a device is offline. The keep-alive interval lets both sides detect dead links.
  • Ports. 1883 plain, 8883 with TLS, and MQTT over WebSocket for browsers.

AMQP

AMQP comes in two different protocols that share a name. AMQP 0-9-1 is the RabbitMQ model: a producer publishes to an exchange, bindings route copies into queues, and consumers read queues. Exchange types are direct (exact routing key), fanout (every bound queue), topic (wildcard keys) and headers. AMQP 1.0 (OASIS and ISO standard) is a lower-level, symmetric link protocol used by Azure Service Bus, ActiveMQ Artemis and others, and RabbitMQ supports it too.

  • Channels. Many lightweight channels share one TCP connection, so a process does not need a connection per thread.
  • Acknowledgments. A consumer acks after it has processed a message. Unacked messages go back to the queue if the consumer dies. Publisher confirms tell the producer the broker has the message.
  • Prefetch. basic.qos caps how many unacked messages a consumer holds, which spreads work evenly and limits memory.
  • Versus Kafka. AMQP brokers delete a message once it is acked and route per message. Kafka keeps an ordered log that many consumer groups replay at their own pace, over its own binary TCP protocol.

13. WebRTC

WebRTC lets two browsers or apps send audio, video and data straight to each other, usually over UDP. It is a bundle of IETF protocols behind a W3C API.

Signaling

Not part of WebRTC. Peers swap SDP offers and answers and ICE candidates over any channel you choose, often a WebSocket.

ICE, STUN, TURN

ICE tries candidate address pairs. STUN tells a peer its public address behind NAT. TURN relays traffic when no direct path works.

Encryption

Mandatory. DTLS sets up keys. Media travels as SRTP, and data channels as SCTP over DTLS.

  • Media uses RTP with congestion control and feedback (RTCP). Late packets are dropped or concealed rather than resent, because latency matters more than completeness.
  • Data channels can be reliable and ordered like TCP, or unordered with limited retransmits, which suits game state.
  • Scaling. Full mesh works for a handful of peers. Larger calls send each stream once to a selective forwarding unit (SFU) that fans it out.

14. FIX

The Financial Information eXchange protocol carries orders, executions and market data between brokers, buy-side firms and exchanges. The classic encoding is tag=value pairs separated by the SOH byte (0x01), sent over a long-lived TCP connection. Below, SOH is shown as |.

Every message starts with a standard header and ends with a checksum trailer. 9= BodyLength counts the bytes after the BodyLength field up to and including the SOH before 10=. 10= CheckSum is the sum of every byte before it, modulo 256, written as three digits:

$$\text{CheckSum} = \Big(\sum_{i} b_i\Big) \bmod 256$$
TagFieldMeaning
8BeginStringProtocol version, such as FIX.4.4 or FIXT.1.1. Always first.
9BodyLengthByte count of the body. Always second.
35MsgTypeWhat the message is. Always third.
49 / 56Sender / TargetCompIDWho is talking to whom. Identifies the session.
34MsgSeqNumPer-direction sequence number for gap detection.
52SendingTimeUTC timestamp.
10CheckSumThree-digit checksum. Always last.

The session layer

FIX sessions outlive TCP connections. Sequence numbers keep counting across reconnects, often for a whole trading day, so neither side loses an order during a network blip.

  • Logon (A) opens the session and sets HeartBtInt (108). Logout (5) closes it.
  • Heartbeat (0) is sent when the line is idle. TestRequest (1) forces the peer to answer with a heartbeat.
  • ResendRequest (2) asks for a range when an incoming sequence number jumps. Replays carry PossDupFlag (43) = Y. SequenceReset (4) skips messages that should not be replayed, such as stale orders.
  • Reject (3) refuses a malformed message at the session level.

Common application messages are NewOrderSingle (D), ExecutionReport (8), OrderCancelRequest (F), OrderCancelReplaceRequest (G) and market data (W, X). FIX 5.0 split the session layer into FIXT.1.1. For lower latency, FIX also defines binary encodings: Simple Binary Encoding (SBE), FAST for market data, and the lightweight FIXP session protocol. Many exchanges offer their own binary order protocols next to FIX.

15. Choosing a protocol

NeedGood fitWhy
Public REST APIHTTP/1.1 or HTTP/2Every client, proxy, cache and tool speaks it.
Web pages on mobileHTTP/3, fallback HTTP/2Fewer round trips, no cross-stream stalls, survives network changes.

Pick the highest layer that meets your latency and loss needs. Every layer you build yourself is code you have to own.
