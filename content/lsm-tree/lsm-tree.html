LSM Tree

A write-optimized store. New data lands in memory, spills to disk as sorted immutable files, and background merges keep the pile tidy. Writes are sequential and fast, and reads pay for it by checking a few places.

Try the machine first

The memtable holds 4 entries. When it fills, it flushes to a new file in L0. Files in L0 may overlap, so a read checks them newest first. Compact merges every L0 file and L1 into one clean sorted run. Put a few keys, overwrite one, delete one, then get it and watch the search path.

1. The idea

  
Disks like big sequential writes and hate random ones. A B-tree updates pages in place, so every write is a seek. An LSM tree never edits anything on disk. It buffers writes in a sorted in-memory table, then writes the whole table out as one immutable file.

  
    
    
  • WAL. Each write is first appended to a log, so a crash does not lose the memtable.
    • 
    
  • Memtable. A sorted structure in memory, often a skip list. Reads and writes hit it first.
    • 
    
  • SSTable. A sorted string table: an immutable sorted file written when the memtable fills.
    • 
    
  • Compaction. A background merge that combines files, keeps the newest value per key, and drops dead data.
    • 
  

  
Never update in place. Append new facts, and merge later.






  
2. Reads, overwrites and deletes

  
An overwrite is just a newer entry for the same key. A delete cannot erase old copies sitting in older files, so it writes a tombstone, a marker that says "this key is gone". A read walks from newest to oldest and stops at the first entry it finds. If that entry is a tombstone, the answer is "not found".

  
Old copies and tombstones are only removed during compaction. In Fig 1, delete a key and compact: the tombstone and the value it hid both vanish.

  
    
    
  • Each file knows its smallest and largest key, so most files are skipped without a search.
    • 
    
  • Real engines also keep a Bloom filter per file, so a missing key usually costs no disk read at all.
    • 
  






  
3. The code

  
class Lsm {
  put(key, value) {
    this.wal.append(key, value);        // durability first
    this.mem.set(key, value);          // sorted, in memory
    if (this.mem.size >= LIMIT) this.flush();
  }
  delete(key) { this.put(key, TOMBSTONE); }

  get(key) {
    if (this.mem.has(key)) return unwrap(this.mem.get(key));
    for (const table of this.tables) {           // newest first
      if (key < table.min || key > table.max) continue;
      const hit = table.find(key);
      if (hit !== undefined) return unwrap(hit);
    }
    return undefined;
  }

  flush() {
    this.tables.unshift(writeSorted(this.mem));
    this.mem = new SortedMap();
    this.wal.reset();
  }
}

// Merge sorted runs. Earlier runs are newer, so they win ties.
function compact(runs, dropTombstones) {
  const out = new Map();
  for (const run of runs)
    for (const [k, v] of run) if (!out.has(k)) out.set(k, v);
  if (dropTombstones) for (const [k, v] of out) if (v === TOMBSTONE) out.delete(k);
  return sortByKey(out);
}






  
4. Compaction strategies

  
Compaction is where an LSM tree spends its effort, and the strategy sets the trade-off. Fig 1 uses the simplest one: everything into one run.

  

    
StrategyHow it worksBest for

    
      
Size-tieredMerge files of similar size into one larger fileHeavy writes, less write amplification

      
LeveledEach level is 10x larger, with non-overlapping files per levelHeavy reads, less space and read cost

      
Time-windowGroup files by time and drop whole windows at onceTime series and data with a TTL

    
  






  
5. Cost

  

    
Write
O(1)
Amortized: one log append and one memory insert.

    
Read
O(L · log n)
Up to one search per file or level, trimmed by ranges and Bloom filters.

    
Write amp.
~10-30x
Each byte may be rewritten by several compactions.

  

  
The three amplifications pull against each other. Compacting more often lowers read and space amplification but raises write amplification. Tuning an LSM tree means choosing which one to pay for.






  
6. Where it shows up

  
    
    
  • Embedded engines such as LevelDB and RocksDB, used inside many other systems.
    • 
    
  • Wide-column databases such as Cassandra, HBase and ScyllaDB.
    • 
    
  • Distributed SQL and time series stores such as CockroachDB, TiDB and InfluxDB.
    • 
  

  
A good rule: pick an LSM tree when writes dominate and you can accept background compaction work. Pick a B-tree when reads and range scans dominate and writes are modest.
