Dynamic programming

Some problems split into smaller problems that repeat. Solve each small problem once, store the answer, and build the big answer from the stored ones. That turns many exponential searches into a table you fill in polynomial time.

1. The idea: overlapping subproblems

  
The Fibonacci numbers are defined by $F(n) = F(n-1) + F(n-2)$ with $F(0) = 0$ and $F(1) = 1$. Written as plain recursion, the code follows the definition exactly, and it is terribly slow. Look at the call tree: $F(n-2)$ is computed once by $F(n)$ and again inside $F(n-1)$, and the waste doubles at every level.


  

  
Plain recursion makes $2F(n+1) - 1$ calls, which grows like $1.618^n$: about 331 million calls for $n = 40$. There are only $n + 1$ different subproblems, though. Store each answer the first time and the call count drops to $2n - 1$.

  
Dynamic programming applies when a problem has two properties:

  
    
    
  • Overlapping subproblems. The same smaller problem comes up again and again. If every subproblem were new, as in merge sort, caching would not help, and plain divide and conquer is enough.
    • 
    
  • Optimal substructure. The best answer to the whole problem is built from best answers to its parts. The shortest path from A to C through B contains a shortest path from A to B.
    • 
  

  
Dynamic programming is recursion plus a memory: never solve the same subproblem twice.






  
2. Top-down or bottom-up

  
There are two ways to write the same idea. Memoization (top-down) keeps the recursive code and adds a cache. Tabulation (bottom-up) fills an array in an order where every dependency is already done, which is exactly what Fig 1 does.


# Top-down: recursion + cache. Only the subproblems you actually need get computed.
from functools import cache

@cache
def fib(n):
    return n if n < 2 else fib(n - 1) + fib(n - 2)

# Bottom-up: fill the table from the base cases upward. No recursion depth limit.
def fib_table(n):
    dp = [0, 1] + [0] * (n - 1)
    for i in range(2, n + 1):
        dp[i] = dp[i - 1] + dp[i - 2]
    return dp[n]

# Bottom-up, keeping only what the next step reads: O(1) memory.
def fib_rolling(n):
    a, b = 0, 1
    for _ in range(n):
        a, b = b, a + b
    return a

3. A recipe for any DP problem

  
    
    
  1. Define the state. Write one sentence: "$dp[i][j]$ is the answer for ...". Most bugs are a vague state.
    2. 
    
  2. Write the transition. How does a state follow from smaller states? Usually "try every last choice and keep the best".
    3. 
    
  3. Set the base cases. The smallest states you can answer directly, such as an empty string or zero capacity.
    4. 
    
  4. Pick the order. Every state must come after the states it reads. For a grid that reads up and left, row by row works.
    5. 
    
  5. Read the answer, and if you need the actual solution, not just its value, store or recompute the choices and trace back.
    6. 
  

  
Take coin change: the fewest coins from the set $C$ that add up to amount $a$. The state is $dp[a]$, the fewest coins for amount $a$. The last coin used is some $c \in C$, and what remains is the smaller problem $a - c$:

  
$$dp[a] = \min_{c \in C,\ c \le a} \bigl(dp[a - c] + 1\bigr), \qquad dp[0] = 0$$

  
With coins $\{1, 3, 4\}$ and amount 6, greedy takes the largest coin first: $4 + 1 + 1$, three coins. The table tries every last coin and finds $3 + 3$, two coins. Greedy is right only for special coin systems; dynamic programming is right for all of them.






  
4. Classic recurrences

  
0/1 knapsack

  
Items have weight $w_i$ and value $v_i$, and the bag holds weight $W$. Let $dp[i][w]$ be the best value using the first $i$ items with capacity $w$. Item $i$ is either left out or taken:

  
$$dp[i][w] = \max\bigl(dp[i-1][w],\ dp[i-1][w - w_i] + v_i\bigr)$$

  
The table has $(n+1)(W+1)$ cells and each costs $O(1)$, so the run time is $O(nW)$. That is pseudo-polynomial: polynomial in the value $W$, but exponential in the number of bits needed to write $W$. Knapsack is NP-hard, and DP only makes it fast when $W$ is small.


  
Longest common subsequence

  
For strings $a$ and $b$, let $dp[i][j]$ be the length of the longest common subsequence of the first $i$ characters of $a$ and the first $j$ of $b$:

  
$$dp[i][j] = \begin{cases} dp[i-1][j-1] + 1 & \text{if } a_i = b_j \\ \max\bigl(dp[i-1][j],\ dp[i][j-1]\bigr) & \text{otherwise} \end{cases}$$

  
This is the core of diff: lines in the LCS are unchanged, everything else was added or removed. Real tools use Myers' algorithm, which finds the same answer faster when the two files are similar.


  
Edit distance

  
The Levenshtein distance is the fewest single-character inserts, deletes and replacements that turn $a$ into $b$. With $dp[i][0] = i$ and $dp[0][j] = j$:

  
$$dp[i][j] = \begin{cases} dp[i-1][j-1] & \text{if } a_i = b_j \\ 1 + \min\bigl(dp[i-1][j],\ dp[i][j-1],\ dp[i-1][j-1]\bigr) & \text{otherwise} \end{cases}$$

  
The three terms are delete, insert and replace. Spell checkers, fuzzy search and DNA alignment (Needleman–Wunsch, Smith–Waterman) are this table with different costs.


  
Longest increasing subsequence

  
Let $dp[i]$ be the length of the longest increasing subsequence that ends at element $i$. Then $dp[i] = 1 + \max\{dp[j] : j < i,\ x_j < x_i\}$, which is $O(n^2)$. Keeping, for each length, the smallest possible last element and binary-searching it brings this down to $O(n \log n)$. Better DP often means a smarter state, not a faster loop.






  
5. Cost, and how to shrink memory

  
The running time of a DP is almost always

  
$$\text{time} = \text{number of states} \times \text{work per transition}$$

  

    
ProblemStatesPer stateTimeMemory, rolling

0/1 knapsack$nW$$O(1)$$O(nW)$$O(W)$

When row $i$ only reads row $i-1$, keep two rows, or even one. In 0/1 knapsack the single-row version must loop the capacity downward, so that $dp[w - w_i]$ still holds the previous row's value. Loop upward and an item can be taken twice, which silently solves the unbounded knapsack instead.


def knapsack(items, W):
    dp = [0] * (W + 1)                 # dp[w] = best value with capacity w
    for weight, value in items:
        for w in range(W, weight - 1, -1):   # downward: each item used at most once
            dp[w] = max(dp[w], dp[w - weight] + value)
    return dp[W]

knapsack([(1, 1), (3, 4), (4, 5), (5, 7)], 7)   # 9: weights 3 + 4

  
Dropping rows loses the traceback, because the choices are gone. If you need the solution itself in little memory, Hirschberg's algorithm recovers an LCS or an alignment in linear space by splitting the problem in half.

Every DP is a shortest or longest path in a directed acyclic graph whose nodes are states and whose edges are transitions. The fill order is a topological order of that graph. If the graph has a cycle, the recurrence is not well defined and you need a different tool, such as Dijkstra or Bellman–Ford.

Query planners such as PostgreSQL's pick the cheapest join order by DP over subsets of tables.

    
Control, RL

Value iteration is DP: a state's value is the best reward plus the value of where it leads.

  






  
Pitfalls

  
    
    
  • Using greedy where only DP is correct, as with coins $\{1, 3, 4\}$. Prove the greedy choice, or use the table.
    • 
    
  • A state that leaves something out. If two situations with the same $dp$ index can need different answers, the state needs another dimension.
    • 
    
  • The wrong fill order, which reads a cell before it is computed. Check that every dependency comes earlier.
    • 
    
  • Looping the 1D knapsack upward, which allows reusing an item.
    • 
    
  • Deep recursion in top-down code: Python stops at about 1000 frames by default. Switch to bottom-up for long inputs.
    • 
    
  • A state space that is simply too big. $O(nW)$ with $W = 10^9$ will not finish; the problem needs a different idea.
