Merge sort

Split the array in half, sort each half, then merge the two sorted halves into one. Every level of splitting costs one pass, so the total is $O(n \log n)$ in every case.

1. The idea

  
Merging two sorted lists is easy and fast. Look at the front of each list, take the smaller item, repeat. That takes one pass. Merge sort uses this by turning sorting into a lot of merging.

  
A single item is already sorted. So split until each piece has one item, then merge pieces back up. Each level of the recursion merges $n$ items in total.

  
Sorting is hard. Merging two sorted lists is not. Reduce the first to the second.






  
2. Split, then merge

  
function mergeSort(a, lo = 0, hi = a.length - 1) {
  if (lo >= hi) return;
  const mid = (lo + hi) >> 1;
  mergeSort(a, lo, mid);
  mergeSort(a, mid + 1, hi);
  merge(a, lo, mid, hi);
}

function merge(a, lo, mid, hi) {
  const L = a.slice(lo, mid + 1), R = a.slice(mid + 1, hi + 1);
  let i = 0, j = 0, k = lo;
  while (i < L.length && j < R.length) {
    a[k++] = L[i] <= R[j] ? L[i++] : R[j++];   // <= keeps it stable
  }
  while (i < L.length) a[k++] = L[i++];
  while (j < R.length) a[k++] = R[j++];
}

  
Copy both halves first, then write back into the original array. Copying is why merge sort needs $O(n)$ extra space. Merging runs of length $p$ and $q$ writes exactly $p+q$ items and needs at most $p+q-1$ comparisons: every comparison outputs one item, and the last item is copied for free. If one run is entirely smaller than the other, only $\min(p,q)$ comparisons are needed.






  
3. Why it is always n log n

  
Let $T(n)$ be the work to sort $n$ items. Two half-size sorts, then a linear merge:

  
$$T(n) = 2\,T\!\left(\tfrac{n}{2}\right) + cn, \qquad T(1) = 0$$

  
Draw the recursion as a tree. The root merges $n$ items. Its two children merge $n/2$ each, which is $n$ again. Every level adds up to $cn$, and halving reaches size one after $\log_2 n$ levels:

  
$$T(n) = \underbrace{cn + cn + \dots + cn}_{\log_2 n \text{ levels}} = cn\log_2 n = \Theta(n \log n)$$

  
Unlike quicksort, the split never depends on the data. The halves are always equal, so there is no bad input. The worst case for comparisons is reached when every merge goes to the last item, and it has an exact formula:

  
$$W(n) = n\lceil \log_2 n \rceil - 2^{\lceil \log_2 n \rceil} + 1$$

  
For $n = 16$ this is $16 \cdot 4 - 16 + 1 = 49$ comparisons.


  
Close to the limit

  
Any sort that only compares items must tell apart all $n!$ orders of the input. Each comparison has two outcomes, so $k$ comparisons can separate at most $2^k$ orders. That forces

  
$$k \;\ge\; \log_2 n! \;=\; n\log_2 n - n\log_2 e + O(\log n) \;\approx\; n\log_2 n - 1.44\,n$$

  
For 16 items the bound is $\lceil \log_2 16! \rceil = 45$, and merge sort's worst case is 49. Merge sort is within a small linear term of the best any comparison sort can do, which is why it is the textbook proof that $\Theta(n\log n)$ is achievable.






  
4. Why it is stable

  
When two items are equal, the merge takes from the left half first (<=, not <). The left half holds items that came earlier in the input, so earlier stays earlier in the output.

  
This matters for multi-key sorts. Sort orders by customer, then stable-sort by date: orders on the same date stay grouped by customer. With < instead of <= the sort is still correct, but no longer stable. It is a one-character bug that no test with distinct keys catches.






  
5. Bottom-up: no recursion

  
The top-down version splits first and merges on the way back. You can skip the splitting entirely. Treat each item as a run of length 1, merge neighbors into runs of length 2, then 4, then 8, until one run is left.

  
function mergeSortBottomUp(a) {
  const n = a.length;
  for (let width = 1; width < n; width *= 2) {          // one pass per width
    for (let lo = 0; lo < n - width; lo += 2 * width) {
      const mid = lo + width - 1;
      const hi = Math.min(lo + 2 * width - 1, n - 1);
      merge(a, lo, mid, hi);
    }
  }
}

  
It does $\lceil \log_2 n \rceil$ passes over the array, needs no stack, and every pass is a sequential sweep. That shape is what tape drives, disk files and GPU kernels like.

7. Merging many runs at once

  
A two-way merge halves the number of runs per pass. A $k$-way merge reads the heads of $k$ runs and keeps them in a min-heap. Each output item costs one heap pop and one push, so merging $n$ items from $k$ runs costs $O(n \log k)$.

  
This is how databases sort data that does not fit in memory. With $N$ records and memory for $M$, first sort $\lceil N/M \rceil$ chunks in memory and write them out as runs. Then merge $k$ runs at a time:

  
$$\text{passes over the data} = 1 + \left\lceil \log_k \frac{N}{M} \right\rceil$$

  
Sorting 1 TB with 10 GB of memory gives 100 runs. A 100-way merge finishes in one more pass, so the whole sort reads and writes the data only twice. The cost is dominated by sequential disk I/O, which is exactly the access pattern merge sort has.






  
8. Linked lists and in-place merging

  
On a linked list, merging needs no buffer: relink the nodes instead of copying them. The extra space is only the recursion, $O(\log n)$, or $O(1)$ with the bottom-up version. Merge sort is the standard way to sort a linked list, because quicksort and heapsort both want random access.

  
function mergeLists(a, b) {
  const head = { next: null };
  let tail = head;
  while (a && b) {
    if (a.val <= b.val) { tail.next = a; a = a.next; }
    else                { tail.next = b; b = b.next; }
    tail = tail.next;
  }
  tail.next = a || b;     // append what is left, no copying
  return head.next;
}

  
On arrays, in-place stable merging exists but it is complicated. Block merge sorts and rotation-based merges reach $O(1)$ extra space, at the price of more moves and much harder code. Most libraries accept a buffer of $n/2$ items instead: copy only the left half out, then merge into the original array from the left.






  
9. Counting inversions for free

  
An inversion is a pair $i < j$ with $a[i] > a[j]$. It measures how unsorted an array is, from $0$ for sorted to $\binom{n}{2}$ for reversed. Counting them pair by pair is $O(n^2)$, but the merge step sees them in bulk. When an item is taken from the right half, it jumps ahead of every item still waiting in the left half, and each of those is one inversion.

  
while (i < L.length && j < R.length) {
  if (L[i] <= R[j]) a[k++] = L[i++];
  else { a[k++] = R[j++]; inversions += L.length - i; }
}

  
The total is $O(n \log n)$. The same trick computes Kendall's tau, a rank correlation used to compare two rankings, for example two search engines' results.






  
10. Merge sort in production: Timsort

  
Real data is rarely random. It has sorted stretches, appended tails and reversed blocks. Timsort, written by Tim Peters for Python in 2002, is a merge sort tuned for that.

  
    
    
  • Find natural runs. Scan for ascending runs, and reverse strictly descending ones (strictly, so equal items keep their order).
    • 
    
  • Minimum run length. Runs shorter than a "minrun" of 32 to 64 items are extended with binary insertion sort, which is fast on small ranges.
    • 
    
  • A merge policy. Runs go on a stack, and rules on their lengths decide which neighbors to merge, so merges stay balanced. Python 3.11 replaced the original rules with Powersort, which has provably near-optimal merge costs.
    • 
    
  • Galloping. When one run keeps winning, switch to exponential search to find how many items to copy in one block. Merging a short run into a long one costs about $O(\log n)$ comparisons instead of $O(n)$.
    • 
  

  
On already sorted input, Timsort does $n-1$ comparisons and no moves. Python's sorted, Java's Arrays.sort for objects, Android and V8's Array.prototype.sort all use Timsort or a close relative.

Merge sort does fewer comparisons than quicksort, but moves every item on every level. When comparisons are expensive, as with strings or user-supplied comparators, merge sort tends to win. When items are small numbers, quicksort usually does.






  
12. Common mistakes

  
    
    
  • Using < in the merge. Still sorted, but not stable.
    • 
    
  • Allocating a new buffer in every call. Thousands of small allocations dominate the run time. Allocate one buffer of size $n$ once and pass it down.
    • 
    
  • Recursing down to one item. Below about 16 items, insertion sort is faster. Every practical merge sort stops early.
    • 
    
  • Skipping the sorted check. If a[mid] <= a[mid + 1], the two halves are already in order and the merge can be skipped. One comparison makes sorted input linear.
    • 
    
  • Overflow in (lo + hi) / 2 with fixed-width integers. Use lo + (hi - lo) / 2. This exact bug sat in Java's binary search and merge sort for years.
    • 
  






  
13. Where it shows up

  
    
    
  • Stable sorting: many standard libraries use a merge sort variant, such as Timsort, for sorting objects.
    • 
    
  • External sorting: databases and tools like Unix sort sort chunks that fit in memory, then merge them from disk. A heap picks the smallest head among many chunks.
    • 
    
  • LSM trees: compaction is a k-way merge of sorted files.
    • 
    
  • Linked lists: merge sort needs no random access and no extra buffer there.
    • 
    
  • Counting inversions and rank correlation, during the merge step.
    • 
    
  • Parallel and distributed sorting: sort parts on separate cores or machines, then merge. MapReduce's shuffle phase is a big merge.
