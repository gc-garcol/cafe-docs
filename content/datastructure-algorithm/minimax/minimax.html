Minimax

How a program picks a move in a two-player game. Assume your opponent plays their best, look ahead through the game tree, and choose the move whose worst case is the best you can get.

1. The idea

  
In a turn-based game with perfect information, such as tic-tac-toe or chess, you can draw every future as a tree. Each node is a position. Each edge is a move. The leaves are finished games, or positions you score with a heuristic when you stop looking ahead.

  
Minimax assumes both players play perfectly. You pick the child with the highest score. The opponent picks the child with the lowest score. Scores are from your point of view, so a big number is good for you and bad for them. The value of a position $s$ is defined by a recursion:

  
$$V(s) = \begin{cases} \text{score}(s) & s \text{ is a leaf} \\ \max_{c \,\in\, \text{children}(s)} V(c) & \text{MAX to move} \\ \min_{c \,\in\, \text{children}(s)} V(c) & \text{MIN to move} \end{cases}$$

  
Pick the move that leaves you best off after the opponent has done their worst.

  
The value is a guarantee in both directions. If MAX plays the minimax move, it gets at least $V(\text{root})$ whatever MIN does. If MIN plays its minimax moves, MAX gets at most $V(\text{root})$. For two-player zero-sum games this is von Neumann's minimax theorem, and for finite games of perfect information Zermelo showed it already in 1913: every such game has a well-defined value under perfect play.






  
2. The algorithm

  
It is a depth-first recursion. A leaf returns its score. A MAX node returns the largest child value. A MIN node returns the smallest. The root's best child is your move.

  
function minimax(node, depth, isMax) {
  if (depth === 0 || isTerminal(node)) return score(node);
  if (isMax) {
    let best = -Infinity;
    for (const child of moves(node))
      best = Math.max(best, minimax(child, depth - 1, false));
    return best;
  } else {
    let best = Infinity;
    for (const child of moves(node))
      best = Math.min(best, minimax(child, depth - 1, true));
    return best;
  }
}

  
In Fig 1 with its starting scores, the left MIN node sees $5$ and $9$ and takes $5$. The right MIN node sees $2$ and $0$ and takes $0$. The root takes the larger, so it plays left and is guaranteed at least $5$.






  
3. Negamax: one branch instead of two

  
The MAX and MIN branches mirror each other. In a zero-sum game, a position worth $v$ to one player is worth $-v$ to the other, and

  
$$\min(a, b) = -\max(-a, -b)$$

  
So score every position from the point of view of the player to move, and always maximize the negated child values:

  
function negamax(node, depth) {
  if (depth === 0 || isTerminal(node)) return scoreForSideToMove(node);
  let best = -Infinity;
  for (const child of moves(node))
    best = Math.max(best, -negamax(child, depth - 1));
  return best;
}

  
It is the same algorithm with half the code, and almost every real engine is written this way. The one trap is the leaf score: it must be from the side to move, not from a fixed player.






  
4. Alpha-beta pruning

  
Minimax looks at every leaf, and the tree grows fast. Alpha-beta keeps the same answer but skips branches that cannot change it. It carries two numbers down the recursion:

  
    
    
  • $\alpha$: the best score MAX is already sure to get on the path so far.
    • 
    
  • $\beta$: the best score MIN is already sure to get on the path so far.
    • 
  

  
Only values strictly inside the window $(\alpha, \beta)$ can still change the decision at the root. When $\beta \le \alpha$, the window is empty. The player above would never allow this branch, so the remaining siblings are cut off. In Fig 1 the left side already guarantees MAX a $5$. The right MIN node finds a $2$ in its first branch, so it can only end up at $2$ or less. MAX will not choose it, and the second branch is never looked at.

  
function alphaBeta(node, depth, alpha, beta, isMax) {
  if (depth === 0 || isTerminal(node)) return score(node);
  if (isMax) {
    let best = -Infinity;
    for (const child of moves(node)) {
      best = Math.max(best, alphaBeta(child, depth - 1, alpha, beta, false));
      alpha = Math.max(alpha, best);
      if (beta <= alpha) break; // MIN above will avoid this branch
    }
    return best;
  } else {
    let best = Infinity;
    for (const child of moves(node)) {
      best = Math.min(best, alphaBeta(child, depth - 1, alpha, beta, true));
      beta = Math.min(beta, best);
      if (beta <= alpha) break; // MAX above will avoid this branch
    }
    return best;
  }
}
alphaBeta(root, depth, -Infinity, Infinity, true);

  
What a call returns depends on where the true value $v$ lies. This is why alpha-beta gives the exact answer at the root, where the window starts as $(-\infty, \infty)$:

  
$$\text{returned} \begin{cases} = v & \text{if } \alpha < v < \beta \\ \le \alpha & \text{if } v \le \alpha \quad (\text{fail low}) \\ \ge \beta & \text{if } v \ge \beta \quad (\text{fail high}) \end{cases}$$






  
5. How much does pruning save?

  
With branching factor $b$ and depth $d$, plain minimax scores all $b^d$ leaves. Alpha-beta's savings depend entirely on move order. Knuth and Moore showed in 1975 that with perfect ordering, best move first everywhere, it scores exactly

  
$$b^{\lceil d/2 \rceil} + b^{\lfloor d/2 \rfloor} - 1 \;\approx\; 2\,b^{d/2} \text{ leaves}$$

  
and no algorithm that is guaranteed to find the minimax value can score fewer. The reason: to prove a value, MAX must show one good move and that every reply to it is answered, while MIN must refute every MAX move with one reply. "One" and "every" alternate, so only every other level branches fully.

  

    
Move orderLeaves scoredEffective branching

An effective branching factor of $\sqrt b$ means that in the same time you can search twice as deep. For chess, $\sqrt{35} \approx 6$, which is roughly what strong engines achieve.

7. Making it practical

  
    
    
  • Depth limit and evaluation function: stop at depth $d$ and score the position with a heuristic, such as material count in chess.
    • 
    
  • Quiescence search: at the depth limit, keep searching captures and checks until the position is quiet. Otherwise the search stops in the middle of an exchange and misjudges it. This is called the horizon effect.
    • 
    
  • Move ordering: try the best move from a previous search first, then captures, then "killer" moves that caused cutoffs at the same depth elsewhere, then moves ranked by a history table.
    • 
    
  • Iterative deepening: search depth 1, then 2, then 3, until time runs out. Earlier passes are cheap compared with the last one, and they provide the move order for it.
    • 
    
  • Transposition table: the same position is reached by different move orders. Cache its value and best move under a Zobrist hash, a XOR of random 64-bit keys for each piece on each square.
    • 
    
  • Null-window search: principal variation search checks "is this move better than the best so far?" with an empty window $(\alpha, \alpha + 1)$, which prunes hard, and only re-searches with a full window when the answer is yes.
    • 
  






  
8. Chance, hidden information and huge trees

  
Minimax is for two players, zero-sum and full information. Other games need other backups.

  
    
    
  • Expectimax adds chance nodes, for dice or card draws, that average their children by probability: $V(s) = \sum_{c} P(c)\,V(c)$. Backgammon programs use it.
    • 
    
  • Monte Carlo tree search builds the tree selectively. It picks children with an upper confidence bound, plays random or learned games to the end, and backs up the results. The UCT rule tries the child $j$ that maximizes
    • 
  

  
$$\bar{X}_j + c\,\sqrt{\frac{\ln N}{n_j}}$$

  
where $\bar X_j$ is the average result through child $j$, $n_j$ its visit count and $N$ the parent's. The first term exploits, the second explores. AlphaGo and AlphaZero replaced random playouts with a value network and guided selection with a policy network.

  
    
    
  • Hidden information, as in poker, breaks the tree view: you do not know which node you are in. Counterfactual regret minimization and its descendants solve those games instead.
    • 
  






  
9. Common mistakes

  
    
    
  • Scoring from the wrong side. In negamax the leaf score must be from the player to move. A sign error makes the engine play for the opponent.
    • 
    
  • Not preferring faster wins. A win in 1 and a win in 5 both score "win", so the program may dawdle forever. Score wins as $\text{WIN} - \text{ply}$ and losses as $-\text{WIN} + \text{ply}$.
    • 
    
  • Caching bounds as exact values. After a cutoff, alpha-beta only knows a bound. A transposition table must store whether an entry is exact, a lower bound or an upper bound.
    • 
    
  • Expecting the opponent to be perfect. Minimax plays safe, not to exploit mistakes. Against weak opponents, a riskier line may score better in practice.
    • 
    
  • Treating pruning as approximate. Alpha-beta returns exactly the minimax value. Only depth limits and the evaluation function approximate.
    • 
  






  
10. Where it shows up

  
    
    
  • Board games: chess engines such as Stockfish run alpha-beta with all the tricks above and a neural evaluation function.
    • 
    
  • Solved games: tic-tac-toe, Connect Four and checkers were solved by exhaustive minimax-style search with huge tables.
    • 
    
  • Robust decisions: "minimize the maximum loss" appears in control, robust optimization and adversarial training of neural networks.
    • 
    
  • Related search: A* finds a cheapest path when there is no opponent. Minimax finds the best guarantee when there is one.
