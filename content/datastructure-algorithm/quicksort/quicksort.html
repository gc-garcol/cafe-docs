Quicksort

Pick a pivot, push smaller items to its left and larger items to its right, then sort each side the same way. The pivot lands in its final place after every pass.

1. The idea

  
Quicksort is divide and conquer, but the work happens before the recursion, not after. Partitioning does the real job. After one partition, the pivot sits where it belongs in the sorted array, and nothing will ever cross it again.

  
Partition once, then forget the pivot. Two smaller problems remain, and they do not interact.






  
2. Partition

  
Walk j from left to right. Whenever a[j] is smaller than the pivot, grow the smaller zone by one and swap the item into it. At the end, swap the pivot into the slot just after the zone.

  
function partition(a, lo, hi) {
  const pivot = a[hi];
  let i = lo - 1;                      // end of the "smaller" zone
  for (let j = lo; j < hi; j++) {
    if (a[j] < pivot) {
      i++;
      [a[i], a[j]] = [a[j], a[i]];
    }
  }
  [a[i + 1], a[hi]] = [a[hi], a[i + 1]];  // pivot into place
  return i + 1;
}

function quicksort(a, lo = 0, hi = a.length - 1) {
  if (lo >= hi) return;
  const p = partition(a, lo, hi);
  quicksort(a, lo, p - 1);
  quicksort(a, p + 1, hi);
}

  
Partitioning takes one pass, so it costs $\Theta(n)$ for a range of size $n$: exactly $n-1$ comparisons with the pivot. While j scans, the range is always split into four zones:

  
$$\underbrace{a[lo..i]}_{<\ \text{pivot}}\quad \underbrace{a[i{+}1..j{-}1]}_{\ge\ \text{pivot}}\quad \underbrace{a[j..hi{-}1]}_{\text{not seen yet}}\quad \underbrace{a[hi]}_{\text{pivot}}$$

  
This is the loop invariant. It is true before the first comparison (the first two zones are empty), each step keeps it true, and when j reaches hi the "not seen" zone is empty. One last swap puts the pivot between the two remaining zones, which is exactly its sorted position.






  
3. Hoare's original partition

  
Lomuto is the easiest to read, but Tony Hoare's 1961 scheme is what fast libraries build on. Two indexes walk toward each other. The left one stops on an item that is too big, the right one stops on an item that is too small, and the pair is swapped. It does about three times fewer swaps than Lomuto on random input, and it splits a range of equal items in the middle instead of sending them all to one side.

  

    

      
Lomuto

      
// one index scans, pivot = last
let i = lo - 1;
for (let j = lo; j < hi; j++)
  if (a[j] < pivot) swap(a, ++i, j);
swap(a, i + 1, hi);
return i + 1;      // pivot is final here

    

    

      
Hoare

      
// two indexes meet, pivot = middle
let i = lo - 1, j = hi + 1;
while (true) {
  do i++; while (a[i] < pivot);
  do j--; while (a[j] > pivot);
  if (i >= j) return j;   // split point
  swap(a, i, j);
}

    

  

  
One difference matters when you write the recursion. Hoare returns a split point, not the pivot's final index, so the calls are quicksort(a, lo, j) and quicksort(a, j + 1, hi). Using j - 1 as with Lomuto loses items or loops forever.






  
4. Why the pivot matters

  
Let $T(n)$ be the time to sort $n$ items. One partition costs $cn$, then two recursive calls follow, of sizes $k$ and $n-1-k$ where $k$ is the pivot's rank:

  
$$T(n) = T(k) + T(n-1-k) + cn$$

  
The value of $k$ decides everything.

  

    
CaseSplitRecurrenceResult

    
      
BestAlways in half$T(n) = 2T(n/2) + cn$$\Theta(n \log n)$

      
Lopsided but fixedAlways 1 : 9$T(n) = T(\tfrac{n}{10}) + T(\tfrac{9n}{10}) + cn$$\Theta(n \log n)$

      
WorstPivot is an extreme$T(n) = T(n-1) + cn$$\Theta(n^2)$

    
  

  
The middle row is the surprising one. Even a 1 : 9 split every time keeps the depth at $\log_{10/9} n$, which is still logarithmic. Quicksort does not need good pivots, only pivots that are not terrible most of the time. The worst case needs the pivot to be the smallest or largest item again and again, and then the comparisons add up to

  
$$(n-1) + (n-2) + \dots + 1 = \frac{n(n-1)}{2}$$

  
With the last item as pivot, an already sorted input does exactly this. Press Sorted array (worst case) in Fig 1 to watch it.


  
The average case, exactly

  
If the input is in random order, every rank $k$ is equally likely for the pivot. Averaging the recurrence over $k$ gives the expected number of comparisons $C(n)$:

  
$$C(n) = (n-1) + \frac{1}{n}\sum_{k=0}^{n-1}\bigl(C(k) + C(n-1-k)\bigr) = (n-1) + \frac{2}{n}\sum_{k=0}^{n-1} C(k)$$

  
Multiply by $n$, subtract the same line for $n-1$, and the sum telescopes to a closed form with the harmonic number $H_n = 1 + \tfrac12 + \dots + \tfrac1n \approx \ln n$:

  
$$C(n) = 2(n+1)H_n - 4n \;\approx\; 2n\ln n \;\approx\; 1.39\, n\log_2 n$$

  
There is a shorter way to see it. Call the items $z_1 < z_2 < \dots < z_n$ in sorted order. Two items $z_i$ and $z_j$ are compared only if one of them is the first pivot chosen among $z_i, \dots, z_j$. Any pivot strictly between them separates them for good. So the chance they are ever compared is $\tfrac{2}{j-i+1}$, and adding over all pairs gives the same $2n\ln n$:

  
$$\mathbb{E}[\text{comparisons}] = \sum_{i \lt j} \frac{2}{j-i+1} \le 2n H_n$$

  
So quicksort does about 39% more comparisons than the $n\log_2 n$ ideal, but each comparison is cheap: a tight loop over consecutive memory, few swaps, no extra array. That is why it usually beats merge sort in practice.

6. Choosing a pivot

  
    
    
  • First or last item: simple, and fine for random data, but sorted, reversed and almost sorted inputs are common in real life, and they hit the worst case.
    • 
    
  • Random item: swap a random index to the end first. The expected cost becomes $2n\ln n$ for every input. Bad luck is still possible, but the chance of $\Theta(n^2)$ is tiny and no input triggers it reliably.
    • 
    
  • Median of three: the median of the first, middle and last items. Sorted and reversed inputs become best cases, and the expected comparisons drop to about $1.19\,n\log_2 n$. Large ranges sometimes use the "ninther", a median of three medians.
    • 
    
  • Median of medians: finds a pivot guaranteed to be in the middle 40% in linear time, which makes the worst case $O(n\log n)$. It is slow in practice and mostly used in theory and in selection.
    • 
  

  
An adversary who knows your pivot rule can always build a bad input for a deterministic rule. Randomness, or a fallback like introsort, is the defense.






  
7. Duplicates and three-way partition

  
With many equal keys, a two-way partition keeps putting equal items on the same side. An array of all equal items is the extreme case: Lomuto makes it $\Theta(n^2)$. Dijkstra's "Dutch national flag" partition splits the range into three zones, smaller, equal and larger, and recurses only into the outer two. The equal block is finished in one pass.

  
function quicksort3(a, lo = 0, hi = a.length - 1) {
  if (lo >= hi) return;
  const pivot = a[lo];
  let lt = lo, i = lo + 1, gt = hi;
  // a[lo..lt-1] < pivot, a[lt..i-1] == pivot, a[gt+1..hi] > pivot
  while (i <= gt) {
    if (a[i] < pivot) swap(a, lt++, i++);
    else if (a[i] > pivot) swap(a, i, gt--);
    else i++;
  }
  quicksort3(a, lo, lt - 1);
  quicksort3(a, gt + 1, hi);
}

  
If there are only $d$ distinct keys, the recursion can never be deeper than $d$ levels, so the cost is $O(n \cdot \min(d, \log n))$ on average. With $d$ small, that is close to linear.






  
8. Quickselect: half the work

  
To find the $k$-th smallest item you do not need to sort. Partition once, see which side $k$ falls on, and recurse into that side only. The other side is thrown away.

  
function select(a, k, lo = 0, hi = a.length - 1) {
  while (lo < hi) {
    const p = partition(a, lo, hi);   // use a random pivot
    if (k === p) return a[k];
    if (k < p) hi = p - 1; else lo = p + 1;
  }
  return a[lo];
}

  
A random pivot lands in the middle half of the range with probability $\tfrac12$, which shrinks the range to at most $\tfrac34$ of its size. The work forms a geometric series:

  
$$T(n) \le n + \tfrac34 n + \left(\tfrac34\right)^2 n + \dots = 4n \quad\Rightarrow\quad O(n) \text{ expected}$$

  
The exact expected comparison count for the median is about $3.39\,n$. C++ std::nth_element and NumPy partition work this way.






  
9. Quicksort in production

  
No real library ships the textbook version. They add a few tricks that keep the speed and remove the weak spots.

  
    
    
  • Small ranges use insertion sort. Below about 16 to 32 items, recursion overhead costs more than the quadratic inner loop of insertion sort.
    • 
    
  • Recurse into the smaller side, loop on the larger. The smaller side has at most $n/2$ items, so the stack depth is at most $\log_2 n$ even when the splits are bad.
    • 
    
  • Introsort. Count the depth, and when it passes about $2\log_2 n$, switch that range to heapsort. The worst case becomes $O(n\log n)$. Typical C++ std::sort implementations do this.
    • 
    
  • Dual pivot. Two pivots split the range into three parts. Java uses Yaroslavskiy's dual-pivot quicksort for arrays of primitives.
    • 
    
  • Pattern-defeating quicksort (pdqsort). Detects sorted runs and bad splits, shuffles a few items when it sees an adversarial pattern, and uses block partitioning to avoid branch mispredictions. Go's sort package and Rust's sort_unstable build on it.
    • 
  

  
function sort(a, lo, hi, depth) {
  while (hi - lo > 16) {
    if (depth-- === 0) return heapsort(a, lo, hi);  // introsort fallback
    const p = partition(a, lo, hi);                 // median-of-3 pivot
    if (p - lo < hi - p) { sort(a, lo, p - 1, depth); lo = p + 1; }
    else                 { sort(a, p + 1, hi, depth); hi = p - 1; }
  }
  insertionSort(a, lo, hi);
}

11. Common mistakes

  
    
    
  • Fixed pivot on real data. First or last item as pivot turns sorted input, a very common case, into $\Theta(n^2)$ time and an $n$-deep stack that can overflow.
    • 
    
  • Mixing partition schemes. Lomuto returns the pivot's index, Hoare returns a split point. The recursive bounds differ.
    • 
    
  • Strict vs non-strict comparisons in Hoare. The inner loops must use < and >, so they stop on items equal to the pivot. With <= they can run off the end of the range.
    • 
    
  • Expecting stability. Sorting records by one key and then by another with quicksort loses the first order. Use a stable sort for that.
    • 
    
  • Computing the middle as (lo + hi) / 2 in languages with fixed-width integers. It can overflow. Use lo + (hi - lo) / 2.
    • 
  






  
12. Where it shows up

  
    
    
  • General-purpose sorting of arrays in memory. Many standard libraries use a quicksort variant, such as introsort, which falls back to heapsort when recursion gets too deep.
    • 
    
  • Quickselect: run one side of the partition only, to find the k-th smallest item, a median or a top-k in $O(n)$ average time.
    • 
    
  • Partition alone: moving all items that pass a test to the front, as in C++ std::partition, is the same loop without recursion.
    • 
    
  • Compare with merge sort: choose merge sort when you need stability, a guaranteed $O(n\log n)$, linked lists, or data that does not fit in memory.
