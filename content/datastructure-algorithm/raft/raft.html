Raft

How a group of servers agrees on one ordered log, even when some of them crash. One server is elected leader, it appends every command to its log, and a command counts as committed once a majority has stored it.

Try the machine first

Five servers start as followers. Press Step to advance time by one tick. When a follower hears nothing for too long it runs for leader. Then send a client write and watch it spread. Try Kill on the leader and watch a new election happen, then bring the old leader back.

1. The idea

  
Many servers must act like one reliable machine. If they all apply the same commands in the same order, they end up in the same state. So the problem becomes: agree on one log. Raft splits that into three smaller pieces that can be understood alone: leader election, log replication, and safety.

  
At any moment a server is a follower, a candidate, or the leader. Time is cut into terms, numbered upward. Each term has at most one leader, and a higher term always wins over a lower one.

  
One leader per term. Only the leader writes to the log.






  
2. Leader election

  
Followers expect a heartbeat from the leader. Each follower has a random election timeout. If it fires, the follower becomes a candidate, adds one to its term, votes for itself, and asks everyone else for a vote.

  
    
    
  • A server gives one vote per term, to the first candidate that asks.
    • 
    
  • A server refuses a candidate whose log is less up to date than its own.
    • 
    
  • A candidate with votes from a majority becomes leader and starts sending heartbeats.
    • 
    
  • If nobody wins, timeouts fire again. The random timeouts make repeated ties unlikely.
    • 
  

  
function onElectionTimeout(me) {
  me.term += 1;
  me.role = 'candidate';
  me.votedFor = me.id;
  me.votes = 1;
  broadcast({ type: 'RequestVote', term: me.term,
              lastLogIndex: me.log.length, lastLogTerm: lastTerm(me) });
}






  
3. Log replication

  
A client sends a command to the leader. The leader appends it to its own log, then sends AppendEntries to every follower. Each message says where the new entries attach: the index and term of the entry just before them.

  
A follower accepts only if its log has a matching entry at that spot. If not, it says no, and the leader steps back one entry and tries again until the logs agree. Then the follower overwrites anything that conflicts.

  
function onAppendEntries(me, m) {
  if (m.term < me.term) return reply(false);
  resetElectionTimer(me);
  if (m.prevIndex > 0 && termAt(me, m.prevIndex) !== m.prevTerm) return reply(false);
  appendAndTruncateConflicts(me, m.prevIndex, m.entries);
  me.commitIndex = Math.min(m.leaderCommit, lastIndex(me));
  reply(true);
}

  
An entry is committed once the leader has stored it on a majority of servers, and it is from the leader's current term. Committed entries are never lost. The next heartbeat tells followers the new commit index. In the table above, committed entries have a solid border.






  
4. Why it is safe

  
Two rules protect committed entries. A candidate needs votes from a majority, and a voter refuses a candidate with a staler log. Any two majorities overlap in at least one server. So a new leader must have collected a vote from a server that holds every committed entry, and it cannot win with a log that misses one.

  
Try it: write a few entries, kill the leader, and see who wins. The winner always has all committed entries. Uncommitted entries on a dead leader may be lost, and the client then has to retry. If you revive the old leader, it learns the new term, steps down, and has its log rewritten to match.

This demo leaves out several things a real system needs: network partitions, persistent storage, log compaction with snapshots, and changing cluster membership.






  
6. Where it shows up

  
    
    
  • Coordination stores: etcd (the brain of Kubernetes) and Consul.
    • 
    
  • Databases: CockroachDB, TiKV, and YugabyteDB replicate each data range with Raft.
    • 
    
  • Streaming: Kafka's KRaft mode and RabbitMQ quorum queues.
    • 
  

  
Raft is equivalent in purpose to Paxos, but it was designed to be easier to teach and implement. Most new systems pick Raft.
