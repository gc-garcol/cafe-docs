Raft

How a group of servers agrees on one ordered log, even when some of them crash. One server is elected leader, it appends every command to its log, and a command counts as committed once a majority has stored it.

1. The idea

  
Many servers must act like one reliable machine. If they all start in the same state and apply the same commands in the same order, they end up in the same state. This is state machine replication, and it turns the problem into: agree on one log. Raft splits that into three smaller pieces that can be understood alone: leader election, log replication, and safety.

  
At any moment a server is a follower, a candidate, or the leader. Time is cut into terms, numbered upward. Each term has at most one leader, and a higher term always wins over a lower one. Every message carries the sender's term. A server that sees a higher term adopts it and becomes a follower at once, which is how a stale leader finds out it has been replaced.

  
One leader per term. Only the leader writes to the log. Everything flows from leader to followers.

  
Each server keeps a little state on disk, because it must survive a restart: currentTerm, votedFor and the log. Everything else, such as the commit index, can be rebuilt.






  
2. Leader election

  
Followers expect a heartbeat from the leader. Each follower has a random election timeout. If it fires, the follower becomes a candidate, adds one to its term, votes for itself, and asks everyone else for a vote.

  
    
    
  • A server gives one vote per term, to the first candidate that asks.
    • 
    
  • A server refuses a candidate whose log is less up to date than its own.
    • 
    
  • A candidate with votes from a majority becomes leader and starts sending heartbeats.
    • 
    
  • If nobody wins, timeouts fire again. The random timeouts make repeated ties unlikely.
    • 
  

  
"Up to date" compares the last entry of each log, term first, then length. A voter $v$ grants its vote to candidate $c$ only if

  
$$\text{lastTerm}_c > \text{lastTerm}_v \quad\text{or}\quad \bigl(\text{lastTerm}_c = \text{lastTerm}_v \ \text{ and } \ \text{lastIndex}_c \ge \text{lastIndex}_v\bigr)$$

  

    

      
Candidate

      
function onElectionTimeout(me) {
  me.term += 1;
  me.role = 'candidate';
  me.votedFor = me.id;
  me.votes = 1;
  persist(me);
  broadcast({ type: 'RequestVote',
    term: me.term,
    lastLogIndex: lastIndex(me),
    lastLogTerm: lastTerm(me) });
}

    

    

      
Voter

      
function onRequestVote(me, m) {
  if (m.term > me.term) stepDown(me, m.term);
  const ok = m.term === me.term
    && (me.votedFor === null
        || me.votedFor === m.from)
    && upToDate(m, me);
  if (ok) {
    me.votedFor = m.from; persist(me);
    resetElectionTimer(me);
  }
  reply({ term: me.term, granted: ok });
}

    

  

  
The timeouts must respect an ordering, or the cluster either never elects anyone or elects all the time:

  
$$\text{broadcast time} \;\ll\; \text{election timeout} \;\ll\; \text{mean time between failures}$$

  
Broadcast time is a few milliseconds in a data center, failures are months apart, so timeouts of 150 to 300 ms are typical. etcd defaults to a 100 ms heartbeat and a 1000 ms election timeout.






  
3. Election lab

  
The leader has just crashed. Every follower's timer was last reset by its final heartbeat, and each timeout is drawn uniformly from $[150,\ 150 + \text{spread}]$ ms. When the first timer fires, that server asks for votes, and the requests take some time to arrive. Any server whose own timer fires before a request reaches it becomes a candidate too, and the vote may split. 4. Log replication

  
A client sends a command to the leader. The leader appends it to its own log, then sends AppendEntries to every follower. Each message says where the new entries attach: the index and term of the entry just before them.

  
A follower accepts only if its log has a matching entry at that spot. If not, it says no, and the leader steps back and tries again until the logs agree. Then the follower overwrites anything that conflicts.

  
function onAppendEntries(me, m) {
  if (m.term < me.term) return reply(false);
  resetElectionTimer(me);
  if (m.prevIndex > 0 && termAt(me, m.prevIndex) !== m.prevTerm) return reply(false);
  appendAndTruncateConflicts(me, m.prevIndex, m.entries);
  me.commitIndex = Math.min(m.leaderCommit, lastIndex(me));
  reply(true);
}

  
The consistency check gives the Log Matching property by induction: if two logs have an entry with the same index and term, they are identical up to that index. A follower can only accept entries that attach to a prefix it already shares with the leader.

  
The leader tracks two numbers per follower: nextIndex, the next entry to send, and matchIndex, the highest entry known to be stored there. It commits index $N$ when a majority stores it and the entry is from the current term:

  
$$\text{commitIndex} = \max \Bigl\{ N \;:\; \bigl|\{\, i : \text{matchIndex}_i \ge N \,\}\bigr| \ge \left\lfloor \tfrac{n}{2} \right\rfloor + 1 \ \text{ and } \ \text{log}[N].\text{term} = \text{currentTerm} \Bigr\}$$

  
Equivalently: sort the match indexes, including the leader's own last index, and take the median. Committed entries are never lost. The next heartbeat tells followers the new commit index, and every server applies entries up to it in order. In Fig 1, committed entries have a solid border.






  
5. Why only current-term entries are counted

  
The second condition in the commit rule looks unnecessary, but it is the subtlest part of Raft. Here is the scenario from the Raft paper, with five servers S1 to S5:

  
    
    
  1. Term 2: leader S1 writes entry 2 and copies it to S2 only, then crashes.
    2. 
    
  2. Term 3: S5 wins with votes from S3, S4 and itself, writes a different entry at index 2, and crashes before copying it.
    3. 
    
  3. Term 4: S1 comes back, wins, and copies its old term-2 entry to S3. Now it is on a majority: S1, S2, S3.
    4. 
    
  4. If S1 counted that as committed and then crashed, S5 could still win term 5, because its last term 3 is newer than their 2. S5 would overwrite the "committed" entry everywhere.
    5. 
  

  
The fix: a leader never commits an old-term entry by counting replicas. It commits a new entry from its own term, and the Log Matching property commits everything before it at the same time. That is also why a new leader appends a no-op entry as soon as it is elected.






  
6. Why it is safe

  
Raft guarantees five properties at all times. The last one is the goal, the others lead to it.

  

    
PropertyStatement

    
      
Election SafetyAt most one leader per term

      
Leader Append-OnlyA leader never overwrites or deletes its own entries

      
Log MatchingSame index and term means same log up to there

      
Leader CompletenessA committed entry is in the log of every later leader

      
State Machine SafetyNo two servers apply different commands at the same index

    
  

  
Election Safety and Leader Completeness both rest on one counting fact. With $n$ servers, a majority has $q = \lfloor n/2 \rfloor + 1$ members, and any two majorities $Q_1, Q_2$ must share a server:

  
$$|Q_1 \cap Q_2| \;\ge\; |Q_1| + |Q_2| - n \;=\; 2\left(\left\lfloor \tfrac n2 \right\rfloor + 1\right) - n \;\ge\; 1$$

  
Two candidates in the same term cannot both get a majority, because the shared server votes only once. And a committed entry sits on a majority, so the voters of any later leader include at least one server that holds it. That server refuses any candidate whose log is less up to date, so a candidate missing the entry cannot win.

  
Try it in Fig 1: write a few entries, kill the leader, and see who wins. The winner always has all committed entries. Uncommitted entries on a dead leader may be lost, and the client then has to retry. If you revive the old leader, it learns the new term, steps down, and has its log rewritten to match.






  
7. Running it for real

  
    
    
  • Snapshots. The log cannot grow forever. Each server periodically writes its state machine to a snapshot and drops the log prefix it covers. A follower that falls too far behind gets the snapshot with InstallSnapshot instead of old entries.
    • 
    
  • Membership changes. Switching from one set of servers to another at once could create two disjoint majorities. Raft either uses joint consensus, a transition config $C_{\text{old,new}}$ that needs majorities of both sets, or changes one server at a time, which keeps old and new majorities overlapping.
    • 
    
  • Linearizable reads. A leader that was cut off may not know it was replaced. Before answering a read, it confirms leadership with a heartbeat round (ReadIndex), or relies on a time lease when clocks are trusted.
    • 
    
  • Exactly-once commands. A client that times out retries, and the command could be applied twice. Clients tag commands with an ID and a sequence number, and the state machine skips duplicates.
    • 
    
  • PreVote and CheckQuorum. A server cut off by a partition keeps timing out and raising its term. When it reconnects, its high term forces a healthy leader to step down. PreVote first asks "would you vote for me?" without changing terms, and CheckQuorum makes a leader step down when it cannot reach a majority.
    • 
    
  • Batching and pipelining. Leaders send many entries per message and do not wait for one reply before sending the next batch. One fsync covers many commands.
    • 
  






  
8. Cost and limits

  

    
Commit latency
1 round trip
Leader to a majority and back, plus a disk write, in the normal case.

    
Fault tolerance
$f$ of $2f{+}1$
5 servers survive 2 crashes. 3 servers survive 1.

    
Throughput
one leader
All writes pass through one server.

  

  
To survive $f$ crashed servers, a majority must still be alive, so $n - f \ge \lfloor n/2 \rfloor + 1$, which gives

  
$$n \ge 2f + 1$$

Even sizes add a server without adding tolerance, and a bigger majority makes every commit wait for one more reply. Most deployments run 3 or 5 servers. Systems that need more throughput run many independent Raft groups, one per shard of the data, so different shards have different leaders.

  
Raft tolerates crashes, slow servers and lost or reordered messages. It does not tolerate servers that lie. That needs Byzantine fault tolerant protocols such as PBFT, which require $n \ge 3f + 1$. And like every consensus protocol, it cannot guarantee progress in a fully asynchronous network (the FLP result). The random timeouts make progress very likely, not certain.






  
9. Common mistakes

  
    
    
  • Replying before persisting. A server that grants a vote or acknowledges entries, then crashes before the fsync, can vote twice in one term or lose a committed entry.
    • 
    
  • Counting replicas of old-term entries. See section 5. Only current-term entries are committed by counting.
    • 
    
  • Resetting the election timer on every message. Reset it only on a valid AppendEntries from the current leader, or when granting a vote. Otherwise a candidate with a stale log can keep everyone from timing out.
    • 
    
  • Serving reads from followers or a stale leader without ReadIndex or a lease. They can return old data.
    • 
    
  • Deleting the follower log too eagerly. Truncate only from the first conflicting entry. A late, duplicated AppendEntries must not remove entries that came after it.
    • 
  






  
10. Where it shows up

  
    
    
  • Coordination stores: etcd (the brain of Kubernetes) and Consul.
    • 
    
  • Databases: CockroachDB, TiKV, and YugabyteDB replicate each data range with Raft.
    • 
    
  • Streaming: Kafka's KRaft mode and RabbitMQ quorum queues.
    • 
    
  • Verification: Raft's safety has been checked with TLA+ and proved in Coq, in the Verdi project.
    • 
  

  
Raft is equivalent in purpose to Multi-Paxos, but it was designed to be easier to teach and implement: a strong leader, logs without holes, and a separate election step. Most new systems pick Raft.
