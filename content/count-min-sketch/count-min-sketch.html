Count-Min Sketch

A small grid of counters that estimates how often each item appeared in a stream. It never stores the items, uses fixed memory, and may over-count but never under-counts.

Try the machine first

The sketch has 4 rows and 12 columns. Each row has its own hash function. Add an item and it bumps one counter in every row. Query an item and it reports the smallest of its 4 counters. With only 12 columns, collisions happen fast, so you can see the estimate drift above the true count.

1. The idea

  
A hash map that counts every distinct item grows with the number of distinct items. For a stream of URLs, IPs or search queries, that can be billions of keys. A count-min sketch gives up exactness to keep memory fixed.

  
It is a d × w matrix of counters. Each of the d rows uses its own hash function that maps an item to one of w columns.

  
Different items can share a counter, which only ever adds. So every counter is at least the true count, and the smallest one is the best guess.






  
2. Add and query

  
To add an item, increment one counter in each row. To query, read the same d counters and take the minimum.

  
class CountMin {
  constructor(w, d) {
    this.w = w; this.d = d;
    this.t = Array.from({ length: d }, () => new Uint32Array(w));
  }
  add(x, n = 1) {
    for (let j = 0; j < this.d; j++) this.t[j][hash(x, j) % this.w] += n;
  }
  count(x) {
    let m = Infinity;
    for (let j = 0; j < this.d; j++) m = Math.min(m, this.t[j][hash(x, j) % this.w]);
    return m;
  }
}

  
Both operations touch exactly d counters, so they cost O(d) no matter how many items the sketch has seen.






  
3. Why the minimum

  
Take an item with true count f. In each row, its counter holds f plus the counts of any other items that landed in the same column. Collisions in different rows hit different items, because the hash functions differ. It is unlikely that all d rows collide with something heavy at once, so at least one counter is usually close to f. The minimum picks it.

  
    
    
  • The estimate is never below the true count.
    • 
    
  • With w = ⌈e / ε⌉ and d = ⌈ln(1 / δ)⌉, the estimate exceeds the truth by more than ε · N with probability at most δ. N is the total number of items added.
    • 
  

  
The error scales with the stream length N, not with the item's own count. So the sketch is accurate for heavy hitters and weak for rare items. In the demo, query an item you never added. It can still return a positive number.






  
4. Sizing

  

    
Width w
e / ε
Wider means smaller error per query.

    
Depth d
ln(1 / δ)
Deeper means a lower failure chance.

    
Memory
O(w · d)
Fixed, however many items arrive.

  

  
Example: ε = 0.001 and δ = 0.01 give w = 2719 and d = 5. That is about 13,600 counters, or roughly 54 KB with 32-bit counters, for a stream of any length.

6. Where it shows up

  
    
    
  • Heavy hitters: pair the sketch with a small heap of the top-k items seen so far.
    • 
    
  • Network monitoring: per-flow packet counts at line rate.
    • 
    
  • Databases: frequency estimates for query planning.
    • 
    
  • Rate limiting and abuse detection: approximate request counts per key.
    • 
    
  • Caches: TinyLFU uses a count-min sketch to decide which entries to admit.
    • 
  

  
If you need to answer "have I seen this item?" rather than "how many times?", a Bloom filter is the lighter tool. The count-min sketch is its counting cousin.
