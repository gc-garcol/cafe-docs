1. What Archive is

  
Aeron Archive records message streams to storage and replays them later, or while they are still being recorded. It is a normal Aeron application. It listens on a control channel for requests, and records by subscribing to a stream like any other subscriber. Its limit is the speed of the disk, and with fast storage it can record or replay at 10 Gb line rate.

  
Recording turns a live stream into history you can read again.

  
Why record? To let a restarted service catch up on what it missed, to reproduce an incident in a test environment, and to run a new version against the same input as the live one.






  
2. Recording

  
You ask Archive to record a channel and stream pair. Each image that arrives is stored as its own recording with a recordingId.

  
    
    
  • Receiving end: record an IPC publication, or the image of a network publication, with a normal subscription.
    • 
    
  • Sending end: record a network publication using a spy subscription. It reads the publication buffer beside the Sender, so there is no network hop.
    • 
    
  • Extend: add to an existing recording by appending.
    • 
  

  
A spy has no real receiver to connect. To record with no subscribers connected, set the property that lets spies simulate a connection. IPC channels connect as soon as the Archive starts recording.






  
3. Replaying

  
A replay request names a recordingId, a start position and a length. An open-ended length keeps going. Archive reads the recording and publishes it on a new replay publication. The consumer subscribes to the replay channel and stream, not the live one.

  
    
    
  • A replay can read a finished recording or one still in progress.
    • 
    
  • If the replay reaches the end of a live recording, it tracks the live edge.
    • 
    
  • Send replays to a different channel and stream pair from the live one to avoid congestion.
    • 
    
  • A slow replay does not slow the live stream, because it is its own stream with its own flow control.
    • 
  






  
4. Replay merge

  
A late joiner needs history and then the live stream, with no gap and no repeat. Replay merge does this in stages.

  
    
    
  1. Replay the recording from the wanted position.
    2. 
    
  2. Once the replay is close to the live position, also add the live stream as a destination.
    3. 
    
  3. When the replay reaches the point where live data begins, drop the replay. The subscriber is now on the live stream.
    4. 
  

  
It works only if the consumer is fast enough to keep up. If it is slower than the live rate, it never catches up. That is why the demo replay runs faster than the live tick.






  
5. The catalog

  
The catalog lists what the Archive holds as recording descriptors. You can page through all of them or filter by channel and stream. A descriptor holds the recording id, start and stop timestamps, start and stop positions, stream and session ids, term and segment sizes, and the channel.

  

    
FieldMeaning

    
      
startPositionWhere in the stream the recording begins.

      
stopPositionWhere it ended. A value of -1 means it is still being recorded.

      
termBufferLengthThe stream's term size, used to map positions to files.

      
segmentFileLengthSize of each file on disk. A multiple of the term size.

    
  

  
The rec-pos counter shows the progress of each active recording, and tools such as AeronStat can read it.






  
6. Durability and checksums

  
The file sync level sets how hard Archive pushes data to disk.

  

    
LevelBehavior

    
      
0Write to the OS page cache and let it flush later.

      
1Force dirty data pages to disk.

      
2Force data pages and file metadata to disk.

    
  

  
If you raise the level, raise the catalog sync level to match. Higher levels cost latency and throughput.

  
Archive can compute a checksum while it records and check it on replay. CRC32 is always available and CRC32C is faster on newer JDKs. Use the same checksum for both, or replay fails. Checksums have a real performance cost.






  
7. Managing recordings

  
    
    
  • Truncate: cut a stopped recording shorter. Truncating to the start deletes it.
    • 
    
  • Replicate: copy a recording from one Archive to another, and optionally merge with a live stream to keep recording.
    • 
    
  • Purge and restore: detach the oldest segments of a long recording to save disk, and attach them back later.
    • 
    
  • Query: list descriptors and read the recorded position of an active recording.
    • 
  






  
8. Threading

  

    
ModeThreads

    
      
DEDICATEDThree: one for control and queries, one for recording, one for replay.

      
SHAREDOne thread does all of it.

      
INVOKERNone. Your code drives the duty cycle.

    
  

  
The Archive embeds a media driver, so the total thread count is the Archive mode plus the driver mode.
