Memory Fence

CPUs and compilers reorder memory operations to go faster. A single thread never notices, another thread can. A fence is the instruction that says: everything before me must be visible before anything after me.

1. Why hardware reorders

A store has to wait for the cache line to be owned before it can land, which can take a hundred cycles or more. Instead of stalling, the core drops the store into a small store buffer and keeps running. Later loads go straight to the cache. The core checks its own buffer first, so a thread always sees its own writes in order.

Other cores cannot see inside that buffer. To them, the load happened before the store. That is a StoreLoad reordering. The compiler adds its own reorderings on top, by caching values in registers and moving loads and stores around.

Fig 2 · Stores queue up, loads do not. This is the only reordering x86 allows, and it is the one the simulator shows.

2. Four kinds of reordering

Name each pair by the first and second operation in program order. A memory model says which pairs may appear swapped to other cores.

On x86, a full fence is mfence or any lock-prefixed instruction. On ARMv8 it is dmb ish, and ldar / stlr give acquire loads and release stores without a separate fence.

3. Acquire and release: one-way fences

Most code does not need a full fence. It needs to publish data: write the payload, then set a flag, and the reader must see the payload once it sees the flag. That needs only half a barrier on each side.

  • Release on the flag store: no earlier load or store may move below it.
  • Acquire on the flag load: no later load or store may move above it.

When the acquire load reads the value written by the release store, everything before the release happens-before everything after the acquire.

Fig 3 · Release keeps earlier writes above the flag. Acquire keeps later reads below it. Together they form a synchronizes-with edge.

4. Code

In C++ you rarely write a raw fence. You attach an ordering to the atomic operation itself, and the compiler emits the right instructions for each CPU and stops its own reordering too.

// Message passing: release / acquire is enough
int data;
std::atomic<bool> ready{false};

void producer() {
    data = 42;
    ready.store(true, std::memory_order_release);
}
void consumer() {
    while (!ready.load(std::memory_order_acquire)) {}
    assert(data == 42);                           // guaranteed
}

// Store buffering: needs StoreLoad ordering, so a full fence
std::atomic<int> x{0}, y{0};
void t0() {
    x.store(1, std::memory_order_relaxed);
    std::atomic_thread_fence(std::memory_order_seq_cst);   // mfence on x86, dmb ish on ARM
    r0 = y.load(std::memory_order_relaxed);
}
// or simply use the default: x.store(1); r0 = y.load();  (both seq_cst)

In Java, a volatile field gives sequentially consistent access, and VarHandle offers setRelease, getAcquire and explicit fullFence(). In Rust, std::sync::atomic::Ordering and fence mirror the C++ model.

5. Cost

Acquire / release on x86
~free

Plain loads and stores already have that order. Only the compiler is restrained.

Full fence
~20–100 cycles

Waits for the store buffer to drain. Hurts in hot loops.

Acquire / release on ARM
cheap

ldar / stlr are much lighter than dmb.

Pitfalls

  • volatile in C and C++ is not a fence. It stops the compiler from removing accesses, but it gives no ordering between threads.
  • A compiler barrier such as asm volatile("" ::: "memory") stops only the compiler. The CPU can still reorder.
  • Fences work in pairs. A release with no matching acquire on the reader side guarantees nothing.
  • Code that works on x86 can break on ARM, because x86 keeps three of the four orders for free. Test on weak hardware, or use tools such as ThreadSanitizer and model checkers like CDSChecker or GenMC.
  • Prefer atomics with the weakest ordering that is still correct over hand-placed fences, and prefer a mutex over both when performance allows.
