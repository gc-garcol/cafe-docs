Java Memory Model

When one thread writes a field and another reads it, what is the reader allowed to see? The Java Memory Model answers that question for every JVM on every CPU. Its core is one relation, happens-before, and a promise: write a program without data races and it behaves as if threads simply took turns.

    The schedules come from a model of the JMM: within a thread, operations that the rules do not order may swap, and the two threads then interleave at random. Real hardware is pickier. That is why such bugs show up after a deploy to ARM servers, or after the code gets hot and is recompiled.

    1. What the JMM is, and what it is not
    
  
    The Java Memory Model is chapter 17.4 of the Java Language Specification. It was rewritten by JSR-133 for Java 5 (2004), because the original model was both too weak to make common idioms safe and too strict to allow normal compiler optimizations. It defines, for any program, which values each read of a shared variable may return.
    
  
    The name is often confused with the memory layout of the JVM, which is a different topic. That layout says where data lives; the JMM says when a write by one thread becomes visible to another.
    
  
    
    
    JVM runtime areaHoldsShared between threads?
    
    
      
    HeapAll objects and arrays, including their fields. Managed by the garbage collector.Yes. This is what the JMM is about.
    
      
    Java stackOne frame per method call: local variables, operand stack, return address.No, one per thread.
    
      
    MetaspaceClass metadata (replaced PermGen in Java 8). Static fields live with the class object on the heap.Yes
    
      
    PC register, native stackThe current instruction of each thread; frames of native (JNI) calls.No
    
      
    Code cacheMachine code produced by the JIT compiler.Yes
    
        
  
    
  
    Local variables and parameters are never shared, so they never race. Instance fields, static fields and array elements can be, and the JMM calls them shared variables.
    

    


    
  
    2. Why Java needs one
    
  
    Three layers may reorder or delay your memory operations, each for speed, each invisible to a single thread:
    
  
    
    
    javac and the JIT
    reorder, hoist
    C2 and Graal move loads and stores, keep fields in registers and lift reads out of loops when no rule forbids it.
    
    
    The CPU
    store buffers
    Stores wait in a per-core buffer; loads can run ahead. ARM and POWER reorder far more than x86. See Memory Fence.
    
    
    Caches
    delay
    A write reaches other cores through the coherence protocol, not instantly. See False Sharing.
    
  
    
  
    A classic example is a stop flag. The JIT sees that the loop body never writes running, so it may read the field once:
    
  
    boolean running = true;          // not volatile

// worker thread                      // what the JIT may compile it to
while (running) { work(); }          if (running) { while (true) { work(); } }

// main thread, later
running = false;                    // the worker may never see this
    
  
    The transformation is legal because, without synchronization, the JMM never promises that the worker sees the main thread's write. Declaring the field volatile forbids it. The "Stop flag" test in Fig 1 shows the same thing.
    
  
    The JMM is the contract that lets all three layers optimize while giving programmers a small set of rules that work on every platform. The JVM implements it by emitting the right barriers per CPU and by telling the JIT which moves are off limits.
    

    


    
  
    3. Data races and the DRF guarantee
    
  
    Two accesses conflict if they touch the same shared variable and at least one is a write. A data race is a pair of conflicting accesses that are not ordered by happens-before. The JMM's main promise is short:
    
  
    If a program has no data races, every execution behaves as if it were sequentially consistent: one global order of all operations that respects each thread's program order.
    
  
    This is called DRF-SC (data-race-free implies sequential consistency). You do not need to think about reordering, store buffers or caches at all, as long as every conflicting pair is ordered by happens-before. That is the whole practical method: find the shared variables, and make sure each read and write of them is connected by one of the rules in the next section.
    
  
    Programs with races are not undefined behaviour as in C++: Java still guarantees memory safety, no out-of-thin-air values, and atomic access to references and to all primitives except non-volatile long and double. But a racy read may return any value the field has held or will hold, in ways that differ from one run, JIT tier or CPU to the next.
    

    


    
  
    4. Happens-before rules
    
  
    Happens-before is a partial order on actions. If action $a$ happens-before action $b$, written $a \xrightarrow{hb} b$, then $a$'s effects are visible to $b$ and $a$ is ordered before $b$. It is built from program order and synchronizes-with edges, closed under transitivity:
    
  
    $$a \xrightarrow{hb} b \;\text{ and }\; b \xrightarrow{hb} c \quad\Longrightarrow\quad a \xrightarrow{hb} c$$
    
  
    
    
    RuleEdge
    
    
      
    Program orderEach action in a thread happens-before every later action of that thread.
    
      
    Monitor lockAn unlock of a monitor happens-before every later lock of the same monitor.
    
      
    VolatileA write to a volatile field happens-before every later read of that field.
    
      
    Thread startt.start() happens-before every action in thread t.
    
      
    Thread endEvery action in t happens-before another thread returns from t.join() or sees t.isAlive() return false.
    
      
    Interruptt.interrupt() happens-before t detects it (InterruptedException or isInterrupted()).
    
      
    Default valuesWriting the default value (0, false, null) of every field happens-before the first action of any thread.
    
      
    Constructor to finalizerThe end of a constructor happens-before the start of that object's finalizer.
    
      
    TransitivityChains combine, which is what lets a single volatile flag publish many plain writes.
    
        
  
    
  
    "Later" means later in the synchronization order, the single total order the JMM puts on all lock, unlock and volatile actions. In the message-passing test with a volatile ready, the chain is data = 42 $\xrightarrow{po}$ ready = true $\xrightarrow{sw}$ r1 = ready $\xrightarrow{po}$ r2 = data, so a thread that sees ready == true must see data == 42.
    
  
    Happens-before is not about time. Two actions can run at the same instant with an edge between them, or minutes apart with none. What matters is the edge.
    

    


    
  
    5. volatile
    
  
    A volatile field gives three things: every read sees the latest write in the synchronization order (visibility), writes before a volatile write cannot move after it and reads after a volatile read cannot move before it (ordering), and all volatile accesses together are sequentially consistent, which also fixes the store-buffering test. Reads and writes of volatile long and double are also atomic.
    
  
    It does not make compound actions atomic. count++ is a read, an add and a write; two threads can both read 5 and both write 6:
    
  
    volatile int count;
count++;                              // still a race: lost updates

AtomicInteger count = new AtomicInteger();
count.incrementAndGet();              // one atomic read-modify-write (lock xadd on x86)

LongAdder hits = new LongAdder();      // better under heavy contention: per-thread cells
hits.increment();
    
  
    What it costs
    
  
    On x86 a volatile read compiles to a plain load, and a volatile write to a store followed by a full barrier (HotSpot uses a locked instruction such as lock addl), typically tens of cycles. On ARMv8 HotSpot uses ldar and stlr. Volatile is cheap enough for flags and published references, and too expensive for a field written in a tight loop.
    
  
    Use it for
    
  
      
    
    • Status flags written by one thread and read by others: volatile boolean running.
      • 
    
    • Publishing an immutable or effectively immutable object: volatile Config current, swapped as a whole.
      • 
    
    • The instance field in double-checked locking (section 8).
      • 
  
    

    


    
  
    6. synchronized and locks
    
  
    synchronized gives mutual exclusion and happens-before: everything a thread did before leaving a block on monitor m is visible to the next thread that enters a block on m. Both halves need the same monitor. A reader without the lock, or with a different lock, gets nothing.
    
  
    class Account {
  private long balance;                    // guarded by this
  synchronized void deposit(long v) { balance += v; }
  synchronized long balance()        { return balance; }  // the getter must lock too
}
    
  
    ReentrantLock, ReadWriteLock and StampedLock give the same memory effects as entering and leaving a monitor: unlock() happens-before a later successful lock() of the same lock. Since Java 21, virtual threads make blocking cheap, and since JDK 24 (JEP 491) they no longer pin their carrier thread inside synchronized, so the old advice to prefer ReentrantLock for virtual threads no longer applies.
    

    


    
  
    7. final fields and safe publication
    
  
    Creating an object and storing a reference to it are separate writes. Without a happens-before edge, another thread can see the reference before it sees the fields: the "Safe publication" test in Fig 1 shows a non-null p whose x is still 0.
    
  
    final fields close that gap. At the end of the constructor the JMM places a freeze on every final field. Any thread that obtains a reference to the object after the constructor finished, even through a data race, sees the final fields as the constructor set them, and also everything reachable through them as of the freeze, such as the contents of a final array. That is why String, Integer and records are safe to share however they are passed.
    
  
    The guarantee breaks if this escapes during construction, for example by registering a listener or starting a thread inside the constructor. The other thread can then see the object before the freeze.
    
  
    Safe publication idioms
    
  
    An object is safely published if both the reference and the object's state become visible together. Any of these works:
    
  
      
    
    1. Initialize it from a static initializer: static final Foo FOO = new Foo(); Class initialization is done under a lock by the JVM.
      2. 
    
    2. Store the reference in a volatile field or an AtomicReference.
      3. 
    
    3. Store it in a final field of an object that is itself properly constructed.
      4. 
    
    4. Store it in a field guarded by a lock that readers also take.
      5. 
    
    5. Put it in a thread-safe collection or hand-off: ConcurrentHashMap, BlockingQueue, CompletableFuture, an ExecutorService.
      6. 
  
    
  
    Immutable objects (all fields final, no escaping this) can be published by any means, even a racy one. Mutable objects need safe publication and synchronization for every later change.
    

    


    
  
    8. Double-checked locking
    
  
    The famous broken idiom tries to avoid locking on every call to a lazy singleton:
    
  
    class Lazy {
  private static Helper helper;          // BROKEN: not volatile
  static Helper get() {
    if (helper == null) {                // 1st check, no lock: a racy read
      synchronized (Lazy.class) {
        if (helper == null) helper = new Helper();
      }
    }
    return helper;                         // may be non-null but half-built
  }
}
    
  
    The first check reads helper without the lock, so it is the safe publication problem again: a thread can see the reference before the constructor's writes. Three correct versions:
    
  
    // 1. volatile field (correct since Java 5)
private static volatile Helper helper;
static Helper get() {
  Helper h = helper;                       // one volatile read on the fast path
  if (h == null) {
    synchronized (Lazy.class) {
      h = helper;
      if (h == null) helper = h = new Helper();
    }
  }
  return h;
}

// 2. holder class: the JVM's class initialization lock does the work, lazily
static Helper get() { return Holder.INSTANCE; }
private static class Holder { static final Helper INSTANCE = new Helper(); }

// 3. enum singleton
enum Singleton { INSTANCE; }
    
  
    The holder idiom is the usual choice for static singletons. Use the volatile version for lazily initialized instance fields.
    

    


    
  
    9. Atomics and VarHandle access modes
    
  
    Java 9 added VarHandle, which exposes four strengths of memory access on any field or array element. The atomic classes use the same modes underneath (AtomicInteger.lazySet is a release store).
    
  
    
    
    ModeMethodsGuarantee
    
    
      
    Plainget, setLike a normal field. Racy accesses get no ordering; no atomicity for long/double.
    
      
    OpaquegetOpaque, setOpaqueAtomic, and each variable is coherent: a thread never sees its values go backwards, and the access is not optimized away. No ordering with other variables.
    
      
    Release / acquiresetRelease, getAcquireEarlier accesses stay before a release store; later accesses stay after an acquire load. Enough for message passing, not for store buffering.
    
      
    VolatilegetVolatile, setVolatile, compareAndSetSame as a volatile field: release/acquire plus a single total order over all volatile accesses.
    
        
  
    
  
    class Mailbox {
  private int data;
  private boolean ready;
  private static final VarHandle READY;
  static {
    try { READY = MethodHandles.lookup().findVarHandle(Mailbox.class, "ready", boolean.class); }
    catch (ReflectiveOperationException e) { throw new ExceptionInInitializerError(e); }
  }
  void send(int v) { data = v; READY.setRelease(this, true); }
  Integer poll() { return (boolean) READY.getAcquire(this) ? data : null; }
}
    
  
    In Fig 1, switch message passing to "release / acquire" and the bug disappears; switch store buffering to the same option and the $0, 0$ result is still allowed. Weaker modes are for library authors chasing nanoseconds. Application code should use volatile, locks or the java.util.concurrent classes.
    
  
    VarHandle also has static fences: acquireFence(), releaseFence(), fullFence(), loadLoadFence() and storeStoreFence(), the Java counterparts of the fences on the Memory Fence page.
    

    


    
  
    10. What java.util.concurrent promises
    
  
    The package documentation of java.util.concurrent extends happens-before to its classes. You rarely need volatile yourself, because these hand-offs already create the edge:
    
  
    
    
    Action in thread Ahappens-before, in thread B
    
    
      
    Putting an object into any concurrent collectionAccessing or removing it from that collection
    
      
    Submitting a Runnable or Callable to an ExecutorIts execution begins
    
      
    The task's actionsReturning from Future.get()
    
      
    Completing a CompletableFutureDependent stages and join()
    
      
    Releasing: Semaphore.release, CountDownLatch.countDownA successful acquire, or await() returning
    
      
    Arriving at a CyclicBarrier or PhaserActions after the barrier in other threads
    
      
    Before Exchanger.exchangeAfter the matching exchange in the other thread
    
        
  
    
  
    So the pattern "build an object in one thread, queue.put(obj), queue.take() in another" is correct with plain fields, as long as the producer stops touching the object after the hand-off.
    

    


    
  
    11. Corner cases
    
  
      
    
    • Non-atomic long and double. JLS 17.7 allows a non-volatile 64-bit write to be split into two 32-bit halves, so a racing reader can see half of each value. 64-bit JVMs do not split in practice, but the spec permits it. Declaring the field volatile makes it atomic.
      • 
    
    • No word tearing. Writing one byte array element or boolean field never disturbs its neighbours, even though CPUs write whole words.
      • 
    
    • No out-of-thin-air values. Even with races, a read cannot return a value that no write produced through a circular "I read 42 because you wrote 42 because I wrote 42" justification. Formalizing this is the hardest part of the JMM and is still studied.
      • 
    
    • Benign races. String.hashCode() caches its hash in a plain field. A race can only make two threads compute the same value twice, because the value is a deterministic function of immutable data and an int write is atomic. Copy this trick only with that much care.
      • 
    
    • Thread.sleep and Thread.yield have no synchronization effect. A loop that sleeps while reading a plain flag can still spin forever.
      • 
    
    • Thread.onSpinWait() is a CPU hint for busy-wait loops (pause on x86). It does not create happens-before either; the flag still needs to be volatile.
      • 
  
    

    


    
  
    12. Testing with jcstress
    
  
    Memory model bugs depend on the JIT tier, the CPU and timing, so unit tests almost never catch them. The OpenJDK jcstress harness runs litmus tests like the ones in Fig 1 millions of times across JIT modes and reports every outcome it saw:
    
  
    @JCStressTest
@Outcome(id = "0, 0", expect = ACCEPTABLE_INTERESTING, desc = "Both reads saw the old value")
@Outcome(expect = ACCEPTABLE, desc = "Some interleaving")
@State
public class StoreBuffering {
  int x, y;
  @Actor public void actor1(II_Result r) { x = 1; r.r1 = y; }
  @Actor public void actor2(II_Result r) { y = 1; r.r2 = x; }
}
    
  
    On x86 this test reports $0, 0$ regularly, the store buffer at work. Make both fields volatile and the outcome disappears. Other tools: static analysis (Error Prone, SpotBugs inconsistent-synchronization checks), and plain code review against one question: what is the happens-before edge for this shared field?
    

    


    
  
    13. Common mistakes
    
  
      
    
    • Using volatile for count++ or check-then-act. Use an atomic class or a lock.
      • 
    
    • Locking the writer but not the reader, or using two different locks for one field.
      • 
    
    • Making only the data volatile instead of the flag: try "volatile data only" in Fig 1, the bug stays.
      • 
    
    • Double-checked locking without volatile.
      • 
    
    • Letting this escape from a constructor, which voids the final-field guarantee.
      • 
    
    • Sharing a HashMap, ArrayList or SimpleDateFormat between threads after "it worked in testing". Use the concurrent versions or confine them to one thread.
      • 
    
    • Assuming a bug cannot happen because "x86 doesn't reorder that". The JIT can, and ARM servers do.
      • 
    
    • Relying on Thread.sleep, timing or log statements to "make it visible". A println takes a lock internally and may hide the bug in debugging, then it returns in production.
