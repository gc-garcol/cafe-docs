False Sharing

Two threads write two different variables, yet they slow each other down. The variables share one cache line, and the hardware moves whole lines between cores.

1. Caches move lines, not variables

A CPU core never loads a single long from memory. It loads the whole cache line around it, usually 64 bytes on x86 and most ARM servers, and 128 bytes on Apple silicon. Every variable inside those bytes travels together.

That is great for reading arrays. It becomes a problem when two cores write to different variables that happen to share one line.

Fig 2 · Packed puts a and b 8 bytes apart in one line. Padded pushes b to the next line, at the cost of 112 unused bytes.

2. Coherence turns writes into a ping-pong

Caches stay consistent with a coherence protocol such as MESI. Each core's copy of a line is Modified, Exclusive, Shared or Invalid. Only a core holding the line in M or E may write it. To write a line it does not own, the core sends a read-for-ownership request, every other copy is invalidated, and the data moves across the interconnect.

With a packed layout, each a++ steals the line from core 1 and each b++ steals it back. A write that should cost about a cycle now waits for a cross-core transfer of tens to over a hundred cycles.

Fig 3 · Packed layout, strictly alternating writes. After the first write, every write is a coherence miss.

The sharing is false because no data is actually shared. The cost is real because the hardware only tracks ownership per line.

3. The fix: give hot fields their own line

Align or pad every variable that one thread writes often so that no other thread's hot data lands in the same line. Read-only data can share a line freely, because many cores can hold it in state S at once.

// C++17: the standard names the padding size
#include <new>
struct alignas(std::hardware_destructive_interference_size) PaddedCounter {
    std::atomic<long> value{0};
};
PaddedCounter counters[NUM_THREADS];   // one line per thread, no false sharing

// The classic bug: per-thread slots packed into one array
std::atomic<long> bad[NUM_THREADS];  // 8 counters share each 64-byte line

Other languages have the same tool. Java offers @Contended (enable it outside the JDK with -XX:-RestrictContended), and libraries such as the LMAX Disruptor and Agrona pad fields by hand. Rust has crossbeam_utils::CachePadded.

The other fix is to share less. Let each thread accumulate into a local variable and publish the total once at the end.

4. Finding it

  • The symptom: adding threads makes the program slower or barely faster, even though the threads touch disjoint data.
  • On Linux, perf c2c record then perf c2c report lists cache lines with many HITM events, meaning loads that hit a line modified in another core's cache. It also shows which offsets inside the line are touched.
  • Hardware counters for cross-core snoops or remote hits tell the same story in VTune and other profilers.

5. Cost

L1 hit
~1–4 cycles

The line is already owned in M or E.

Cross-core transfer
~40–200 cycles

Higher across sockets. Paid on every write under false sharing.

Padding
64–128 B

Memory spent per hot field to buy back the speed.

Pitfalls

  • 64 bytes is not always enough. Intel's adjacent-line prefetcher fetches lines in pairs, and Apple silicon uses 128-byte lines, so many libraries pad to 128 bytes.
  • Padding only helps false sharing. If two threads really write the same counter, the fix is to split the work, not to add bytes.
  • Padding everything wastes cache. Pad only the fields that different threads write in hot loops.
  • Heap allocators may not honour your alignment unless you use aligned allocation, such as C++17 aligned new or posix_memalign.
  • Fields of an object a JVM or compiler reorders can end up next to each other again. Check the real layout, for example with JOL on the JVM.
