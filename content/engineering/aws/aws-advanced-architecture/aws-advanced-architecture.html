1. HA

  
    
    
  • Remove single points of failure: at least two zones for every tier.
    • 
    
  • Put instances behind a load balancer with health checks, and use Auto Scaling to replace failed ones.
    • 
    
  • Keep servers stateless and store state in managed multi-AZ services, such as S3, DynamoDB, Aurora and RDS Multi-AZ.
    • 
    
  • Leave spare capacity so losing one zone does not overload the rest.
    • 
  






  
2. DR

  
Two numbers drive the design. RTO is how long you can be down. RPO is how much recent data you can lose. The four strategies, from cheapest, are backup and restore, pilot light, warm standby and multi-site active/active. Automate recovery with infrastructure as code, use AWS Backup, and test restores regularly. An untested plan is a guess.







  
3. Multi-region

  
Use a second Region for disasters, for users far away, or for data rules. Route users with Route 53 (failover, latency or weighted routing) or Global Accelerator, and cache with CloudFront. Replicate data with S3 cross-Region replication, DynamoDB global tables or Aurora Global Database. The hard part is data: cross-Region writes add latency and need a plan for conflicts. Do it only when the requirement justifies the complexity.







  
4. Cost Optimization

  
    
    
  • Right-size: match instance size to real use, and delete idle resources.
    • 
    
  • Commit: Savings Plans or Reserved Instances for steady load. Spot for fault-tolerant work.
    • 
    
  • Scale with demand and shut down non-production at night.
    • 
    
  • Storage: S3 lifecycle rules and Intelligent-Tiering. Delete old snapshots.
    • 
    
  • Data transfer: cross-AZ and internet egress and NAT Gateway traffic add up. Use VPC endpoints and CloudFront.
    • 
    
  • Visibility: tag everything, and use Cost Explorer and Budgets with alerts.
