Rate limiter strategies

A rate limiter decides, for each request, whether it may go through now, wait, or be turned away. Every algorithm answers "how many is too many, and over what span of time?" a little differently. This page runs six of them on the same traffic, then covers concurrency limits, distributed counters, where to enforce limits and how to tell clients to slow down.

1. Why limit, and what to call it

A service has finite capacity: threads, database connections, CPU, money for a downstream API billed per call. Without a limit, one client with a bug in a retry loop, one scraper, or one sudden viral moment can use all of it, and everyone else gets timeouts. A rate limiter caps how much each caller may use, so that overload hits the caller who causes it, early and cheaply, instead of hitting everyone deep inside the system.

  • Protection. Keep the service inside the load it was sized for.
  • Fairness. Share capacity between tenants so one cannot starve the rest.
  • Cost. Cap spend on metered dependencies such as an LLM or SMS API.
  • Abuse. Slow down credential stuffing, scraping and enumeration of IDs.

The words get mixed up, so it helps to separate them:

TermMeaningExample
Rate limitRequests per unit of time, per key. Excess is rejected.100 requests per minute per API key
Throttling / shapingExcess is delayed instead of rejected, so the output is smooth.A queue that sends 10 messages per second
QuotaA budget over a long period, often tied to billing.1 million calls per month
Concurrency limitRequests in flight at the same time, not per second.At most 20 open queries per tenant
Load sheddingThe server drops work because it is overloaded, whoever sent it.Reject low-priority traffic when CPU is above 90%

A limit is a promise to the callers you keep, paid for by the callers you turn away. The algorithm decides how fair and how predictable that trade is.

2. Fixed window counter

Cut time into windows of length $W$, for example whole minutes. Keep one counter per key per window. Each request increments it; if the count is above $N$, reject. When the window ends, start a new counter at zero. In Redis this is two commands, INCR rl:42:1700000040 and an EXPIRE on the first increment.

  • One integer per key, O(1) per request, trivial to explain to users ("1000 per hour, resets on the hour").
  • All clients get their reset at the same instant, so traffic spikes at the top of every window.
  • The boundary problem: a client can send $N$ just before a reset and $N$ just after.

A span of length $W$ that straddles a boundary can hold the end of one window and the start of the next, so the fixed window lets through up to twice the limit:

$$\max_{t}\ \bigl|\{\text{accepted in } [t,\ t+W)\}\bigr| \;=\; 2N \quad\text{(fixed window, worst case)}$$

Choose "Window edge" in Fig 1: the fixed window row accepts every request, and the table shows $2N$ in one span of $W$ seconds. The sliding log holds that span to exactly $N$ and the sliding counter to about $N$. The token bucket and GCRA allow $N$ plus whatever refilled during the span, by design, and the leaky queue keeps its output at $N$ by delaying the excess instead of rejecting it.

3. Sliding window log

Store the timestamp of every accepted request, per key. On a new request, drop timestamps older than $t - W$, count the rest, and accept if the count is below $N$. The window is anchored at "now", so there is no boundary to exploit, and the limit holds exactly over every span.

It costs memory and time proportional to $N$: a limit of 10,000 per hour is up to 10,000 timestamps per key. In Redis it is usually a sorted set: ZREMRANGEBYSCORE to trim, ZCARD to count, ZADD to record, all in one Lua script or MULTI. Use it when limits are small and exactness matters, such as login attempts or password resets.

A variant also records rejected requests. Then a client that keeps hammering stays blocked until it stops for a full window, which is a useful penalty for abuse but harsh for an honest client in a retry loop.

4. Sliding window counter

A cheap approximation of the log. Keep the fixed window counters for the current and the previous window. Assume the previous window's requests were spread evenly, and count only the part of it that still overlaps the sliding window that ends now:

$$\hat n(t) \;=\; n_{\text{prev}}\cdot\frac{W - (t - t_w)}{W} \;+\; n_{\text{cur}}$$

where $t_w$ is the start of the current window. Accept if $\hat n + 1 \le N$. For example, with $N = 100$ per minute, 84 requests last minute and 36 so far this minute, 15 s into it: $\hat n = 84 \cdot 0.75 + 36 = 99$, so one more is allowed.

Two integers per key, no boundary burst, and close to the exact log on real traffic, which is why Cloudflare and many API gateways use it. It is wrong when traffic in the previous window was very uneven: if all of it arrived in the last second, the estimate undercounts.

5. Token bucket

A bucket holds up to $C$ tokens and is refilled at $r$ tokens per second. Each request takes one token (or $c$ tokens for an expensive call). If there are not enough tokens, reject. You do not need a timer to refill: store the token count and the time of the last update, and top up lazily when the next request arrives.

$$b(t) \;=\; \min\bigl(C,\; b(t_0) + r\,(t - t_0)\bigr), \qquad \text{accept if } b(t) \ge c$$

Two numbers set two separate things: $r$ is the sustained rate and $C$ is the burst. Over any span of length $\Delta$, the bucket accepts at most $C + r\Delta$ tokens' worth. That makes it a good fit for APIs where clients are idle, then send a short burst, and is why AWS API Gateway, Stripe and Envoy's local rate limit describe their limits as "rate and burst".

6. Leaky bucket

  
The name covers two different things, and both appear in the literature.

  
As a queue (traffic shaping)

  
Requests enter a FIFO queue of size $C$. A worker takes one out every $1/r$ seconds and passes it on. If the queue is full, new requests are dropped. The output is perfectly smooth, never faster than $r$, whatever the input looks like. In Fig 1 the leaky bucket row is this version: bursts become evenly spaced blue dots, and the table shows the average wait.

  
Good when the thing behind the limiter cannot take bursts at all: a legacy system, a hardware device, a partner API with a strict per-second limit. Bad for interactive APIs, because queued requests wait, and a client cannot tell a slow server from a long queue. Nginx limit_req works this way; with burst=20 nodelay it stops delaying and behaves like the meter below.

  
As a meter (policing)

  
Keep a level that drains at rate $r$. Each request adds 1; if that would overflow capacity $C$, reject. Nothing is queued. This is the token bucket seen from the other side: the level is $C - b$, the used tokens instead of the free ones, and it makes exactly the same decisions.






  
7. GCRA

  
The Generic Cell Rate Algorithm comes from ATM networks and is the leaky bucket meter with a clever encoding: it stores one timestamp per key and no counter. Let $T = 1/r$ be the spacing between requests at the sustained rate and $\tau = (C - 1)\,T$ the burst tolerance. The state is the theoretical arrival time $\text{TAT}$, the time the next request would be due if the client sent at exactly rate $r$.

  
$$\text{accept at } t \iff t \;\ge\; \text{TAT} - \tau, \qquad \text{then } \text{TAT} \leftarrow \max(\text{TAT},\, t) + T$$

  
A client ahead of schedule by more than $\tau$ is rejected. A rejected request does not change the state. Compare the token bucket and GCRA rows in Fig 1: they always agree, because they are the same limiter. GCRA wins in practice because it is one value to read and write, which fits an atomic compare-and-set and costs less memory in Redis. The redis-cell module and several gateway libraries implement it. The time to wait after a rejection is simply $\text{TAT} - \tau - t$.






  
8. Concurrency and adaptive limits

  
Rate is not the only resource. A request that takes 30 s holds a connection for 30 s, and 10 of those per second exhaust a pool that 10 fast requests per second would never touch. Little's law ties the three together: the number in flight $L$ equals the arrival rate $\lambda$ times the time each one spends inside, $d$.

  
$$L \;=\; \lambda\, d$$

  
At 200 requests per second and 50 ms each, about 10 are in flight. If latency jumps to 2 s because a dependency is slow, the same rate means 400 in flight. A concurrency limit (a semaphore, a bulkhead, a connection pool) caps $L$ directly and protects against exactly this case, which a per-second limit does not.

  
Adaptive limits

  
A fixed number goes stale as the code, hardware and dependencies change. An adaptive limiter measures and adjusts, like TCP congestion control. The simplest rule is AIMD, additive increase and multiplicative decrease:

  
$$L \leftarrow \begin{cases} L + 1 & \text{request succeeded and latency is normal} \\ \lfloor \beta L \rfloor & \text{timeout, error or latency spike}, \quad 0.5 \le \beta < 1 \end{cases}$$

  
Netflix's concurrency-limits library and Envoy's adaptive concurrency filter grow the limit while latency stays near its minimum and shrink it when queueing shows up. Google's SRE book describes client-side adaptive throttling: each client tracks its own requests and accepts, and rejects locally with probability

  
$$p_{\text{reject}} \;=\; \max\!\left(0,\ \frac{\text{requests} - K\cdot\text{accepts}}{\text{requests} + 1}\right)$$

  
with $K$ around 2. When the backend starts refusing, clients stop sending most of the doomed requests before they reach the network.

  
Load shedding by priority

  
When the server itself is overloaded, it should drop the least valuable work first: background syncs and prefetches before user clicks, and user clicks before checkout. Tag requests with a priority at the edge and let every limiter consult it.






  
9. Distributed rate limiting

  
With one server, a limiter is a map in memory. With 20 servers behind a load balancer, a limit of 100 per minute per user must hold across all of them. There are three broad options.

  

    
OptionHowTrade-off

    
      
Local onlyEach of $K$ servers enforces $N / K$.No network call. Wrong when load is uneven or $K$ changes; a user pinned to one server gets only $N/K$.

      
Central storeAll servers update one counter in Redis per request, atomically.Exact, but adds a round trip (about 0.3 ms) and makes Redis a dependency of every request.

      
Local + syncEnforce locally and push usage to a shared store every few hundred ms, or lease batches of tokens.Cheap and fast; may overshoot by one sync interval of traffic.

    
  

  
The read-modify-write race

  
A central counter is only correct if each update is atomic. Two gateways that read, compare and write in separate steps can both let a request through when only one should go:

  

    
StepGateway AGateway BCounter (limit 5)

    
      
1GET → 44

      
2GET → 44

      
34 < 5, allow, SET 55

      
44 < 5, allow, SET 55, but 6 were allowed

    
  

  
Fix it by letting the store do the arithmetic. For a fixed window, INCR returns the new value atomically, so compare after incrementing. For a token bucket, sliding log or GCRA, put the read, the decision and the write in one Lua script (EVALSHA), which Redis runs without interleaving. Use the store's clock (TIME in the script) rather than each server's, so clock skew between servers does not create or destroy tokens.

  
Failure modes

  
    
    
  • Fail open or closed. If Redis is unreachable, allowing everything (fail open) keeps the API up but unprotected; rejecting everything (fail closed) turns a cache outage into a full outage. Most public APIs fail open with a local fallback limit, while security limits such as login attempts fail closed.
    • 
    
  • Hot keys. One tenant's counter lives on one Redis shard. A giant tenant can overload it; split the key into $M$ sub-counters, each with $N/M$, and pick one at random.
    • 
    
  • Multiple regions. A global counter across regions costs a cross-region round trip. Usually each region gets its own share, and the shares are rebalanced from usage now and then.
    • 
  






  
10. Keys, tiers and where to enforce

  
What to count by

  
The key decides who shares a budget. Common keys are the API key or OAuth client, the authenticated user, the tenant, the source IP (for anonymous traffic), and the endpoint. Real systems combine several, for example 1000 per minute per tenant and 20 per minute per user on POST /login. IP keys are weak: many users share one IP behind a corporate NAT or a mobile carrier, and an attacker with a botnet has thousands. Behind a proxy, read the client IP from a header that only your own proxy can set, otherwise anyone can forge it.

  
Not all requests cost the same. A search across a year of data is worth more tokens than a lookup by ID. Weighted limits, where each request takes a cost $c$ from the bucket, model this. GitHub's GraphQL API, for example, charges points per query based on the nodes it may return.

  
Where to enforce

  

    
LayerExampleGood for

    
      
ClientSDK with a local token bucket, adaptive throttlingBeing a good citizen; avoids wasted round trips

      
Edge / WAFCloudflare, AWS WAF rate-based rulesFloods and abuse by IP, before traffic reaches you

      
API gatewayAWS API Gateway, Kong, Envoy global rate limit servicePer API key and plan limits, one place for all services

      
Service mesh sidecarEnvoy local rate limit, IstioService-to-service protection without code changes

      
ApplicationMiddleware, a library like Bucket4j or Resilience4jLimits that need business context: tenant plan, request cost

Layers complement each other. The edge stops floods cheaply and coarsely, the gateway enforces the contract per customer, and the resource limits catch whatever got through.






  
11. Telling the client

  
A rejected request should say so clearly: HTTP 429 Too Many Requests, with a Retry-After header in seconds. Do not use 503 for a client exceeding its own limit; keep that for server overload, where the client is not at fault. gRPC uses the status RESOURCE_EXHAUSTED.

  
Many APIs also advertise the remaining budget on every response. The de facto headers are X-RateLimit-Limit, X-RateLimit-Remaining and X-RateLimit-Reset. The IETF HTTPAPI working group is standardizing this in the RateLimit header fields draft, with a RateLimit-Policy field for the policy and a RateLimit field for the quota left:

  
HTTP/1.1 429 Too Many Requests
Retry-After: 2
RateLimit-Policy: "default";q=100;w=60
RateLimit: "default";r=0;t=2
Content-Type: application/problem+json

  
As an Internet-Draft it may still change; check the current version before relying on the exact syntax. The headers tell clients what is left, but a limit is still enforced on the server: a header is advice, never a grant.

  
Retrying well

  
A client that retries a 429 immediately makes the overload worse, and a thousand clients that all wait exactly 2 s and retry together create a new spike. Honour Retry-After when it is present. Otherwise use exponential backoff with full jitter, where attempt $k$ waits a random time:

  
$$\text{sleep}_k \;\sim\; \text{Uniform}\bigl(0,\ \min(\text{cap},\ \text{base}\cdot 2^{k})\bigr)$$

  
Cap the number of attempts, retry only idempotent requests (or send an idempotency key), and use a retry budget, for example "retries may add at most 10% to traffic", so retries cannot multiply load during an outage.

13. In code

  
A token bucket in a Redis Lua script. Redis runs the whole script atomically, so there is no race between servers, and it uses the Redis clock, so server clock skew does not matter:

  
-- KEYS[1] = bucket key; ARGV = capacity, refill per second, cost
local cap  = tonumber(ARGV[1])
local rate = tonumber(ARGV[2])
local cost = tonumber(ARGV[3])
local tm   = redis.call('TIME')                  -- {seconds, microseconds}
local now  = tonumber(tm[1]) + tonumber(tm[2]) / 1e6

local s      = redis.call('HMGET', KEYS[1], 'tokens', 'ts')
local tokens = tonumber(s[1]) or cap               -- a new key starts full
local ts     = tonumber(s[2]) or now
tokens = math.min(cap, tokens + (now - ts) * rate)  -- lazy refill

local allowed = tokens >= cost
if allowed then tokens = tokens - cost end
redis.call('HSET', KEYS[1], 'tokens', tokens, 'ts', now)
redis.call('PEXPIRE', KEYS[1], math.ceil(cap / rate * 1000)) -- a full bucket needs no state

local retry = 0
if not allowed then retry = (cost - tokens) / rate end
return { allowed and 1 or 0, math.floor(tokens), tostring(retry) } -- floats as strings

  
And a middleware that calls it, keys by user or by IP, sets the headers and fails open if Redis is down, in JavaScript with node-redis and Express:

  
const POLICY = { cap: 20, rate: 5 };               // burst 20, then 5 requests/s

async function rateLimit(req, res, next) {
  const who = req.user ? `u:${req.user.id}` : `ip:${req.ip}`; // req.ip needs 'trust proxy' set correctly
  let reply;
  try {
    reply = await redis.evalSha(TOKEN_BUCKET_SHA, {
      keys: [`rl:${who}`],
      arguments: [String(POLICY.cap), String(POLICY.rate), '1'],
    });
  } catch (err) {
    log.warn('rate limiter unavailable, failing open', err);
    return next();
  }
  const [allowed, remaining, retry] = reply;
  res.set('RateLimit-Policy', `"default";q=${POLICY.cap};w=${POLICY.cap / POLICY.rate}`);
  res.set('RateLimit', `"default";r=${remaining}`);
  if (allowed === 1) return next();

  res.set('Retry-After', String(Math.max(1, Math.ceil(Number(retry)))));
  res.status(429).json({ error: 'rate_limited', retryAfterSeconds: Math.ceil(Number(retry)) });
}

  
Load the script once with SCRIPT LOAD to get its SHA, and reload it on a NOSCRIPT error after a Redis restart. On a Redis Cluster, every key a script touches must be in KEYS so it routes to the right shard. The fail-open branch keeps the API up during a Redis outage; for login or OTP limits, return 503 there instead.
