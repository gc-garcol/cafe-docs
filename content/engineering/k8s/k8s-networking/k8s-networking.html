Kubernetes Networking

How Pods find and reach each other and the outside world. Services, DNS, ingress, the CNI plugin and the rules that enforce it all.

#kubernetes#k8s#service#coredns

Which Pods does a Service reach?

A Service has a stable address and a label selector. Its endpoints are the Pods that match the selector and are ready. Click a Pod to flip its readiness, then send requests.

1. Pod Networking

  
Every Pod gets its own IP. Any Pod can reach any other Pod by IP with no NAT, across nodes. Containers in one Pod share the network namespace and talk over localhost. The CNI plugin builds this flat network.







  
2. ClusterIP / NodePort / LoadBalancer

  

    
TypeReachable from

    
      
ClusterIPInside the cluster only. The default.

      
NodePortA fixed port on every node.

      
LoadBalancerAn external load balancer from the cloud provider.

      
ExternalNameA DNS alias to a name outside the cluster.

    
  
  
A Service has a stable virtual IP and picks ready Pods by label. A headless Service (clusterIP: None) skips the virtual IP and returns Pod IPs.







  
3. CoreDNS

  
CoreDNS is the cluster DNS server. A Service web in namespace shop is web.shop.svc.cluster.local. Inside the same namespace the short name web works because of the search list in each Pod's /etc/resolv.conf.







  
4. Ingress Controller

  
An Ingress routes outside HTTP and HTTPS traffic to Services by host and path, and terminates TLS. It does nothing alone. An ingress controller such as NGINX or Traefik watches Ingress objects and does the routing.







  
5. Gateway API

  
The successor to Ingress with roles split across objects: a GatewayClass (the implementation), a Gateway (listeners, owned by platform teams) and HTTPRoute (rules, owned by app teams). It also supports TCP, gRPC, header matching and traffic splitting without vendor annotations.







  
6. CNI

  
The Container Network Interface is the plugin contract the kubelet uses to wire up a Pod. The plugin assigns the IP and sets up routes. Common choices are Calico, Cilium (eBPF) and Flannel. Many also enforce NetworkPolicy. Without a CNI, nodes stay NotReady.







  
7. NetworkPolicy

  
By default all Pods can talk to all Pods. A NetworkPolicy selects Pods and lists allowed ingress and egress. Once a Pod is selected, anything not allowed is dropped. The CNI must support it.


kind: NetworkPolicy
spec:
  podSelector: {}           # every Pod in the namespace
  policyTypes: [Ingress]    # no rules = deny all ingress






  
8. kube-proxy / iptables / IPVS

  
On every node, kube-proxy turns the Service and endpoint lists into kernel rules. In iptables mode a packet to the Service IP is rewritten to one endpoint, and rule lookup grows with the number of Services. IPVS mode uses hash tables and scales better. No proxy process sits in the data path. Some CNIs, such as Cilium, replace kube-proxy with eBPF.
