Caching strategies

A cache is a fast copy of slow data. The hard part is not storing the copy, it is deciding who fills it, who updates it, and when it stops being true. This page runs eight read and write strategies side by side, then covers eviction, invalidation, stampedes and the layers a real system stacks up.

1. Why cache, and what it costs

  
A database query might take 5 ms. A read from an in-memory cache such as Redis takes about 0.3 ms over the network, and a read from the process's own memory takes well under a microsecond. If most reads can be served from the copy, the average read gets much faster and the database does much less work.

  
With hit ratio $h$, the expected read time is a weighted average of a hit and a miss. A miss pays for the cache lookup and the database:

  
$$T = h\,t_{\text{cache}} + (1-h)\,\bigl(t_{\text{cache}} + t_{\text{db}}\bigr) = t_{\text{cache}} + (1-h)\,t_{\text{db}}$$

  
With $t_{\text{cache}} = 0.3$ ms and $t_{\text{db}} = 5$ ms, a 90% hit ratio gives 0.8 ms and a 99% hit ratio gives 0.35 ms. Going from 90% to 99% cuts the database load by a factor of ten, which is often worth more than the latency.

  
The price is that you now have two copies of the truth. Every strategy below is a different answer to three questions:

  
    
    
  • Who fills the cache on a miss: the application, or the cache itself?
    • 
    
  • What happens on a write: update the cache, delete the entry, or leave it alone?
    • 
    
  • When does the database learn about a write: before the call returns, or later?
    • 
  

  
There are only two hard things in computer science: cache invalidation and naming things. The rest of this page is about the first one.






  
2. Read strategies

  
Cache-aside (lazy loading)

  
The application owns the logic. It asks the cache first. On a miss it reads the database itself and puts the result in the cache with a TTL. The cache is a plain key-value store and knows nothing about the database.

  
    
    
  • Only data that is actually read gets cached, so memory is not wasted on cold keys.
    • 
    
  • If the cache is down, the app can still read the database, just slower.
    • 
    
  • The first read of every key is a miss, and the miss path costs three round trips.
    • 
    
  • Writes go to the database and usually delete the cache entry, so the next read reloads it.
    • 
  

  
This is the default choice for Redis and Memcached, and the most common pattern in practice.


  
Read-through

  
The same flow, but the cache does the loading. The application only ever talks to the cache. On a miss, the cache calls a loader you registered, stores the result and returns it. Libraries such as Caffeine and Guava LoadingCache, and products such as NCache or a DynamoDB Accelerator (DAX) cluster, work this way.

  
The app code gets simpler, and the loading logic lives in one place, which makes it easy to add request coalescing there. In exchange, the cache must know how to reach the database, and a cache outage now blocks reads.


  
Refresh-ahead

  
A hot key that expires causes a miss, and on a busy key many readers see it at the same moment. Refresh-ahead reloads an entry in the background before it expires, when it is read late in its life (for example in the last 40% of the TTL). Readers keep getting hits. In Fig 1, read the key, press "+10 s" twice and read again: the cache refreshes itself while still serving the old value.

  
It works well when access is predictable. For keys that are read once and never again, it wastes database queries.


  
Stale-while-revalidate

  
A softer version of the same idea. When an entry has expired but is still in memory, return it immediately and refresh it in the background. The reader pays no latency, at the cost of one possibly stale answer. The HTTP header Cache-Control: max-age=60, stale-while-revalidate=30 asks browsers and CDNs to do exactly this for 30 seconds after expiry.






  
3. Write strategies

  
Write-through

  
The application writes to the cache, and the cache writes to the database in the same call. The call returns only after both have the new value. The cache is never behind the database for that key, so reads right after a write are fresh.

  
The write is slower, because it waits for two stores. Data that is written but never read still fills the cache, so write-through is usually paired with a TTL. Without a transaction across both, a failure between the two writes still leaves them different, so production code retries or falls back to deleting the entry.


  
Write-behind (write-back)

  
The application writes to the cache and gets an answer at once. The cache queues the change and writes it to the database later, often in batches. Writes are as fast as the cache, and ten updates of the same key can collapse into one database write.

  
The risk is durability. Until the queue is flushed, the only copy of the new value is in the cache. In Fig 1, choose write-behind, write twice and press "Crash cache": both writes are gone. Use it for data you can afford to lose or rebuild, such as view counters and metrics, or back the queue with a durable log.


  
Write-around

  
Writes go straight to the database and skip the cache. The cache is filled only by reads, as in cache-aside. This keeps write-heavy, rarely read data such as logs or bulk imports from flushing useful entries out of the cache.

  
If the key is already cached, the old value stays there until its TTL runs out. In Fig 1, read, then write with write-around and read again: the cache returns the previous version. That is why write-around is usually combined with a short TTL, or with a delete on write, which turns it into cache-aside.


  
Update or delete on write?

  
With cache-aside, after writing the database you can either set the new value in the cache or delete the entry. Prefer delete. Two concurrent writers can set their values in the cache in the opposite order to the database, leaving the cache wrong until the TTL. A delete is idempotent: whatever the order, the next read loads the current value.






  
4. Keeping it fresh: TTLs

  
A time to live is the safety net under every strategy. Even if an invalidation is lost, an entry cannot be wrong for longer than its TTL. Choosing it is a trade between staleness and hit ratio:

  

    
DataTypical TTLWhy

    
      
Exchange rates, pricessecondsStale values cost money, but even 1 s absorbs thousands of reads.

      
User profile, settingsminutesChanges are rare and usually invalidated on write.

      
Product catalog, confighoursChanges are deployed or published, and can purge explicitly.

      
Static assets with a hash in the namea yearThe content never changes; a new version gets a new URL.

    
  

  
Add jitter. If a deploy warms 100,000 keys with the same 300 s TTL, they all expire in the same second and the database takes the whole load at once. Use a TTL of $300 \pm 30$ s chosen at random per key instead.






  
5. Invalidation

  
Deleting the right entries at the right time is where most caching bugs live. The common approaches, from simplest to most robust:

  

    
ApproachHowWeak spot

    
      
TTL onlyNever delete; let entries expire.Stale for up to one TTL after every write.

      
Delete on writeThe code that writes the DB deletes the key.Every write path must remember to do it, including scripts and admin tools.

      
Versioned keysPut a version in the key: user:42:v7. Bump the version on write.Old versions linger until evicted; the version itself must be read from somewhere.

      
Event-driven (CDC)Read the database's change log (Debezium, DynamoDB Streams) and delete keys from it.More moving parts; deletes arrive a little after the commit.

      
Tag or group purgeTag entries (product:9) and purge everything with a tag, as CDNs do.Needs a cache or CDN that supports tags.

    
  


  
The cache-aside race

  
Even "write the DB, then delete the key" can leave a stale entry, when a slow reader overlaps a writer:

  

    
StepReaderWriterCache

    
      
1miss, reads v1 from DBempty

      
2(paused)writes v2 to DB, deletes keyempty

      
3sets v1 in cachev1, stale until TTL

    
  

  
The window is small, because a database read is usually faster than a write, but under load it happens. Fixes, in order of effort: keep TTLs short so the damage is bounded; delete again a moment later ("delayed double delete"); or set with a condition, for example store the row version and only overwrite when the new version is higher, or use a lease token that a delete invalidates, as Memcached leases at Facebook do.






  
6. Eviction policies

  
A cache has a fixed amount of memory. When it is full and a new key arrives, something has to go. The policy decides what, and the right one depends on the access pattern. Click keys below, or play a pattern, and compare three policies on the same capacity of 3.

  
  

    
PolicyEvictsGood atBad at

    
      
LRUThe least recently used keyRecency: what was read lately is read againOne big scan flushes the whole cache

      
LFUThe least frequently used keyStable hot sets, scansOld popular keys stay forever without aging

      
FIFOThe oldest inserted keySimplicity, very cheapEvicts hot keys just because they are old

      
RandomAny keyZero bookkeeping; surprisingly close to LRUNo guarantees for hot keys

      
TTL firstKeys closest to expiryData with natural lifetimesKeys without a TTL

      
W-TinyLFU, ARCMix of recency and frequencyReal workloads; used by Caffeine and ZFSMore complex to implement

    
  

  
Redis exposes these as maxmemory-policy: allkeys-lru, allkeys-lfu, volatile-ttl, allkeys-random and others. Its LRU and LFU are approximate: it samples a few keys and evicts the best candidate among them, which costs far less memory than a full linked list.






  
7. Stampedes and hot keys

  
A cache stampede (thundering herd, dog-piling) happens when a popular key expires and every concurrent request misses at once. Each one queries the database for the same row. In Fig 1, choose cache-aside and press "5 reads at once" on an empty cache: five database reads for one value. Switch to request coalescing and try again: one.

  
Request coalescing (single-flight)

  
The first miss for a key starts the load and registers it as in flight. Later misses for the same key wait for that load instead of starting their own. Go's singleflight package, Caffeine's loaders and CDN "collapsed forwarding" all do this. Inside one process it is a map of promises; across many servers it needs a short distributed lock, such as SET key:lock NX PX 2000 in Redis.

  
Probabilistic early expiration

  
Instead of everyone missing at the expiry time, let each reader decide at random to refresh a little early, with a probability that grows as expiry approaches. The XFetch rule refreshes when

  
$$t_{\text{now}} - \delta\,\beta\,\ln(u) \;\ge\; t_{\text{expiry}}, \qquad u \sim \text{Uniform}(0,1)$$

  
where $\delta$ is how long the recompute takes and $\beta \ge 1$ tunes how eager it is. Since $\ln(u) \le 0$, the left side is "now, pushed forward by a random amount". Usually one reader refreshes shortly before expiry and nobody else notices, with no locks at all.

  
Hot keys

  
One key can receive more traffic than one cache node can serve, for example a celebrity's profile. Spread it: keep a small in-process copy in every app server for a second or two, or store replicas under key#1 to key#N and pick one at random on read.

9. Cache layers

  
Real systems stack caches. A request can be answered by the first layer that has a fresh copy, and each layer shields the next.

  

    
LayerExampleLatencyInvalidation

    
      
BrowserCache-Control, ETag0Hard: you cannot reach it, so use versioned URLs

      
CDN edgeCloudFront, Fastly, Cloudflare~10 msPurge API, tags, short TTLs

      
Reverse proxyNginx, Varnish~1 msPurge, TTL

      
In-process (L1)Caffeine, a map with TTL< 1 µsPer server: needs pub/sub to broadcast deletes

      
Distributed (L2)Redis, Memcached, ElastiCache~0.3 msOne place to delete

      
DatabaseBuffer pool, query cache~1–5 msAutomatic

    
  

  
A two-level setup, a small L1 per server with a TTL of a few seconds in front of a shared L2, takes most of the load off the network for hot keys. The price is that each server may be a few seconds behind, so keep the L1 TTL short or broadcast invalidations over Redis pub/sub.

  
HTTP has caching built in. Cache-Control: max-age sets the TTL, ETag with If-None-Match lets a client revalidate and get a tiny 304 Not Modified instead of the full body, and stale-while-revalidate and stale-if-error are the HTTP versions of the patterns above.

The strategies combine. A common production setup is cache-aside or read-through for reads, delete on write, a jittered TTL as a safety net, and coalescing on the miss path.

Simple, survives a cache outage, and the TTL bounds every mistake.

11. In code

  
Cache-aside with delete on write, a jittered TTL and in-process request coalescing, in JavaScript against a Redis-like client:

  
const inflight = new Map();                     // key -> Promise of the value being loaded
const ttl = (base) => base + Math.floor(Math.random() * base * 0.1); // +0..10% jitter

async function getUser(id) {
  const key = `user:${id}`;
  const hit = await cache.get(key);
  if (hit !== null) return JSON.parse(hit);         // hit

  if (!inflight.has(key)) {                         // first miss loads, others wait
    inflight.set(key, (async () => {
      try {
        const row = await db.query('SELECT * FROM users WHERE id = $1', [id]);
        await cache.set(key, JSON.stringify(row), { EX: ttl(300) });
        return row;
      } finally {
        inflight.delete(key);
      }
    })());
  }
  return inflight.get(key);
}

async function updateUser(id, fields) {
  await db.query('UPDATE users SET name = $2 WHERE id = $1', [id, fields.name]);
  await cache.del(`user:${id}`);                    // delete, do not set
}

  
The query uses parameters, never string concatenation. The finally clears the in-flight entry even when the database fails, so the next request retries instead of waiting forever on a rejected promise.
