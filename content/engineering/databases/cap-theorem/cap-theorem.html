CAP theorem

When the network between replicas breaks, a distributed database has to pick: refuse some requests to stay correct, or answer every request and risk returning old data. That choice, Consistency or Availability under a Partition, is the CAP theorem. This page lets you cut the network yourself and watch both answers play out.

1. The three letters, precisely

  
Eric Brewer stated CAP as a conjecture in 2000. Seth Gilbert and Nancy Lynch proved it in 2002, and the proof depends on these exact meanings, which are stricter than everyday usage:

  

    
C · Consistency
linearizable
Every read returns the most recent completed write, as if there were one copy of the data. Not the "C" of ACID, which is about constraints.

    
A · Availability
always answers
Every request to a node that has not crashed gets a non-error response, eventually. A timeout or "try later" counts as unavailable.

    
P · Partition tolerance
survives splits
The system keeps its promises even when the network drops or delays any number of messages between nodes.

  

  
A partition is anything that stops nodes hearing each other: a cut cable, a misconfigured firewall, a switch failure, a long GC pause. To the nodes on each side, a slow peer and a dead peer look the same.






  
2. Why you cannot have all three

  
The proof fits in one picture. Take two replicas, G1 and G2, both holding $x = v_0$, and cut the link between them.

  
  
That is the whole theorem. It is less a deep result than a precise statement of something engineers already felt: during a partition, a node cut off from the latest write must either guess or refuse.






  
3. "Pick two" is misleading

  
CAP is often drawn as a triangle where you pick any two corners. In practice:

  
    
    
  • P is not optional for anything that runs on more than one machine. Networks do partition. A "CA" system is really a single-node system, or one that stops being correct when the network fails.
    • 
    
  • The choice only applies during a partition. When the network is healthy, a well-built system can be both consistent and available. CAP says nothing about normal operation; PACELC (below) does.
    • 
    
  • It is per operation, not per product. Cassandra lets each query choose ONE or QUORUM; DynamoDB lets each read ask for ConsistentRead. One app can be CP for payments and AP for likes.
    • 
    
  • It is a spectrum. Real systems give up a bit of C (bounded staleness, session guarantees) or a bit of A (only the minority side refuses), not all of either.
    • 
  

  
The real question is: when the network splits, does this operation wait, or does it guess?






  
4. CP systems

  
A CP system accepts a write only when a majority of replicas confirm it, usually through a consensus protocol such as Raft or Paxos. With 3 replicas any 2 form a majority, and two majorities always share at least one node, so a later majority read is guaranteed to see the write.

  
In Fig 1, choose CP and partition. The side with A and B still has a majority and keeps working normally. C, alone, can reach neither a write quorum nor a read quorum, so it refuses both. Clients on C's side see errors, but nobody ever reads a stale value. Heal the network and C simply catches up from the majority.

  
    
    
  • Examples: etcd, ZooKeeper, Consul, Google Spanner, CockroachDB, HBase, MongoDB with majority write and read concern.
    • 
    
  • Good for: money, inventory, unique usernames, locks, leader election, configuration. Anything where a wrong answer is worse than no answer.
    • 
    
  • Cost: every write waits for the nearest majority, and a minority partition (often a whole region) goes read-only or dark.
    • 
  






  
5. AP systems

  
An AP system lets any reachable replica accept reads and writes, and copies changes to the others in the background. During a partition both sides keep serving, so the data can diverge. When the partition heals the replicas must reconcile.

  
In Fig 1, choose AP, partition, then write via A and via C. Both writes succeed. A read via C returns C's own value, which is stale from A's point of view. Heal the network: with last-write-wins, the write with the later timestamp survives and the other is silently discarded. That lost-write counter is the price of availability.

  
How AP systems converge

  

    
TechniqueWhat it does

    
      
Last-write-wins (LWW)Keep the value with the highest timestamp. Simple, but drops concurrent writes and trusts clocks.

      
Version vectorsDetect that two writes were concurrent and keep both as siblings for the app to merge (Riak, Amazon's original Dynamo).

      
CRDTsData types whose merges always commute: counters, sets, maps. Replicas converge without conflicts (Riak, Redis Enterprise active-active, Automerge).

      
Read repairWhen a read sees replicas disagree, write the newest value back to the stale ones.

      
Hinted handoffA node holds writes meant for an unreachable peer and delivers them when it returns.

      
Anti-entropyBackground comparison of replicas using Merkle trees, so only differing ranges are copied.

    
  

  
    
    
  • Examples: Apache Cassandra, ScyllaDB, Riak, CouchDB, DynamoDB with default (eventually consistent) reads, DNS.
    • 
    
  • Good for: shopping carts, likes and view counts, feeds, presence, sensor data. Anything where a slightly old answer beats an error.
    • 
  






  
6. Quorums: R + W > N

  
Dynamo-style systems make the trade tunable. With $N$ replicas, a write waits for $W$ acknowledgements and a read asks $R$ replicas and keeps the newest answer. If the two sets must overlap, every read meets at least one replica that has the latest acknowledged write:

  
$$R + W > N \quad\Longrightarrow\quad \text{every read quorum intersects every write quorum}$$

  
Writes keep working with up to $N - W$ replicas down, reads with up to $N - R$ down. Raising $W$ and $R$ buys consistency with availability and latency.


  

  

    
N = 3Behaviour

    
      
W = 2, R = 2The usual "quorum" setting. Overlaps, tolerates one node down for both reads and writes.

      
W = 3, R = 1Fast reads, but one node down blocks every write.

      
W = 1, R = 3Fast writes, but one node down blocks every read.

      
W = 1, R = 1Fastest and most available. No overlap, so reads can be stale: eventual consistency.

    
  

  
Overlap is necessary but not quite sufficient for linearizability. Sloppy quorums (writing to stand-in nodes during failures), concurrent writes resolved by clock timestamps, and reads that race an in-flight write can still return old data. Systems that promise strict linearizability use consensus on top.






  
7. PACELC: the trade without a partition

  
Partitions are rare; latency is constant. Daniel Abadi's PACELC extends CAP: if there is a Partition, choose A or C; Else, choose Latency or Consistency.

  
Fig 1 shows the "else" half. In CP mode with a healthy network, a write via A waits 2 ms for B, but a write via C waits 70 ms for the nearest other replica. In AP mode every write returns after about 1 ms locally and replicates afterwards. Consistency costs a round trip to a majority on every request, partition or not.

  

    
SystemPACELCMeaning

    
      
Cassandra, ScyllaDB, RiakPA / ELAvailable under partition, low latency otherwise (at default consistency levels).

      
DynamoDB (default reads)PA / ELEventually consistent reads; strongly consistent reads on request.

      
MongoDB (typical)PA / ECAbadi's classification: consistent normally, but a partitioned primary may accept writes that are later rolled back.

      
Spanner, CockroachDBPC / ECConsensus on every write, always.

      
etcd, ZooKeeperPC / ECSmall, strongly consistent coordination stores.

    
  






  
8. Consistency models

  
"Consistent" and "eventually consistent" are the ends of a ladder. Each rung down is cheaper and more available, and promises less.

  

    
ModelGuarantee

    
      
LinearizableBehaves like one copy; once a write completes, every later read sees it. CAP's C.

      
SequentialAll clients see operations in the same order, but not necessarily in real-time order.

      
CausalIf one write could have caused another (reply after comment), everyone sees them in that order. Available under partition.

      
Read-your-writesA client always sees its own writes. Often done by pinning a session to one replica.

      
Monotonic readsA client never sees time go backwards: no older value after a newer one.

      
EventualIf writes stop, all replicas eventually agree. No promise about when or in between.

    
  

  
Causal consistency is the strongest model that can stay available during a partition, which is why many geo-replicated systems aim for it plus session guarantees.






  
9. Designing with CAP

  
Decide per operation, by asking what a wrong answer costs versus what an error costs:

  

    
OperationChooseWhy

    
      
Debit an accountCPTwo sides spending the same balance is worse than a retry.

      
Reserve the last seatCPOverselling costs real money and trust.

      
Register a unique usernameCPUniqueness needs one authority.

      
Add to cartAPMerge carts after the partition; never lose a sale to an error page.

      
Like, view countAPA CRDT counter converges; being off by a few for a minute is fine.

      
Show a feed or profileAPSlightly stale content beats no content.

    
  

  
Common patterns mix both: accept an order optimistically (AP) and confirm it asynchronously against a CP inventory service, compensating if it fails. That is the saga pattern.

  
A quorum read in code

  
// Ask all N replicas, wait for R answers, return the newest.
async function quorumRead(replicas, key, R) {
  const answers = [];
  await new Promise((done, fail) => {
    let failed = 0;
    replicas.forEach(r => r.get(key)
      .then(a => { answers.push(a); if (answers.length === R) done(); })
      .catch(() => { if (++failed > replicas.length - R) fail(new Error('no quorum')); }));
  });
  const newest = answers.reduce((a, b) => (b.version > a.version ? b : a));
  // read repair: push the newest value to replicas that answered with an older one
  answers.filter(a => a.version < newest.version).forEach(a => a.replica.put(key, newest));
  return newest.value;
}

  
The fail branch is CAP in one line: with too many replicas unreachable, the read refuses instead of guessing.






  
10. Misconceptions

  
    
    
  • "NoSQL is AP, SQL is CP." It depends on configuration. A single PostgreSQL with async replicas and failover can lose acknowledged writes; Cassandra at QUORUM behaves much more like CP.
    • 
    
  • "We chose CA." Only possible on one machine. With replicas, a partition will happen, and the system will do something: find out what.
    • 
    
  • "AP means no consistency." It means no linearizability during a partition. Causal and session guarantees are still possible.
    • 
    
  • "CAP availability means high uptime." CAP's A is a strict per-request property. A CP system with a healthy majority can still have 99.99% uptime.
    • 
    
  • "Partitions are rare, so CAP does not matter." The latency side (PACELC) matters on every request, and partitions include GC pauses and overloaded links, not just cut cables.
    •
