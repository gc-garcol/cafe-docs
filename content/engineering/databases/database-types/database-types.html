Database types and use cases

Every database is a bet on what you will ask it. A relational store bets on joins and transactions, a key-value store on lookups by one key, a column store on scanning millions of rows for one number. This page maps the ten main families plus append-only stores, names real products in each, shows the data model each one is built around, and matches them to real workloads.

1. Why there are so many kinds

Any database answers the same few design questions, and each answer closes a door somewhere else:

  • Data model. Tables, documents, key-value pairs, graphs, time-stamped points, text, vectors. The model decides which questions are natural to ask.
  • Layout on disk. Rows stored together make "fetch this order" cheap. Columns stored together make "sum every amount" cheap. You cannot have both in one layout.
  • Index structure. B-trees for ranges, hash tables for exact keys, LSM-trees for heavy writes, inverted indexes for words, HNSW graphs for nearest vectors.
  • Consistency and distribution. One node with full transactions, or many nodes that trade some consistency for availability and scale. The CAP theorem page covers that trade.
SQL
schema first

Model the data, normalize it, and let the query planner work out how to answer any question with joins.

NoSQL
query first

Start from the access patterns, then shape the data so each one is a single, cheap lookup. Flexible schema, easy horizontal scale.

Specialized
one job

Search, time-series, graph, vector and analytics engines do one kind of query far better than a general store.

The labels blur in practice. PostgreSQL stores JSON documents, full-text indexes and vectors. MongoDB and DynamoDB support multi-item transactions. The family tells you what a system is built around, which is what decides how it behaves at the edges.

3. The families in detail

Relational (SQL)

Self-hosted / open source: PostgreSQL · MySQL · MariaDB · SQLite · Microsoft SQL Server · Oracle Database · IBM Db2

Managed / cloud: Amazon RDS · Amazon Aurora · Google Cloud SQL · AlloyDB · Azure SQL Database · Neon · Supabase

Data lives in tables with a fixed schema, rows reference each other with foreign keys, and SQL describes what you want while the planner decides how. ACID transactions keep several changes all-or-nothing.

Good at
Integrity constraints, joins, ad-hoc queries, transactions across many rows and tables.
Weak at
Writes beyond one primary node without sharding work, very large analytical scans, frequently changing schemas.
Use for
Orders, payments, inventory, user accounts, SaaS back ends. The safe default for most new systems.

Key-value

Self-hosted / open source: Redis · Valkey · Memcached · etcd · Aerospike · FoundationDB · RocksDB · LMDB

Managed / cloud: Amazon DynamoDB · Amazon ElastiCache · MemoryDB · Azure Cache for Redis · Google Memorystore · Upstash

A giant hash map: get(key), put(key, value), delete(key). The store does not look inside the value, so it can spread keys over many nodes and answer in well under a millisecond when the data is in memory.

Good at
Very fast lookups by exact key, huge request rates, simple horizontal scaling, TTLs.
Weak at
Any query that is not "by key": filters, ranges over values, joins, reporting.
Use for
Caches, sessions, shopping carts, feature flags, rate-limit counters, leaderboards (Redis sorted sets), cluster config and leader election (etcd).

Document

Self-hosted / open source: MongoDB · Couchbase · Apache CouchDB · RavenDB · FerretDB · PostgreSQL jsonb

Managed / cloud: MongoDB Atlas · Google Firestore · Amazon DocumentDB · Azure Cosmos DB · DynamoDB (items)

Each record is a self-contained JSON-like document that can nest arrays and objects. Data that is read together is stored together, so loading a product page is one read instead of five joins. Fields can differ from document to document.

Good at
Aggregates that are read as a whole, evolving schemas, secondary indexes on nested fields, sharding by document id.
Weak at
Many-to-many relationships, data duplicated across documents that must stay in sync, cross-document reporting.
Use for
Product catalogs, content management, user profiles, mobile app back ends, event payloads.

Wide-column

Self-hosted / open source: Apache Cassandra · ScyllaDB · Apache HBase · Apache Accumulo

Managed / cloud: Google Bigtable · Amazon Keyspaces · DataStax Astra DB · ScyllaDB Cloud · Azure Cosmos DB for Apache Cassandra

Rows are grouped by a partition key that decides which nodes own them, and sorted inside the partition by clustering columns. You design one table per query, so every read hits one partition. Built on LSM-trees, they absorb enormous write rates across many machines and data centers.

Good at
Massive write throughput, linear scale-out, multi-region replication, time-ordered data per entity.
Weak at
Ad-hoc queries, joins, aggregations, strong consistency across partitions. Changing access patterns means new tables.
Use for
Chat message history, activity feeds, IoT ingestion, tracking events, per-user timelines at billions of rows.

Graph

Self-hosted / open source: Neo4j · Memgraph · JanusGraph · NebulaGraph · Dgraph · ArangoDB (multi-model)

Managed / cloud: Amazon Neptune · Neo4j AuraDB · TigerGraph Cloud · Azure Cosmos DB for Apache Gremlin

Nodes and edges are first-class, and both carry properties. A query walks the graph hop by hop (in Cypher, Gremlin or the ISO GQL standard) and each hop costs about the same however large the graph is, where SQL would need one self-join per hop.

Good at
Multi-hop traversals, shortest paths, pattern matching, recommendations from connections.
Weak at
Bulk aggregation over all nodes, very high write volume, sharding a dense graph across machines.
Use for
Fraud rings, social networks, knowledge graphs, access-control graphs, network and dependency maps.

Time-series

Self-hosted / open source: TimescaleDB · InfluxDB · Prometheus · VictoriaMetrics · QuestDB · TDengine · Apache IoTDB · kdb+

Managed / cloud: Amazon Timestream · InfluxDB Cloud · Timescale Cloud · Grafana Cloud (Mimir) · Azure Data Explorer

Optimized for data that arrives in time order and is mostly appended, never updated. Points are stored in time-partitioned chunks, compressed with delta encoding, and queried by window: "average per minute over the last 6 hours". Retention policies drop or downsample old data automatically.

Good at
High-rate ingestion, time-window aggregates, compression of 10x or more, retention and downsampling.
Weak at
Random updates, relational data, very high cardinality labels in some engines.
Use for
Metrics and monitoring, IoT sensors, market tick data, application telemetry.

Search engine

Self-hosted / open source: Elasticsearch · OpenSearch · Apache Solr · Meilisearch · Typesense · Vespa · Apache Lucene (library)

Managed / cloud: Elastic Cloud · Amazon OpenSearch Service · Algolia · Azure AI Search

Text is split into terms, and an inverted index maps every term to the documents that contain it. Queries rank matches by relevance (BM25), and support fuzzy matching, stemming, facets and highlighting. Indexing is near real time: a new document becomes searchable after a short refresh, about a second by default in Elasticsearch.

Good at
Full-text search, relevance ranking, faceted filters, log search and exploration.
Weak at
Acting as the source of truth, transactions, frequent updates to the same document.
Use for
Site and product search, autocomplete, log analytics (the ELK stack), document discovery.

Vector

Self-hosted / open source: pgvector · Milvus · Qdrant · Weaviate · Chroma · LanceDB · FAISS (library)

Managed / cloud: Pinecone · Zilliz Cloud · Qdrant Cloud · Weaviate Cloud · vector search in OpenSearch, MongoDB Atlas and Redis

Stores embeddings, arrays of hundreds of numbers produced by a model, and finds the nearest ones to a query vector. Exact search compares against every vector, so engines use approximate indexes such as HNSW or IVF that trade a little recall for orders of magnitude in speed.

Good at
Semantic similarity: "find things like this" for text, images or users, combined with metadata filters.
Weak at
Exact matches, keyword relevance on its own (hybrid search adds BM25), transactions.
Use for
Retrieval for LLM chatbots (RAG), semantic search, recommendations, duplicate and anomaly detection.

Columnar / analytical (OLAP)

Self-hosted / open source: ClickHouse · DuckDB · Apache Druid · Apache Pinot · StarRocks · Apache Doris

Managed / cloud: Snowflake · Google BigQuery · Amazon Redshift · Databricks SQL · ClickHouse Cloud · MotherDuck · Azure Synapse

Each column is stored on its own, compressed, and processed in vectorized batches. A query that touches 3 of 80 columns reads only those 3, which makes scanning billions of rows in seconds routine. Data usually arrives in bulk loads or streams from the operational databases.

Good at
Aggregations, group-bys and joins over huge tables, dashboards, ad-hoc analysis.
Weak at
Single-row lookups and updates, high-rate small transactions.
Use for
Data warehouses, BI dashboards, product analytics, reporting, feature generation for ML.

Distributed SQL (NewSQL)

Self-hosted / open source: CockroachDB · TiDB · YugabyteDB · Citus (distributed PostgreSQL) · Vitess (sharded MySQL)

Managed / cloud: Google Spanner · Amazon Aurora DSQL · CockroachDB Cloud · TiDB Cloud · PlanetScale

SQL and ACID transactions on top of automatic sharding. Tables are split into ranges, each range is replicated with a consensus protocol (Paxos or Raft), and transactions span ranges. You get relational semantics that survive a node or a whole region failing.

Good at
Strongly consistent transactions at a scale one node cannot hold, multi-region deployments, no manual sharding.
Weak at
Latency: a write waits for a majority of replicas, often across regions. More cost and operational weight than one PostgreSQL.
Use for
Global ledgers and payments, multi-region SaaS, inventory that must never oversell.

Append-only (event store, ledger, log)

Self-hosted / open source: KurrentDB (formerly EventStoreDB) · Axon Server · immudb · TigerBeetle · Datomic · XTDB · Apache Kafka · Redpanda

Managed / cloud: Kurrent Cloud · Confluent Cloud · Amazon MSK · Amazon Kinesis · SQL Server and Azure SQL ledger tables

Nothing is updated or deleted in place. Every change is a new record appended to the end, so the full history is kept and the current state is derived from it. Section 4 covers the kinds and how they work.

Good at
Audit trails, "what did it look like on date X", tamper evidence, very fast sequential writes, replaying history into new views.
Weak at
Ad-hoc queries on current state (you build read models for that), unbounded growth, real deletion for privacy rules.
Use for
Financial ledgers, event sourcing, compliance and audit logs, order and payment histories, integration events between services.

Two neighbours worth knowing: object storage (Amazon S3, GCS) is the cheap, durable bottom layer for files, backups and data lakes queried by engines like Trino or Athena, and embedded databases (SQLite, DuckDB, RocksDB) run inside your process with no server at all.

4. Append-only databases

"Append-only" is a design property more than a data model. The log of changes is the source of truth, and records are never overwritten. To change a value you append a new fact; to remove one you append a tombstone or a reversing entry. It shows up at three levels: whole databases built around it, storage engines that use it underneath, and workloads that are naturally append-only.

The state after $n$ events is the previous state with one more event applied. Starting from an empty state $S_0$ and an apply function $f$:

$$S_n = f(S_{n-1}, e_n) = f(\cdots f(f(S_0, e_1), e_2) \cdots, e_n)$$

A snapshot stores some $S_k$, so a reader replays only $e_{k+1}, \ldots, e_n$. Replaying the same log with a different $f$ builds a new view, such as a monthly report, without touching the source data.

Trade-offs

You get
history

A complete audit trail, debugging by replay, time travel, and new read models built from old events.

You get
fast writes

Appends are sequential and need no locks on existing records. Replication is just shipping the tail of the log.

You pay
growth

Storage grows forever without snapshots, compaction or retention, and current-state queries need a separate read model.

Deleting personal data is the hard case, because rules such as GDPR require real erasure. The common answer is crypto-shredding: encrypt each person's data with its own key and delete the key, which leaves the log intact but the data unreadable.

5. OLTP vs OLAP: rows vs columns

Operational (OLTP) work touches a few whole rows at a time: insert this order, load that user. Analytical (OLAP) work touches a few columns of very many rows: total revenue per month. The physical layout decides which one is cheap.

Column stores also compress far better, because a column holds values of one type that often repeat. With $c$ columns of similar width and a query that needs $k$ of them, a column store reads roughly a fraction $k / c$ of the bytes a row store would, before compression widens the gap further.

OLTPOLAP
Typical queryRead or write a few rows by keyAggregate millions of rows
LayoutRow-oriented, B-tree indexesColumn-oriented, compressed, sorted
Latency targetMillisecondsSeconds is fine
ConcurrencyThousands of small transactionsFew large scans
ExamplesPostgreSQL, MySQL, DynamoDBClickHouse, Snowflake, BigQuery

Running dashboards against the production OLTP database works until it doesn't: one heavy report can starve user traffic. The usual fix is to copy data to a warehouse with change data capture or nightly batch jobs. HTAP systems such as TiDB (with TiFlash) or SingleStore keep both layouts in one product.

6. Storage engines: B-tree vs LSM-tree

Under the data model sits an index structure, and two designs dominate.

B-tree

A wide, balanced tree of fixed-size pages, updated in place. With a branching factor $b$ the depth for $n$ keys is about $\log_b n$, so with $b = 500$ a billion rows need only about four page reads, and the top levels are always cached. Reads and range scans are fast and predictable. Writes cost a random page update plus a write-ahead log entry. Used by PostgreSQL, MySQL InnoDB, SQL Server, Oracle and SQLite.

$$\text{depth} \approx \left\lceil \log_{500} 10^9 \right\rceil = \lceil 3.33 \rceil = 4$$

LSM-tree

Writes go to an in-memory table and a log, and are flushed as sorted, immutable files (SSTables). Background compaction merges files and drops old versions. Every write is sequential, so ingest is very fast. A read may have to check several files, which engines speed up with a Bloom filter per file. Used by Cassandra, ScyllaDB, RocksDB, LevelDB, HBase and many time-series engines.

B-treeLSM-tree
WritesRandom, in placeSequential, batched: higher throughput
ReadsOne path, predictableSeveral files, helped by Bloom filters
SpaceSome page fragmentationCompacts well, but old versions linger until compaction
Hidden costPage splits, vacuumCompaction spikes in I/O and CPU

8. Polyglot persistence

Real systems combine several stores, each doing the job it is built for. One database stays the source of truth; the others are derived from it and can be rebuilt.

The danger is keeping copies in sync. Writing to PostgreSQL and then to OpenSearch from the app is a dual write: if the second call fails, the stores disagree forever. Instead, read the database's own change log (change data capture with Debezium, or an outbox table) and publish it through Kafka, as the Kafka use cases page shows. Every derived store then converges on the source of truth, a little later.

Add a second database when a real query demands it, not because the architecture diagram looks thin.

9. How to choose

  1. List the top queries and writes, with rates and latency targets. "Get order by id, 2k/s, p99 < 20 ms" is a requirement; "we might need graphs" is not.
  2. Decide what must be transactional. Money, stock and uniqueness usually do. Likes, views and feeds usually don't.
  3. Estimate size and growth. One modern server with PostgreSQL handles terabytes and tens of thousands of transactions per second. Many systems never outgrow it.
  4. Check the failure story. What happens on a node or region loss: refuse writes, or accept them and reconcile later? That is the CAP choice.
  5. Count the operational cost. Backups, upgrades, monitoring, expertise on the team, managed offerings in your cloud.
  6. Prototype the hardest query on real-sized data before committing.

10. Common mistakes

  • Choosing NoSQL "for scale" with a dataset that fits in RAM on one machine, then rebuilding joins in application code.
  • Modeling Cassandra or DynamoDB like SQL tables. Without designing per access pattern you get full scans or hot partitions.
  • Using the search engine as the primary store. Index rebuilds and refresh delays make it a poor source of truth.
  • Running analytics on the OLTP primary. Use a replica or a warehouse.
  • Dual writes to two stores without an outbox or CDC, so they drift apart on the first failure.
  • Picking a low-cardinality partition key (country, status), which sends most traffic to a few nodes.
  • Querying an event store directly for current state. Project the events into a read model built for the query.
  • Ignoring the extensions you already have: jsonb, full-text search, PostGIS and pgvector cover many "we need a new database" moments.
