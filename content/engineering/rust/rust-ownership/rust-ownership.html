Rust Ownership

Rust frees memory without a garbage collector and without manual free. It does this with ownership: every value has exactly one owner, and the value is dropped when the owner goes out of scope. The compiler checks the rules, so the cost is paid at compile time, not at run time.

1. Stack and heap

The stack holds values whose size is known at compile time: integers, fixed arrays, pointers. Pushing and popping is just moving a pointer, and the frame of a function vanishes when it returns. The heap holds data whose size is decided at run time, such as the text of a String. Allocating means asking the allocator for space, and someone must later give it back.

Managing that "someone" is the hard problem. Forget to free and you leak. Free twice and you corrupt the allocator. Free too early and another pointer reads garbage. Garbage collectors solve this at run time; C leaves it to you. Ownership is Rust's third answer.

2. The ownership rules

  • Each value in Rust has an owner.
  • There can only be one owner at a time.
  • When the owner goes out of scope, the value is dropped.
fn main() {
    {                                   // s is not valid here yet
        let s = String::from("hello");  // s is valid from here
        println!("{s}");
    }                                   // scope over: drop(s) runs, memory freed
}

At the closing brace Rust calls drop automatically. This is the RAII pattern from C++: tie a resource to a scope. It works for files, locks and sockets too, not only memory.

3. Move, Copy and Clone

A String is three words on the stack (pointer, length, capacity) plus a heap buffer. let s2 = s1; copies the three words. If both stayed valid, both would free the same buffer at the end of the scope. So Rust treats the assignment as a move: s1 is no longer usable.

does not compile
fn main() {
    let s1 = String::from("hello");
    let s2 = s1;
    println!("{s1}"); // error[E0382]: borrow of moved value: `s1`
}

A move is always a cheap shallow copy. Rust never deep-copies implicitly, so any copy you do not see in the code is cheap. When you do want a deep copy, call clone, which makes the cost visible.

Types that live entirely on the stack and have no destructor can implement the Copy trait. For them, assignment copies and the original stays valid.

Ownership and functions

Passing a value to a function moves or copies it, exactly like assignment. Returning a value moves it out to the caller.

fn main() {
    let s = String::from("hello");
    takes_ownership(s);           // s moves into the function
    // println!("{s}");           // would not compile

    let n = 5;
    makes_copy(n);                // i32 is Copy, n is still fine
    println!("{n}");

    let s2 = gives_back(String::from("yo")); // moved in, moved out
    println!("{s2}");
}

fn takes_ownership(text: String) { println!("{text}"); } // text dropped here
fn makes_copy(x: i32) { println!("{x}"); }
fn gives_back(text: String) -> String { text }

Moving values in and back out of every function would be tedious. That is what references are for.

4. References and borrowing

&s creates a reference: a pointer to the value that does not own it. Creating one is called borrowing. When the reference goes away, nothing is dropped, because it never owned anything.

fn main() {
    let s = String::from("hello");
    let len = calculate_length(&s);
    println!("'{s}' has {len} bytes"); // s is still ours
}

fn calculate_length(s: &String) -> usize {
    s.len()
}

A shared reference is read-only. To change a borrowed value, both the variable and the reference must be mutable:

fn main() {
    let mut s = String::from("hello");
    change(&mut s);
    println!("{s}"); // hello, world
}

fn change(s: &mut String) {
    s.push_str(", world");
}

5. The borrowing rules

At any time you can have either one mutable reference or any number of shared references. And references must always be valid.

This is "aliasing XOR mutation". It rules out data races at compile time: a data race needs two pointers to the same data, at least one writing, with no synchronization. It also rules out iterator invalidation, where a loop reads a vector while another pointer makes it reallocate.

does not compile
fn main() {
    let mut s = String::from("hello");
    let r1 = &mut s;
    let r2 = &mut s; // error[E0499]: cannot borrow `s` as mutable more than once
    println!("{r1}, {r2}");
}

A borrow lasts from where it is created to its last use, not to the end of the block. This is called non-lexical lifetimes (NLL), and it is why the following is fine:

fn main() {
    let mut s = String::from("hello");
    let r1 = &s;
    let r2 = &s;
    println!("{r1} and {r2}"); // last use of r1 and r2

    let r3 = &mut s;           // OK: no shared borrow is alive any more
    r3.push('!');
    println!("{r3}");
}

Use a new scope { } when you need two mutable borrows one after the other in a way NLL cannot see.

6. Dangling references

In languages with raw pointers, a function can return a pointer to its own local variable, which is freed on return. Rust refuses:

does not compile
fn dangle() -> &String { // error[E0106]: missing lifetime specifier
    let s = String::from("hello");
    &s                   // s is dropped at the end of this function
}

The fix is to return the owned value, String, and move it out. Chapter 10 explains lifetimes, the tool the compiler uses to prove a reference never outlives its data.

7. The slice type

A slice borrows a contiguous part of a collection. It is a "fat pointer": a pointer plus a length. &s[0..5] is a &str pointing at the first five bytes of s.

fn first_word(s: &str) -> &str {
    for (i, &b) in s.as_bytes().iter().enumerate() {
        if b == b' ' {
            return &s[..i];
        }
    }
    &s[..]
}

fn main() {
    let owned = String::from("hello world");
    let word = first_word(&owned);   // &String coerces to &str
    let lit = first_word("ok then"); // string literals are &str already
    println!("{word} {lit}");

    let a = [1, 2, 3, 4, 5];
    let mid: &[i32] = &a[1..3];      // [2, 3]
    println!("{mid:?}");
}

Returning a slice instead of an index ties the result to the data. If the caller tries to clear() the string while word is still in use, the borrow checker rejects it, because clear needs a &mut while a & is alive. An index would silently become stale.

does not compile
fn first_word(s: &str) -> &str { s.split(' ').next().unwrap() }

fn main() {
    let mut s = String::from("hello world");
    let word = first_word(&s);
    s.clear(); // error[E0502]: cannot borrow `s` as mutable because it is also borrowed as immutable
    println!("{word}");
}

Range syntax: [..2] from the start, [3..] to the end, [..] the whole thing. String slice indexes are byte offsets and must fall on UTF-8 character boundaries, otherwise the program panics. Prefer parameters of type &str and &[T] over &String and &Vec<T>: they accept more callers at no cost.

9. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
fn main() {
    let a = String::from("x");
    let b = a;
    println!("{a}");
}

String is not Copy, so let b = a moves it and a can no longer be used.

Q2 Does this compile?
fn main() {
    let a = (1, 2.0);
    let b = a;
    println!("{a:?} {b:?}");
}

A tuple of Copy types is Copy, so a stays valid.

Q3 Does this compile?
fn main() {
    let mut v = vec![1, 2, 3];
    let first = &v[0];
    v.push(4);
    println!("{first}");
}

push needs &mut v while first is still used afterwards. Pushing may reallocate, which would leave first dangling.

Q4 Does this compile?
fn main() {
    let mut s = String::from("a");
    let r = &s;
    println!("{r}");
    s.push('b');
    println!("{s}");
}

The shared borrow r ends at its last use, before push. Non-lexical lifetimes allow this.

Q5 Does this compile?
fn longest() -> &str {
    let s = String::from("hi");
    &s
}
fn main() {}

The reference would outlive s, which is dropped when the function returns. Return a String instead.
