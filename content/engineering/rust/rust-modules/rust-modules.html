Rust Packages, Crates and Modules

As a program grows, you need to group code, hide details and name things without collisions. Rust has four layers for this: packages that Cargo builds, crates that the compiler compiles, modules that organize and hide code, and paths that name items.

1. Packages and crates

TermWhat it is
CrateThe unit the compiler works on. A binary crate has a main and becomes an executable. A library crate has no main and is used by other crates.
Crate rootThe source file the compiler starts from: src/main.rs or src/lib.rs.
PackageOne or more crates plus a Cargo.toml. At most one library crate, any number of binary crates.
WorkspaceSeveral packages that share one Cargo.lock and target directory (chapter 14).
my-app/
├── Cargo.toml
└── src/
    ├── main.rs          # binary crate "my-app"
    ├── lib.rs           # library crate "my_app"
    └── bin/
        └── tool.rs      # extra binary crate "tool"

Cargo follows conventions instead of configuration: if src/main.rs exists there is a binary crate with the package's name, and if src/lib.rs exists there is a library crate. A common layout keeps almost all logic in lib.rs and a thin main.rs, so the logic can be tested and reused.

2. The module tree

mod declares a module. Modules nest and form a tree whose root is the implicit module crate.

mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() { println!("added"); }
        fn seat_at_table() {}
    }
    mod serving {
        fn take_order() {}
    }
}

fn main() {
    front_of_house::hosting::add_to_waitlist();
}
crate
└── front_of_house
    ├── hosting
    │   ├── add_to_waitlist   (pub)
    │   └── seat_at_table
    └── serving
        └── take_order

3. Paths and privacy

A path names an item. An absolute path starts with crate (or an external crate's name). A relative path starts at the current module, or with self or super (the parent).

Everything is private by default. The rules are short:

  • An item is visible inside the module where it is defined and in all of its descendants.
  • A parent cannot see private items of its children. Adding pub opens an item to the parent (and further, if every module on the path is reachable).
  • Siblings can see each other, because both live in the same parent.
mod kitchen {
    pub fn fix_order() {
        cook();
        super::deliver();          // relative path to the parent
    }
    fn cook() { println!("cooking"); }
}

fn deliver() { println!("delivered"); }

fn main() {
    crate::kitchen::fix_order();   // absolute
    kitchen::fix_order();          // relative
}
does not compile
mod kitchen {
    fn cook() {}
}
fn main() {
    kitchen::cook(); // error[E0603]: function `cook` is private
}

Finer grains exist: pub(crate) is visible in the whole crate but not to users of the library, and pub(super) is visible to the parent module only.

4. Public structs and enums

The two behave differently. Making a struct pub does not make its fields public; each field opts in. If a field is private, code outside cannot build the struct with a literal, so you provide a constructor. Making an enum pub makes all of its variants public, since an enum with hidden variants would be of little use.

mod back_of_house {
    pub struct Breakfast {
        pub toast: String,
        seasonal_fruit: String,   // private
    }
    impl Breakfast {
        pub fn summer(toast: &str) -> Breakfast {
            Breakfast { toast: String::from(toast), seasonal_fruit: String::from("peaches") }
        }
    }
    pub enum Appetizer { Soup, Salad } // both variants are public
}

fn main() {
    let mut meal = back_of_house::Breakfast::summer("rye");
    meal.toast = String::from("wheat");    // pub field: OK
    // meal.seasonal_fruit = "x".into();   // private field: error
    let _a = back_of_house::Appetizer::Soup;
    println!("{} toast", meal.toast);
}

Private fields are how a type keeps an invariant: if nobody outside can touch len, nobody outside can make it wrong.

5. Bringing paths into scope with use

use creates a shortcut, like a symbolic link, valid in the scope where it appears. A use at the top of a module does not reach into a child module; the child needs its own use or super::.

use std::collections::HashMap;          // types: import the item
use std::fmt::Result;
use std::io::Result as IoResult;        // rename to avoid a clash
use std::io::{self, Write};             // nested: std::io and std::io::Write
use std::collections::*;                // glob: rarely a good idea outside tests

mod shapes {
    pub fn area(w: u32, h: u32) -> u32 { w * h }
}
use shapes::area as rect_area;

fn main() {
    let mut m = HashMap::new();
    m.insert("a", rect_area(2, 3));
    let _: Option<Result> = None;
    let _: Option<IoResult<()>> = None;
    let _ = BTreeMap::<u8, u8>::new();
    io::stdout().flush().unwrap();
    println!("{m:?}");
}

Idioms

  • For functions, import the parent module and call hosting::add_to_waitlist(). The prefix shows the function is not local.
  • For structs, enums and traits, import the item itself: use std::collections::HashMap;.
  • When two items share a name, import their parents (fmt::Result, io::Result) or rename one with as.

Re-exporting with pub use

pub use imports a name and makes it public at the new location. The internal tree can stay organized for maintainers while the public API stays flat for users.

mod front_of_house {
    pub mod hosting {
        pub fn add_to_waitlist() {}
    }
}
pub use crate::front_of_house::hosting; // users can write my_crate::hosting

fn main() { hosting::add_to_waitlist(); }

6. External packages

Add a dependency to Cargo.toml; Cargo downloads it from crates.io and its crate name becomes available as the first segment of a path. The standard library, std, is always available without listing it, though you still use items from it.

# Cargo.toml
[dependencies]
rand = "0.8.5"

$ cargo add serde --features derive   # edits Cargo.toml for you
use rand::Rng;

fn main() {
    let secret = rand::thread_rng().gen_range(1..=100);
    println!("{secret}");
}

7. Separating modules into files

mod name; with a semicolon instead of a block tells the compiler to load the body from a file. You declare each module once, in its parent; other files refer to it by path, not with another mod. (mod is not an include.)

src/
├── lib.rs               mod front_of_house;
├── front_of_house.rs    pub mod hosting;
└── front_of_house/
    └── hosting.rs       pub fn add_to_waitlist() {}
Declared inModuleFile the compiler looks for
src/lib.rsmod front_of_house;src/front_of_house.rs (or the older src/front_of_house/mod.rs)
src/front_of_house.rspub mod hosting;src/front_of_house/hosting.rs

Prefer the front_of_house.rs style. With many mod.rs files open in an editor, every tab has the same name. Do not mix both styles for the same module.

8. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
mod a {
    fn helper() -> u8 { 1 }
    pub mod b {
        pub fn call() -> u8 { super::helper() }
    }
}
fn main() { println!("{}", a::b::call()); }

A child module can see private items of its ancestors. b is inside a, so it may call a::helper.

Q2 Does this compile?
mod shop {
    pub struct Item { pub name: String, price: u32 }
}
fn main() {
    let i = shop::Item { name: "pen".into(), price: 2 };
}

price is private, so code outside shop cannot use a struct literal. Add a public constructor.

Q3 Does this compile?
mod m {
    pub enum Level { Low, High }
}
fn main() {
    let _l = m::Level::High;
}

Variants of a public enum are public automatically.

Q4 Does this compile?
use std::collections::HashMap;
mod inner {
    pub fn make() -> HashMap<u8, u8> { HashMap::new() }
}
fn main() {}

use applies only to the scope it is in. The child module inner needs its own use or a path like super::HashMap.
