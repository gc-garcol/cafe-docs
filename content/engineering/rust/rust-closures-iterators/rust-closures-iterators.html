Rust Closures and Iterators

A closure is an anonymous function that can capture values from where it is defined. An iterator produces a sequence of values one at a time, and adapters chain into pipelines. Together they let Rust code read like a description of the result, and the compiler still turns it into a tight loop.

Step through it

Building v.iter().map(..).filter(..) does no work. sum calls next repeatedly, and each call pulls one element through the whole chain.

1. Closures

#[derive(Debug, PartialEq, Copy, Clone)]
enum ShirtColor { Red, Blue }

struct Inventory { shirts: Vec<ShirtColor> }

impl Inventory {
    fn giveaway(&self, preference: Option<ShirtColor>) -> ShirtColor {
        preference.unwrap_or_else(|| self.most_stocked()) // closure captures self
    }
    fn most_stocked(&self) -> ShirtColor {
        let reds = self.shirts.iter().filter(|c| **c == ShirtColor::Red).count();
        if reds * 2 > self.shirts.len() { ShirtColor::Red } else { ShirtColor::Blue }
    }
}

fn main() {
    let store = Inventory { shirts: vec![ShirtColor::Blue, ShirtColor::Red, ShirtColor::Blue] };
    println!("{:?}", store.giveaway(Some(ShirtColor::Red)));
    println!("{:?}", store.giveaway(None));
}

Closures usually need no type annotations: they are short, local, and not part of an API, so the compiler infers parameter and return types from use. All of these are equivalent:

fn main() {
    fn  add_one_v1   (x: u32) -> u32 { x + 1 }
    let add_one_v2 = |x: u32| -> u32 { x + 1 };
    let add_one_v3 = |x|             { x + 1 };
    let add_one_v4 = |x|               x + 1  ;
    println!("{} {} {} {}", add_one_v1(1), add_one_v2(1), add_one_v3(1), add_one_v4(1));
}

Each closure gets one concrete type, inferred on first use. Calling the same closure with a String and then an i32 is a type error.

2. Capturing and the move keyword

A closure captures each variable in the least demanding way its body allows: shared borrow, then mutable borrow, then move.

use std::thread;

fn main() {
    let list = vec![1, 2, 3];
    let only_borrows = || println!("borrow: {list:?}");
    only_borrows();
    println!("still usable: {list:?}");

    let mut list2 = vec![1, 2, 3];
    let mut borrows_mut = || list2.push(7);  // the closure itself must be mut
    borrows_mut();
    println!("after: {list2:?}");            // the &mut borrow ended

    // move: take ownership, required when the closure may outlive the scope
    thread::spawn(move || println!("from thread: {list:?}"))
        .join()
        .unwrap();
}

Between the definition of borrows_mut and its last call, list2 is mutably borrowed, so even a println! of it there is rejected. move forces ownership; a new thread needs it because the main thread might finish and drop list first.

3. Fn, FnMut and FnOnce

What a closure does with captured values decides which traits it implements, and functions use those traits as bounds.

TraitThe closure...Can be calledExample
FnOncemay move captured values out of its bodyonceOption::unwrap_or_else
FnMutmay change captured values, does not move them outmany times, with exclusive accesssort_by_key
Fnonly reads captured values, or captures nothingmany times, even concurrentlyIterator::map in a shared context

Every closure is FnOnce; those that do not move out are also FnMut; those that do not mutate are also Fn. Ask for the weakest bound you can: FnOnce accepts the most closures.

#[derive(Debug)]
struct Rectangle { width: u32, height: u32 }

fn main() {
    let mut list = [
        Rectangle { width: 10, height: 1 },
        Rectangle { width: 3, height: 5 },
        Rectangle { width: 7, height: 12 },
    ];
    let mut calls = 0;
    list.sort_by_key(|r| {      // FnMut: called once per comparison
        calls += 1;
        r.width
    });
    println!("{list:#?}\nsorted in {calls} calls");
}
does not compile
fn main() {
    let mut list = vec![String::from("a"), String::from("b")];
    let value = String::from("closure called");
    let mut ops = vec![];
    list.sort_by_key(|r| {
        ops.push(value); // error[E0507]: cannot move out of `value`, a captured variable in an `FnMut` closure
        r.clone()
    });
}

4. The Iterator trait

pub trait MyIterator {
    type Item;                                // associated type (chapter 20)
    fn next(&mut self) -> Option<Self::Item>;
    // ...about 75 provided methods built on next
}
fn main() {}

Everything else, map, filter, sum, collect, is a default method built on next. Implement next and you get all of them.

CallYieldsCollection afterwards
v.iter() / for x in &v&Tunchanged
v.iter_mut() / for x in &mut v&mut Tpossibly changed
v.into_iter() / for x in vTmoved, gone
fn main() {
    let v1 = vec![1, 2, 3];
    let mut it = v1.iter();        // must be mut: next changes its position
    assert_eq!(it.next(), Some(&1));
    assert_eq!(it.next(), Some(&2));
    assert_eq!(it.next(), Some(&3));
    assert_eq!(it.next(), None);
}

5. Consuming and adapter methods

Consuming adapters call next until the end and use the iterator up: sum, count, collect, fold, max, find, any, all. Iterator adapters wrap an iterator in another one and do nothing until consumed: map, filter, enumerate, zip, take, skip, chain, flat_map, rev, peekable. Fig 1 shows the laziness.

#[derive(PartialEq, Debug)]
struct Shoe { size: u32, style: String }

fn shoes_in_size(shoes: Vec<Shoe>, size: u32) -> Vec<Shoe> {
    shoes.into_iter().filter(|s| s.size == size).collect() // closure captures size
}

fn main() {
    let v = vec![1, 2, 3];
    let doubled: Vec<i32> = v.iter().map(|x| x * 2).collect();
    let evens = (1..=10).filter(|n| n % 2 == 0).count();
    let words = ["apple", "bob", "kayak"];
    let palins: Vec<_> = words.iter().filter(|w| w.chars().eq(w.chars().rev())).collect();
    let pairs: Vec<(usize, char)> = "abc".chars().enumerate().collect();
    let total = v.iter().fold(0, |acc, x| acc + x);
    println!("{doubled:?} {evens} {palins:?} {pairs:?} {total}");

    let shoes = vec![
        Shoe { size: 10, style: String::from("sneaker") },
        Shoe { size: 13, style: String::from("sandal") },
        Shoe { size: 10, style: String::from("boot") },
    ];
    println!("{:?}", shoes_in_size(shoes, 10));
}

An adapter chain that is never consumed triggers the warning "unused Map that must be used: iterators are lazy and do nothing unless consumed".

Your own iterator

struct Counter { count: u32 }

impl Iterator for Counter {
    type Item = u32;
    fn next(&mut self) -> Option<u32> {
        if self.count < 5 {
            self.count += 1;
            Some(self.count)
        } else {
            None
        }
    }
}

fn main() {
    let sum: u32 = Counter { count: 0 }
        .zip(Counter { count: 0 }.skip(1))
        .map(|(a, b)| a * b)
        .filter(|x| x % 3 == 0)
        .sum();
    println!("{sum}"); // 2*3 + 3*4 = 18
}

6. Improving minigrep

Config::build cloned the arguments because it only had a slice. Taking the iterator itself removes the clone, since next hands over owned Strings. search becomes one expression with no mutable state, which also makes it easy to parallelize later.

pub struct Config { pub query: String, pub file_path: String }

impl Config {
    pub fn build(mut args: impl Iterator<Item = String>) -> Result<Config, &'static str> {
        args.next(); // skip the program name
        let query = args.next().ok_or("Didn't get a query string")?;
        let file_path = args.next().ok_or("Didn't get a file path")?;
        Ok(Config { query, file_path })
    }
}

pub fn search<'a>(query: &str, contents: &'a str) -> Vec<&'a str> {
    contents.lines().filter(|line| line.contains(query)).collect()
}

fn main() {
    let args = ["minigrep", "fast", "x"].into_iter().map(String::from);
    let cfg = Config::build(args).unwrap();
    println!("{:?}", search(&cfg.query, "safe, fast, productive.\nPick three."));
}

7. Performance: loops versus iterators

The book benchmarks search over the full text of a novel: the for loop version and the iterator version run in about the same time. Iterators are a zero-cost abstraction: what you do not use you do not pay for, and what you do use you could not hand-code any better.

Adapter chains are generic structs and closures with known types, so the compiler inlines every next and closure call. Bounds checks often disappear, because the iterator knows it stays inside the slice, and fixed-length loops are unrolled. Choose whichever reads better; performance is not the deciding factor.

8. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
fn main() {
    let add = |x| x + 1;
    println!("{}", add(1));
    println!("{}", add(1.5));
}

The first call fixes the parameter type to an integer. A closure has exactly one concrete type, so 1.5 does not fit.

Q2 Does this compile?
fn main() {
    let mut n = 0;
    let mut inc = || n += 1;
    inc();
    inc();
    println!("{n}");
}

The closure borrows n mutably until its last call. After that, n can be read: prints 2.

Q3 Does this compile?
fn call_twice<F: Fn()>(f: F) { f(); f(); }
fn main() {
    let s = String::from("x");
    call_twice(move || drop(s));
}

The closure moves s out of its body, so it is only FnOnce. It cannot satisfy an Fn bound.

Q4 Does this compile?
fn main() {
    let v = vec![1, 2, 3];
    let total: i32 = v.iter().map(|x| x * 2).sum();
    println!("{total} {}", v.len());
}

iter() borrows, so v is still usable after the chain. Prints 12 3.

Q5 Does this compile?
fn main() {
    let v = vec![String::from("a")];
    for s in v { println!("{s}"); }
    println!("{}", v.len());
}

for s in v calls into_iter(), which consumes the vector. Loop over &v to keep it.
