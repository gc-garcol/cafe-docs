Rust Advanced Features

The features most code never needs, and that some code cannot do without: unsafe for talking to hardware and C, the finer points of traits and types that libraries rely on, function pointers, and macros, which write code for you at compile time.

1. Unsafe Rust

The compiler is conservative: it rejects some correct programs because it cannot prove them correct. Hardware is also unsafe by nature. An unsafe block unlocks five extra powers, and nothing else; the borrow checker and every other check stay on.

SuperpowerExample
Dereference a raw pointer*ptr where ptr: *const T or *mut T
Call an unsafe function or methodslice::from_raw_parts_mut, FFI functions
Access or modify a mutable staticstatic mut COUNTER: u32
Implement an unsafe traitunsafe impl Send for T
Access fields of a unionC-compatible unions

unsafe does not mean the code is wrong. It means "I, not the compiler, have checked these rules here". Keep unsafe blocks small and wrap them in safe APIs, so a memory bug can only come from a few audited places.

Raw pointers

fn main() {
    let mut num = 5;
    let r1 = &raw const num;   // *const i32
    let r2 = &raw mut num;     // *mut i32: may coexist with r1, unlike references
    unsafe {
        *r2 += 1;
        println!("r1 is: {}", *r1);
    }
    let address = 0x012345usize;
    let _r = address as *const i32; // creating one is safe; dereferencing this would be UB
}

Raw pointers may be null, may dangle, may alias mutably, and have no automatic cleanup. They exist for FFI and for building safe abstractions the borrow checker cannot understand.

Unsafe functions and safe abstractions

/// # Safety
/// The caller must ensure `i < s.len()`.
unsafe fn get_unchecked(s: &[u8], i: usize) -> u8 {
    unsafe { *s.as_ptr().add(i) }   // unsafe ops still need a block in edition 2024
}

fn main() {
    let data = [1u8, 2, 3];
    // SAFETY: 2 < data.len()
    let x = unsafe { get_unchecked(&data, 2) };
    println!("{x}");
}

Fig 1 shows split_at_mut from the standard library. Borrowing &mut values[..mid] and &mut values[mid..] at the same time is rejected, even though they never overlap; the unsafe version is sound because of the bounds assert. Document every unsafe fn with a # Safety section and every block with a // SAFETY: comment.

does not compile
fn split_at_mut(values: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {

Calling C with extern

unsafe extern "C" {
    safe fn abs(input: i32) -> i32;      // we vouch it is safe to call
    fn strlen(s: *const std::ffi::c_char) -> usize;
}

#[unsafe(no_mangle)]
pub extern "C" fn call_from_c() {       // callable from C by this exact name
    println!("Just called a Rust function from C!");
}

fn main() {
    println!("Absolute value of -3 according to C: {}", abs(-3));
    let n = unsafe { strlen(c"hello".as_ptr()) };
    println!("{n}");
}

Mutable statics and unsafe traits

static mut COUNTER: u32 = 0;

/// # Safety
/// Only call from a single thread at a time.
unsafe fn add_to_count(inc: u32) {
    unsafe { COUNTER += inc; }
}

struct MyPtr(*mut u8);
// SAFETY: we promise MyPtr is only used in ways that are thread-safe
unsafe impl Send for MyPtr {}

fn main() {
    unsafe {
        // SAFETY: main is the only thread
        add_to_count(3);
        println!("COUNTER: {}", *(&raw const COUNTER));
    }
    let _p = MyPtr(std::ptr::null_mut());
}

Every access to a static mut is unsafe, because two threads could race on it. Prefer atomics, Mutex or OnceLock. To catch undefined behaviour in unsafe code, run tests under Miri: cargo +nightly miri test.

2. Advanced traits

Associated types

type Item; in Iterator is a placeholder that each implementation fills in once. With a generic Iterator<T>, a type could implement it many times and every call would need annotations. An associated type says there is exactly one Item per implementing type.

struct Counter { n: u32 }

impl Iterator for Counter {
    type Item = u32;                         // chosen once
    fn next(&mut self) -> Option<Self::Item> {
        self.n += 1;
        if self.n < 4 { Some(self.n) } else { None }
    }
}

fn main() {
    println!("{:?}", Counter { n: 0 }.collect::<Vec<_>>());
}

Default type parameters and operator overloading

Operators are traits in std::ops. Add is declared as trait Add<Rhs = Self>: the right-hand side defaults to the same type, but can differ.

use std::ops::Add;

#[derive(Debug, Copy, Clone, PartialEq)]
struct Point { x: i32, y: i32 }

impl Add for Point {                          // Rhs = Self by default
    type Output = Point;
    fn add(self, other: Point) -> Point {
        Point { x: self.x + other.x, y: self.y + other.y }
    }
}

#[derive(Debug)] struct Millimeters(u32);
struct Meters(u32);

impl Add<Meters> for Millimeters {            // different Rhs
    type Output = Millimeters;
    fn add(self, other: Meters) -> Millimeters { Millimeters(self.0 + other.0 * 1000) }
}

fn main() {
    assert_eq!(Point { x: 1, y: 0 } + Point { x: 2, y: 3 }, Point { x: 3, y: 3 });
    println!("{:?}", Millimeters(500) + Meters(2));
}

Disambiguating methods with the same name

trait Pilot { fn fly(&self); fn name() -> String; }
trait Wizard { fn fly(&self); }
struct Human;

impl Pilot for Human {
    fn fly(&self) { println!("This is your captain speaking."); }
    fn name() -> String { String::from("pilot") }
}
impl Wizard for Human { fn fly(&self) { println!("Up!"); } }
impl Human {
    fn fly(&self) { println!("*waving arms furiously*"); }
    fn name() -> String { String::from("human") }
}

fn main() {
    let person = Human;
    person.fly();            // the type's own method wins
    Pilot::fly(&person);
    Wizard::fly(&person);
    println!("{} / {}", Human::name(), <Human as Pilot>::name()); // fully qualified syntax
}

For associated functions without self, Pilot::name() is ambiguous, since any type could implement Pilot. Fully qualified syntax, <Type as Trait>::function(..), names both.

Supertraits

use std::fmt;

trait OutlinePrint: fmt::Display {            // requires Display
    fn outline_print(&self) {
        let output = self.to_string();        // available because of the supertrait
        let len = output.len();
        println!("{}", "*".repeat(len + 4));
        println!("* {output} *");
        println!("{}", "*".repeat(len + 4));
    }
}

struct Point { x: i32, y: i32 }
impl fmt::Display for Point {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result { write!(f, "({}, {})", self.x, self.y) }
}
impl OutlinePrint for Point {}

fn main() { Point { x: 1, y: 3 }.outline_print(); }

The newtype pattern

The orphan rule forbids implementing an external trait on an external type. Wrap the type in a local tuple struct and implement the trait on the wrapper. The wrapper has no run-time cost; implement Deref if it should expose all the inner methods.

use std::fmt;

struct Wrapper(Vec<String>);

impl fmt::Display for Wrapper {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        write!(f, "[{}]", self.0.join(", "))
    }
}

fn main() {
    let w = Wrapper(vec![String::from("hello"), String::from("world")]);
    println!("w = {w}");
}

3. Advanced types

Newtypes for safety, aliases for brevity

A newtype such as struct Meters(u32) is a distinct type: mixing it with Millimeters is an error. A type alias is only another name, interchangeable with the original. Use aliases to shorten long types.

type Kilometers = i32;                                  // same type as i32
type Thunk = Box<dyn Fn() + Send + 'static>;
type Result<T> = std::result::Result<T, std::io::Error>; // as std::io does

fn takes_long_type(f: Thunk) { f() }
fn read() -> Result<usize> { Ok(0) }

fn main() {
    let x: i32 = 5;
    let y: Kilometers = 5;
    println!("x + y = {}", x + y);
    takes_long_type(Box::new(|| println!("hi")));
    println!("{:?}", read().unwrap());
}

The never type !

! is the type of expressions that never produce a value: panic!, continue, break, return, loop without break, process::exit. It coerces to any type, which is why a match arm can continue while others yield a u32.

fn forever() -> ! {
    loop {
        std::thread::park();
    }
}

fn main() {
    let guesses = ["x", "7"];
    for g in guesses {
        let n: u32 = match g.trim().parse() {
            Ok(num) => num,
            Err(_) => continue,     // type !, coerces to u32
        };
        println!("{n}");
    }
    if false { forever(); }
}

Dynamically sized types and Sized

str (not &str) and dyn Trait have sizes known only at run time. You cannot hold one in a variable; you use them behind a pointer that also stores the size or a vtable: &str, Box<str>, Rc<dyn Trait>. Every generic parameter gets an implicit T: Sized bound. ?Sized relaxes it, and then the value must be behind a pointer:

fn show<T: ?Sized + std::fmt::Debug>(t: &T) { println!("{t:?}"); }

fn main() {
    show("a str, which is unsized");
    show(&[1, 2, 3][..]);   // [i32] is unsized too
}

4. Function pointers and returning closures

fn (lowercase) is the type of a function pointer. It implements all three closure traits, so a function can be passed wherever a closure is expected. C has function pointers but no closures, so FFI callbacks use fn.

fn add_one(x: i32) -> i32 { x + 1 }

fn do_twice(f: fn(i32) -> i32, arg: i32) -> i32 {
    f(arg) + f(arg)
}

#[derive(Debug)]
enum Status { Value(u32) }

fn main() {
    println!("The answer is: {}", do_twice(add_one, 5));

    let strings: Vec<String> = vec![1, 2, 3].iter().map(ToString::to_string).collect();
    let statuses: Vec<Status> = (0u32..3).map(Status::Value).collect(); // variants are functions
    println!("{strings:?} {statuses:?}");
}

Each closure has its own anonymous type. Return one closure with impl Fn; return different closures from one function with a trait object.

fn returns_closure() -> impl Fn(i32) -> i32 {
    |x| x + 1
}

fn returns_initialized_closure(init: i32) -> Box<dyn Fn(i32) -> i32> {
    if init > 0 { Box::new(move |x| x + init) } else { Box::new(|x| x * 2) }
}

fn main() {
    let handlers = vec![returns_initialized_closure(5), returns_initialized_closure(-1), Box::new(returns_closure())];
    for h in handlers { println!("{}", h(5)); }
}

5. Macros

Macros are metaprogramming: code that writes code. Unlike functions, they can take a variable number of arguments, run at compile time, and generate items such as trait implementations. The price is that macro definitions are harder to read and to debug, and must be defined or imported before use.

Declarative macros with macro_rules!

A declarative macro matches its input against patterns of Rust syntax and replaces it with code. A simplified vec!:

#[macro_export]
macro_rules! my_vec {
    ( $( $x:expr ),* $(,)? ) => {      // zero or more expressions, separated by commas
        {
            let mut temp_vec = Vec::new();
            $(
                temp_vec.push($x);     // repeated once per matched $x
            )*
            temp_vec
        }
    };
}

macro_rules! square {
    ($e:expr) => { $e * $e };
}

fn main() {
    let v = my_vec![1, 2, 3,];
    println!("{v:?} {}", square!(2 + 1)); // 9: $e is an expression, not text
}
FragmentMatches
$x:expran expression
$t:tya type
$i:identan identifier
$p:pata pattern
$b:block, $s:stmt, $tt:tta block, a statement, any single token tree
$( ... ),* / + / ?repeat zero or more / one or more / zero or one times

Procedural macros

A procedural macro is a function from a TokenStream to a TokenStream, compiled in its own crate with proc-macro = true. The syn crate parses tokens into a syntax tree and quote turns code back into tokens. There are three kinds:

KindUsed asExample
Custom derive#[derive(HelloMacro)] on a struct or enumserde::Serialize
Attribute-like#[route(GET, "/")] on any itemweb frameworks, #[tokio::main]
Function-likesql!(SELECT * FROM posts)checking a DSL at compile time
// hello_macro_derive/src/lib.rs   ([lib] proc-macro = true)
use proc_macro::TokenStream;
use quote::quote;

#[proc_macro_derive(HelloMacro)]
pub fn hello_macro_derive(input: TokenStream) -> TokenStream {
    let ast: syn::DeriveInput = syn::parse(input).unwrap();
    let name = &ast.ident;
    let generated = quote! {
        impl HelloMacro for #name {
            fn hello_macro() {
                println!("Hello, Macro! My name is {}!", stringify!(#name));
            }
        }
    };
    generated.into()
}

// in a user crate
#[derive(HelloMacro)]
struct Pancakes;

fn main() {
    Pancakes::hello_macro(); // Hello, Macro! My name is Pancakes!
}

cargo expand (a separate tool) prints the code after macro expansion, which is the fastest way to see what a macro really generates.

6. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
fn main() {
    let x = 5;
    let p = &raw const x;
    println!("{}", *p);
}

Creating a raw pointer is safe, but dereferencing it requires an unsafe block.

Q2 Does this compile?
use std::ops::Add;
#[derive(Debug)]
struct V(i32);
impl Add for V { type Output = V; fn add(self, o: V) -> V { V(self.0 + o.0) } }
fn main() { println!("{:?}", V(1) + V(2)); }

Implementing std::ops::Add overloads +. Prints V(3).

Q3 Does this compile?
type Meters = u32;
type Feet = u32;
fn main() {
    let a: Meters = 3;
    let b: Feet = 4;
    println!("{}", a + b);
}

Type aliases are just names for u32, so they mix freely. Use newtypes when they should not.

Q4 Does this compile?
fn make(n: i32) -> impl Fn(i32) -> i32 {
    if n > 0 { move |x| x + n } else { move |x| x - n }
}
fn main() {}

Every closure has its own type, and impl Fn must be one type. Return Box<dyn Fn(i32) -> i32> instead. (Closures that capture nothing would compile here: both coerce to the same fn pointer type.)

Q5 Does this compile?
macro_rules! twice { ($e:expr) => { $e * 2 }; }
fn main() { println!("{}", twice!(1 + 2)); }

$e captures an expression node, not text, so this is (1 + 2) * 2 = 6, not 1 + 2 * 2.
