Rust Smart Pointers

A reference only borrows. A smart pointer is a struct that acts like a pointer and also owns the data, adding a capability on top: heap allocation (Box), shared ownership (Rc), or borrow checks at run time (RefCell). They are built on two traits, Deref and Drop.

#rust#smart pointers#box#rc

Step through it

Each Rc::clone adds an owner; each drop removes one. A Weak points at the same allocation without keeping the value alive. Watch the counts in the heap box.

1. Box<T>: data on the heap

Box<T> puts a value on the heap and keeps a pointer on the stack. It has no overhead besides the allocation and no extra capability. Use it when:

  • a type's size cannot be known at compile time, but you need it in a context that requires a size (recursive types);
  • you have a large value and want to move ownership without copying the bytes;
  • you want a value of "some type implementing a trait" (Box<dyn Trait>, chapter 18).
does not compile
enum List {
    Cons(i32, List), // error[E0072]: recursive type `List` has infinite size
    Nil,
}

To size List, the compiler needs the size of List, forever. A Box has a fixed size, one pointer, which breaks the recursion:

#[derive(Debug)]
enum List {
    Cons(i32, Box<List>),
    Nil,
}
use List::{Cons, Nil};

fn main() {
    let list = Cons(1, Box::new(Cons(2, Box::new(Cons(3, Box::new(Nil))))));
    println!("{list:?}");
    let b = Box::new(5);
    println!("b = {b}"); // used like the value itself
}

2. Deref: treating a pointer like a reference

*x follows a reference. Implementing Deref lets your type support * too: *y becomes *(y.deref()). deref returns a reference, so the value is not moved out.

use std::ops::Deref;

struct MyBox<T>(T);

impl<T> MyBox<T> {
    fn new(x: T) -> MyBox<T> { MyBox(x) }
}

impl<T> Deref for MyBox<T> {
    type Target = T;
    fn deref(&self) -> &T { &self.0 }
}

fn hello(name: &str) { println!("Hello, {name}!"); }

fn main() {
    let x = 5;
    let y = MyBox::new(x);
    assert_eq!(5, *y);

    let m = MyBox::new(String::from("Rust"));
    hello(&m);              // &MyBox<String> -> &String -> &str
    hello(&(*m)[..]);       // what we would write without coercion
}

Deref coercion

When a reference's type does not match a parameter, the compiler inserts as many deref calls as needed. It is resolved at compile time and costs nothing. The rules:

FromToWhen
&T&UT: Deref<Target = U>
&mut T&mut UT: DerefMut<Target = U>
&mut T&UT: Deref<Target = U>

An immutable reference never coerces to a mutable one: that would break the rule that a &mut is the only reference.

3. Drop: running code on cleanup

struct CustomSmartPointer { data: String }

impl Drop for CustomSmartPointer {
    fn drop(&mut self) {
        println!("Dropping CustomSmartPointer with data `{}`!", self.data);
    }
}

fn main() {
    let _c = CustomSmartPointer { data: String::from("my stuff") };
    let d = CustomSmartPointer { data: String::from("other stuff") };
    println!("CustomSmartPointers created");
    drop(d);                       // std::mem::drop: drop it early
    println!("d dropped before the end of main");
}                                  // _c dropped here

Variables are dropped in reverse order of creation. You cannot call d.drop() yourself (error E0040), because Rust would call it again at the end of the scope: a double free. std::mem::drop(d), in the prelude as drop, takes ownership instead, so the automatic drop never happens. Typical uses: releasing a lock early, closing a file, flushing a buffer.

4. Rc<T>: shared ownership

Sometimes a value has several owners, such as a node in a graph that many edges point to, and none of them is clearly the last to use it. Rc<T>, reference counted, keeps a count of owners and frees the value when it reaches zero. Fig 1 steps through the counts.

use std::rc::Rc;

#[derive(Debug)]
enum List { Cons(i32, Rc<List>), Nil }
use List::{Cons, Nil};

fn main() {
    let a = Rc::new(Cons(5, Rc::new(Cons(10, Rc::new(Nil)))));
    println!("count after creating a = {}", Rc::strong_count(&a));
    let _b = Cons(3, Rc::clone(&a));     // b and c share a
    println!("count after creating b = {}", Rc::strong_count(&a));
    {
        let _c = Cons(4, Rc::clone(&a));
        println!("count after creating c = {}", Rc::strong_count(&a));
    }
    println!("count after c goes out of scope = {}", Rc::strong_count(&a));
}

Write Rc::clone(&a), not a.clone(): same effect, but it signals a cheap count increment, not a deep copy. Rc gives only shared, read-only access, since many owners with mutable access would be aliasing plus mutation. It is single-threaded; across threads use Arc (chapter 16).

5. RefCell<T> and interior mutability

Interior mutability lets you mutate data through a shared reference. The borrowing rules still hold, but RefCell<T> checks them at run time: borrow() returns a Ref<T>, borrow_mut() a RefMut<T>, and the cell counts them. Breaking the rules panics instead of failing to compile.

Box<T>Rc<T>RefCell<T>
Ownersonemanyone
Borrows checkedcompile timecompile time (shared only)run time
Mutate through &selfnonoyes

A typical case is a test double. A Messenger trait takes &self, but the mock wants to record each message:

use std::cell::RefCell;

pub trait Messenger { fn send(&self, msg: &str); }

struct MockMessenger { sent: RefCell<Vec<String>> }

impl Messenger for MockMessenger {
    fn send(&self, message: &str) {
        self.sent.borrow_mut().push(String::from(message)); // mutate via &self
    }
}

fn main() {
    let m = MockMessenger { sent: RefCell::new(vec![]) };
    m.send("over 75% of quota");
    assert_eq!(m.sent.borrow().len(), 1);

    let cell = RefCell::new(1);
    let _first = cell.borrow_mut();
    println!("second borrow_mut is ok? {}", cell.try_borrow_mut().is_ok()); // false
}

Two live borrow_mut() calls panic with "already borrowed: BorrowMutError". try_borrow_mut returns a Result instead. For Copy types, Cell<T> offers get and set with no run-time borrow tracking.

Rc<RefCell<T>>: many owners that can mutate

use std::cell::RefCell;
use std::rc::Rc;

#[derive(Debug)]
enum List { Cons(Rc<RefCell<i32>>, Rc<List>), Nil }
use List::{Cons, Nil};

fn main() {
    let value = Rc::new(RefCell::new(5));
    let a = Rc::new(Cons(Rc::clone(&value), Rc::new(Nil)));
    let b = Cons(Rc::new(RefCell::new(3)), Rc::clone(&a));
    let c = Cons(Rc::new(RefCell::new(4)), Rc::clone(&a));

    *value.borrow_mut() += 10;   // seen through a, b and c

    println!("a = {a:?}\nb = {b:?}\nc = {c:?}");
}

6. Reference cycles and Weak<T>

Rust guarantees memory safety, not freedom from leaks. With Rc and RefCell you can build a cycle: a points to b, b points back to a. When both variables go out of scope, each count drops to 1, never 0, and the memory is never freed.

The fix is to decide which links own and which only observe. Rc::downgrade creates a Weak<T> that does not count as an owner. upgrade() returns Option<Rc<T>>, None if the value is gone. In a tree, parents own their children and children point weakly to their parent:

use std::cell::RefCell;
use std::rc::{Rc, Weak};

#[derive(Debug)]
struct Node {
    value: i32,
    parent: RefCell<Weak<Node>>,       // does not own
    children: RefCell<Vec<Rc<Node>>>,  // owns
}

fn main() {
    let leaf = Rc::new(Node { value: 3, parent: RefCell::new(Weak::new()), children: RefCell::new(vec![]) });
    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value));

    {
        let branch = Rc::new(Node { value: 5, parent: RefCell::new(Weak::new()), children: RefCell::new(vec![Rc::clone(&leaf)]) });
        *leaf.parent.borrow_mut() = Rc::downgrade(&branch);
        println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value));
        println!("branch strong = {}, weak = {}", Rc::strong_count(&branch), Rc::weak_count(&branch));
        println!("leaf strong = {}, weak = {}", Rc::strong_count(&leaf), Rc::weak_count(&leaf));
    }

    println!("leaf parent = {:?}", leaf.parent.borrow().upgrade().map(|p| p.value)); // None
    println!("leaf strong = {}", Rc::strong_count(&leaf));                          // 1
}
PointerUse it for
Box<T>Single owner on the heap; recursive types; trait objects.
Rc<T>Several owners, read-only, one thread.
RefCell<T> / Cell<T>Mutation through a shared reference, checked at run time.
Weak<T>Back-pointers and caches that must not keep a value alive.
Arc<T> / Mutex<T>The thread-safe versions of Rc and RefCell.

7. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
use std::rc::Rc;
fn main() {
    let a = Rc::new(vec![1]);
    a.push(2);
}

Rc only hands out shared references. To mutate shared data, wrap it: Rc<RefCell<Vec<i32>>>.

Q2 Does this compile?
use std::cell::RefCell;
fn main() {
    let v = RefCell::new(vec![1]);
    let r1 = v.borrow_mut();
    let r2 = v.borrow_mut();
}

It compiles: RefCell checks borrows at run time. Running it panics with BorrowMutError, because two mutable borrows are alive.

Q3 Does this compile?
struct D;
impl Drop for D { fn drop(&mut self) {} }
fn main() {
    let d = D;
    d.drop();
}

Explicit destructor calls are not allowed (E0040). Use drop(d), which takes ownership.

Q4 Does this compile?
fn len(s: &str) -> usize { s.len() }
fn main() {
    let b = Box::new(String::from("hey"));
    println!("{}", len(&b));
}

Deref coercion: &Box<String> → &String → &str, all at compile time.
