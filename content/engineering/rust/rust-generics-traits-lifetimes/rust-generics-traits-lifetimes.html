Rust Generics, Traits and Lifetimes

Three tools remove duplication without losing type safety. Generics let one definition work for many types. Traits describe what a type can do, and bound which types a generic accepts. Lifetimes are generics too: they tell the compiler how long references must stay valid.

#rust#generics#traits#lifetimes

Step through it

The signature fn longest<'a>(x: &'a str, y: &'a str) -> &'a str says the result lives no longer than the shorter of the two inputs. Step through and see which use the compiler would reject.

1. Generic data types

Two functions that find the largest i32 and the largest char have identical bodies. A type parameter, conventionally T, merges them. The body may only do what the bounds allow, here comparison via PartialOrd:

fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut largest = &list[0];
    for item in list {
        if item > largest {
            largest = item;
        }
    }
    largest
}

fn main() {
    println!("{}", largest(&[34, 50, 25, 100, 65]));
    println!("{}", largest(&['y', 'm', 'a', 'q']));
}

In structs, enums and methods

#[derive(Debug)]
struct Point<T, U> {
    x: T,
    y: U,
}

impl<T, U> Point<T, U> {                       // for every T and U
    fn x(&self) -> &T { &self.x }
    fn mixup<V, W>(self, other: Point<V, W>) -> Point<T, W> {
        Point { x: self.x, y: other.y }
    }
}

impl Point<f64, f64> {                         // only for this concrete type
    fn distance_from_origin(&self) -> f64 {
        (self.x.powi(2) + self.y.powi(2)).sqrt()
    }
}

fn main() {
    let p = Point { x: 5, y: 10.4 };
    let q = Point { x: "Hello", y: 'c' };
    println!("{}", p.x());
    println!("{:?}", p.mixup(q)); // p is moved: mixup takes self
    println!("{}", Point { x: 3.0, y: 4.0 }.distance_from_origin());
}

Option<T> and Result<T, E> are ordinary generic enums. Note the impl<T, U>: the parameters are declared after impl so the compiler knows Point<T, U> refers to generic, not concrete, types.

Zero cost: monomorphization

At compile time Rust generates one copy of a generic function for each concrete type it is used with, largest_i32, largest_char and so on. There is no boxing or dynamic dispatch, so generic code runs as fast as hand-written code. The cost is compile time and binary size.

2. Traits: shared behaviour

A trait is a set of method signatures that a type can implement, similar to an interface.

pub trait Summary {
    fn summarize_author(&self) -> String;

    fn summarize(&self) -> String {            // default implementation
        format!("(Read more from {}...)", self.summarize_author())
    }
}

pub struct Tweet { pub username: String, pub content: String }
pub struct Article { pub title: String, pub author: String }

impl Summary for Tweet {
    fn summarize_author(&self) -> String { format!("@{}", self.username) }
}

impl Summary for Article {
    fn summarize_author(&self) -> String { self.author.clone() }
    fn summarize(&self) -> String {            // override the default
        format!("{}, by {}", self.title, self.author)
    }
}

fn main() {
    let t = Tweet { username: "horse_ebooks".into(), content: "of course".into() };
    let a = Article { title: "Penguins win".into(), author: "Iceburgh".into() };
    println!("{}\n{}", t.summarize(), a.summarize());
}

Default methods may call other methods of the trait, even ones without a default. Implementors then only write the required pieces.

The orphan rule

You can implement a trait for a type only if the trait or the type is defined in your crate. You can implement Display for your Tweet, or your Summary for Vec<T>, but not Display for Vec<T>. This coherence rule guarantees that two crates can never provide conflicting implementations. The newtype pattern (chapter 20) is the usual workaround.

3. Traits as parameters and bounds

use std::fmt::{Debug, Display};

trait Summary { fn summarize(&self) -> String; }
impl Summary for String { fn summarize(&self) -> String { self.chars().take(5).collect() } }

// impl Trait in argument position: sugar for a generic with a bound
fn notify(item: &impl Summary) {
    println!("Breaking news! {}", item.summarize());
}

// trait bound syntax: forces both arguments to be the same type
fn notify_pair<T: Summary>(a: &T, b: &T) {
    println!("{} / {}", a.summarize(), b.summarize());
}

// several bounds, written in a where clause for readability
fn report<T, U>(t: &T, u: &U) -> String
where
    T: Display + Clone,
    U: Clone + Debug,
{
    format!("{t} {u:?}")
}

// impl Trait in return position: one concrete hidden type
fn make_summary() -> impl Summary {
    String::from("hello world")
}

fn main() {
    let s = String::from("hello there");
    notify(&s);
    notify(&make_summary());
    notify_pair(&s, &String::from("general kenobi"));
    // notify_pair(&s, &make_summary()); // error: the opaque type is not String
    println!("{}", report(&1, &vec![2]));
}
FormMeaning
fn f(x: &impl Tr)Any type implementing Tr. Short, but the caller cannot name the type with turbofish.
fn f<T: Tr>(x: &T, y: &T)Same type for both. Required when parameters must match.
T: A + BMust implement both traits.
where T: ...The same bounds, moved after the signature.
fn f() -> impl TrReturns one concrete type the caller cannot name. Used for closures and iterators. All return paths must be the same type; for different types use Box<dyn Tr>.

Conditional and blanket implementations

An impl block can require bounds, so methods exist only when the type parameter supports them. A blanket implementation implements a trait for every type that satisfies a bound. The standard library implements ToString for every T: Display, which is why 3.to_string() works.

use std::fmt::Display;

struct Pair<T> { x: T, y: T }

impl<T> Pair<T> {
    fn new(x: T, y: T) -> Self { Self { x, y } }
}

impl<T: Display + PartialOrd> Pair<T> {   // only if T can be compared and printed
    fn cmp_display(&self) {
        if self.x >= self.y { println!("largest is x = {}", self.x); }
        else { println!("largest is y = {}", self.y); }
    }
}

trait Shout { fn shout(&self) -> String; }
impl<T: Display> Shout for T {            // blanket impl
    fn shout(&self) -> String { self.to_string().to_uppercase() }
}

fn main() {
    Pair::new(3, 7).cmp_display();
    println!("{}", "quiet".shout());
}

4. Lifetimes

Every reference has a lifetime, the region of code where it is valid. Usually the compiler infers them. You annotate when a function returns a reference and the compiler cannot tell which input it came from:

does not compile
fn longest(x: &str, y: &str) -> &str { // error[E0106]: missing lifetime specifier
    if x.len() > y.len() { x } else { y }
}

Annotations do not change how long anything lives. They name relationships, so the compiler can check every caller. &'a str reads "a string slice valid for at least 'a". In longest<'a>, the returned reference is valid as long as both inputs are; Fig 1 shows the consequence.

Only annotate parameters that the result can come from. If longest always returned x, y would need no lifetime at all. A function can never return a reference to a local value, whatever the annotation: return an owned value instead.

In structs

struct ImportantExcerpt<'a> {
    part: &'a str,           // the struct cannot outlive the text it borrows
}

impl<'a> ImportantExcerpt<'a> {
    fn announce(&self, msg: &str) -> &str {   // elision rule 3: result tied to &self
        println!("Attention: {msg}");
        self.part
    }
}

fn main() {
    let novel = String::from("Call me Ishmael. Some years ago...");
    let first = novel.split('.').next().unwrap();
    let ex = ImportantExcerpt { part: first };
    println!("{}", ex.announce("hi"));
}

Elision rules

Early Rust required annotations everywhere. Common patterns were turned into three rules the compiler applies to signatures; you only write annotations when they leave something ambiguous.

RuleEffectExample
1. Each input reference gets its own lifetimefn f(x: &str, y: &str) becomes fn f<'a, 'b>(x: &'a str, y: &'b str)-
2. One input lifetime → all outputs get itfn first_word(s: &str) -> &str needs nothingmost getters
3. A &self or &mut self → outputs get its lifetimemethods returning borrowed fields need nothingannounce above

If outputs still have no lifetime after the rules, the compiler asks you. That is exactly the longest case: two inputs, no self.

The 'static lifetime

'static means "can live for the whole program". String literals are &'static str, because they are stored in the binary. A bound T: 'static means T contains no short-lived borrows; owned types like String satisfy it. When the compiler suggests adding 'static to fix an error, it is usually pointing at a dangling reference, not a missing annotation.

5. All three together

use std::fmt::Display;

fn longest_with_an_announcement<'a, T>(x: &'a str, y: &'a str, ann: T) -> &'a str
where
    T: Display,
{
    println!("Announcement! {ann}");
    if x.len() > y.len() { x } else { y }
}

fn main() {
    println!("{}", longest_with_an_announcement("abcd", "xyz", 2024));
}

Lifetime parameters and type parameters share the angle brackets, lifetimes first. All of this is checked at compile time and erased before code generation.

6. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
fn largest<T>(list: &[T]) -> &T {
    let mut m = &list[0];
    for x in list { if x > m { m = x; } }
    m
}
fn main() {}

Without a PartialOrd bound, the compiler does not know T supports >. Write T: PartialOrd.

Q2 Does this compile?
use std::fmt::Display;
impl Display for Vec<u8> {
    fn fmt(&self, f: &mut std::fmt::Formatter) -> std::fmt::Result { Ok(()) }
}
fn main() {}

The orphan rule: neither Display nor Vec is local to your crate. Wrap the vector in a newtype.

Q3 Does this compile?
fn first<'a>(x: &'a str, y: &str) -> &'a str { x }
fn main() {
    let s = String::from("a");
    let r;
    {
        let t = String::from("b");
        r = first(&s, &t);
    }
    println!("{r}");
}

The result is tied only to x, so t may die early. r borrows s, which is still alive.

Q4 Does this compile?
fn pick(flag: bool) -> impl std::fmt::Display {
    if flag { 1 } else { "one" }
}
fn main() {}

impl Trait in return position is a single concrete type. Returning i32 on one path and &str on another needs Box<dyn Display>.

Q5 Does this compile?
fn get(v: &Vec<String>) -> &str {
    &v[0]
}
fn main() { println!("{}", get(&vec!["x".into()])); }

One input reference, so elision rule 2 gives the output its lifetime. &String coerces to &str.
