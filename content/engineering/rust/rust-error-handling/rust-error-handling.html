Rust Error Handling

Rust splits errors in two. A bug, such as an index past the end, is unrecoverable and stops the thread with panic!. A failure the caller should handle, such as a missing file, is recoverable and is returned as a Result. There are no exceptions, so every fallible call is visible in the types.

1. Unrecoverable errors with panic!

A panic prints a message, unwinds the stack of the current thread (running drop for every value on the way) and ends the thread. If it is the main thread, the program exits with a non-zero code. Panics come from panic! or from code that detects a bug, such as an out-of-bounds index.

fn main() {
    let v = vec![1, 2, 3];
    v[99]; // thread 'main' panicked at src/main.rs:3:5: index out of bounds: the len is 3 but the index is 99
}
$ RUST_BACKTRACE=1 cargo run      # show the call stack that led to the panic
$ RUST_BACKTRACE=full cargo run   # with every frame

Unwinding takes work and code size. In Cargo.toml, [profile.release] panic = 'abort' makes a panic end the process immediately and leaves cleanup to the OS.

2. Recoverable errors with Result

enum Result<T, E> {
    Ok(T),
    Err(E),
}
fn main() {}

A function that can fail returns Result. The caller has to look inside to get the value, and Result is marked #[must_use], so ignoring one gives a warning.

use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let path = "/tmp/hello-rust-book.txt";
    let file = match File::open(path) {
        Ok(f) => f,
        Err(e) if e.kind() == ErrorKind::NotFound => match File::create(path) {
            Ok(f) => f,
            Err(e) => panic!("cannot create {path}: {e:?}"),
        },
        Err(e) => panic!("cannot open {path}: {e:?}"),
    };
    println!("{file:?}");
}

Nested matches grow quickly. Closures make the same logic shorter:

use std::fs::File;
use std::io::ErrorKind;

fn main() {
    let path = "/tmp/hello-rust-book.txt";
    let file = File::open(path).unwrap_or_else(|e| {
        if e.kind() == ErrorKind::NotFound {
            File::create(path).expect("cannot create file")
        } else {
            panic!("cannot open file: {e:?}");
        }
    });
    println!("{file:?}");
}

unwrap and expect

unwrap() returns the Ok value or panics with the error. expect("msg") does the same with your message, which should say why you expected success: expect("config.toml is shipped with the binary"). Production code prefers expect, because the message explains the assumption that broke.

3. Propagating errors with ?

Often a function should not decide what to do with an error, only pass it up. Writing that with match is repetitive:

use std::fs::File;
use std::io::{self, Read};

fn read_username_long() -> Result<String, io::Error> {
    let mut f = match File::open("username.txt") {
        Ok(f) => f,
        Err(e) => return Err(e),
    };
    let mut s = String::new();
    match f.read_to_string(&mut s) {
        Ok(_) => Ok(s),
        Err(e) => Err(e),
    }
}

fn read_username() -> Result<String, io::Error> {
    let mut s = String::new();
    File::open("username.txt")?.read_to_string(&mut s)?;
    Ok(s)
}

fn main() {
    println!("{:?} {:?}", read_username_long().is_err(), read_username().is_err());
}

expr? means: if Ok(v), evaluate to v; if Err(e), return Err(From::from(e)). The From conversion lets one function return a single error type while calling functions with different ones. (For this exact task, std::fs::read_to_string does it all in one call.)

Where ? can be used

Only in a function whose return type is compatible: Result with Result, Option with Option (where None returns early), or another type implementing FromResidual. It does not convert between Option and Result on its own; use ok_or or .ok().

does not compile
use std::fs::File;
fn main() {
    let f = File::open("hello.txt")?; // error[E0277]: the `?` operator can only be used in a function that returns `Result` or `Option`
}
use std::error::Error;
use std::fs::File;

fn main() -> Result<(), Box<dyn Error>> {
    let _f = File::open("/etc/hosts")?;
    let n: i32 = "42".parse()?;   // a different error type, boxed by From
    println!("{n}");
    Ok(())                        // exit code 0; an Err gives a non-zero code
}
fn last_char_of_first_line(text: &str) -> Option<char> {
    text.lines().next()?.chars().last()
}
fn main() {
    println!("{:?} {:?}", last_char_of_first_line("Hi\nthere"), last_char_of_first_line(""));
}

4. Your own error types

A library should return a specific error type that callers can match on. An enum with one variant per failure, plus Display, Error and From implementations, makes ? work across layers.

use std::fmt;
use std::num::ParseIntError;

#[derive(Debug)]
enum ConfigError {
    Missing(&'static str),
    BadNumber(ParseIntError),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter) -> fmt::Result {
        match self {
            ConfigError::Missing(k) => write!(f, "missing key {k}"),
            ConfigError::BadNumber(e) => write!(f, "bad number: {e}"),
        }
    }
}
impl std::error::Error for ConfigError {}

impl From<ParseIntError> for ConfigError {
    fn from(e: ParseIntError) -> Self { ConfigError::BadNumber(e) }
}

fn port(value: Option<&str>) -> Result<u16, ConfigError> {
    let v = value.ok_or(ConfigError::Missing("port"))?;
    let n: u16 = v.parse()?;            // ParseIntError -> ConfigError via From
    Ok(n)
}

fn main() {
    println!("{:?}", port(Some("8080")));
    for bad in [None, Some("80x")] {
        if let Err(e) = port(bad) { println!("{e}"); }
    }
}

Application code, errors are reported, not matchedBox<dyn Error> or the anyhow crate

5. To panic or not to panic

Returning Result leaves the decision to the caller, so it is the right default for functions that might fail. Panicking is appropriate when continuing would be wrong:

  • Examples, prototypes and tests. unwrap keeps the code short, and a failing unwrap in a test is the failure you want.
  • You know more than the compiler. "127.0.0.1".parse::<IpAddr>().expect("hardcoded IP is valid") cannot fail; document why.
  • A broken contract. If a caller passes a value that violates the documented precondition, that is a bug in the caller, and panicking points at it. Standard library indexing does this.
  • Bad state you cannot recover from, such as a corrupted invariant.

When the failure is expected (bad user input, a network timeout, a parse error), return Result.

Let types carry the validation

Instead of checking a value in every function, check it once in a constructor and make the type impossible to build otherwise. Then functions that take the type need no checks.

pub struct Guess {
    value: i32, // private: only new() can set it
}

impl Guess {
    pub fn new(value: i32) -> Guess {
        if !(1..=100).contains(&value) {
            panic!("Guess must be between 1 and 100, got {value}.");
        }
        Guess { value }
    }
    pub fn value(&self) -> i32 { self.value }
}

fn main() {
    println!("{}", Guess::new(42).value());
}

6. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
fn half(n: &str) -> Option<i32> {
    let x: i32 = n.parse()?;
    Some(x / 2)
}
fn main() {}

parse returns a Result, but the function returns Option. ? does not convert between them; write n.parse().ok()?.

Q2 Does this compile?
fn half(n: &str) -> Result<i32, std::num::ParseIntError> {
    let x: i32 = n.parse()?;
    Ok(x / 2)
}
fn main() { println!("{:?}", half("8")); }

The error type of parse::<i32> is ParseIntError, the same as the function returns. Prints Ok(4).

Q3 Does this compile?
fn main() {
    let n: i32 = "5".parse()?;
    println!("{n}");
}

main returns (), so ? has nowhere to return the error to. Make main return Result<(), Box<dyn Error>>.

Q4 Does this compile?
use std::error::Error;
fn run() -> Result<u8, Box<dyn Error>> {
    let a: u8 = "7".parse()?;
    let f = std::fs::read_to_string("/nonexistent")?;
    Ok(a + f.len() as u8)
}
fn main() { println!("{}", run().is_err()); }

Both ParseIntError and io::Error convert into Box<dyn Error> through From, so ? accepts both.
