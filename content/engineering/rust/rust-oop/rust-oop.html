Rust OOP Features

Is Rust object-oriented? It has objects (structs with methods), encapsulation (privacy), and polymorphism (traits), but no inheritance. This chapter shows how to get the benefits of OOP with trait objects, what they cost, and when encoding states as types works better than the classic patterns.

Step through it

A Box<dyn Draw> is two words: a data pointer and a vtable pointer. The vtable is chosen when the box is created and tells each call which draw to run.

1. Characteristics of object-oriented languages

OOP ideaIn Rust
Objects: data plus behaviourStructs and enums with impl blocks.
Encapsulation: hide the implementationFields and functions are private by default; expose a pub API.
Inheritance: reuse a parent's codeNot supported. Use default trait methods for reuse.
Polymorphism: one interface, many typesGenerics with trait bounds (static) or trait objects (dynamic).
pub struct AveragedCollection {
    list: Vec<i32>,   // private: callers cannot desynchronize list and average
    average: f64,
}

impl AveragedCollection {
    pub fn new() -> Self { Self { list: vec![], average: 0.0 } }
    pub fn add(&mut self, value: i32) {
        self.list.push(value);
        self.update_average();
    }
    pub fn remove(&mut self) -> Option<i32> {
        let result = self.list.pop();
        if result.is_some() { self.update_average(); }
        result
    }
    pub fn average(&self) -> f64 { self.average }
    fn update_average(&mut self) {
        let total: i32 = self.list.iter().sum();
        self.average = if self.list.is_empty() { 0.0 } else { total as f64 / self.list.len() as f64 };
    }
}

fn main() {
    let mut c = AveragedCollection::new();
    c.add(2); c.add(4);
    println!("{}", c.average()); // 3
}

Because list is private, the Vec could later become a HashSet without breaking callers. Inheritance is left out on purpose: it tends to share more code than intended, and subclasses inherit methods that may not make sense for them. Rust prefers composition and traits.

2. Trait objects for values of different types

A GUI library wants a list of components to draw, including types its users will write later. A generic Vec<T> holds one type; an enum is closed. A trait object, dyn Draw behind a pointer, means "some type that implements Draw, decided at run time".

pub trait Draw {
    fn draw(&self);
}

pub struct Screen {
    pub components: Vec<Box<dyn Draw>>,
}

impl Screen {
    pub fn run(&self) {
        for component in self.components.iter() {
            component.draw();
        }
    }
}

pub struct Button { pub width: u32, pub height: u32, pub label: String }
impl Draw for Button {
    fn draw(&self) { println!("button {} ({}x{})", self.label, self.width, self.height); }
}

// written by a user of the library
struct SelectBox { width: u32, options: Vec<String> }
impl Draw for SelectBox {
    fn draw(&self) { println!("select {} wide: {:?}", self.width, self.options); }
}

fn main() {
    let screen = Screen {
        components: vec![
            Box::new(SelectBox { width: 75, options: vec!["Yes".into(), "Maybe".into(), "No".into()] }),
            Box::new(Button { width: 50, height: 10, label: String::from("OK") }),
        ],
    };
    screen.run();
}

This is duck typing, checked at compile time: Screen does not care what a component is, only that it can draw. Putting a String in the list is a compile error, because String does not implement Draw.

does not compile
pub trait Draw { fn draw(&self); }
pub struct Screen { pub components: Vec<Box<dyn Draw>> }

fn main() {
    let screen = Screen {
        components: vec![Box::new(String::from("Hi"))], // error[E0277]: the trait bound `String: Draw` is not satisfied
    };
}

3. Static versus dynamic dispatch

Generics: T: DrawTrait objects: dyn Draw
Dispatchstatic: the call target is known at compile timedynamic: looked up in a vtable at run time (Fig 1)
Mixed types in one collectionnoyes
Inlining and optimizationyesblocked across the call
Code sizeone copy per type (monomorphization)one copy
Pointerany, or by valuealways behind &, Box, Rc, ...

Prefer generics by default. Use dyn when you need heterogeneous collections, want smaller binaries or faster builds, or need to choose an implementation at run time, such as a plugin or a strategy read from config.

Dyn compatibility

Only some traits can be made into trait objects (formerly called "object safe"). Roughly, every method must be callable without knowing the concrete type:

  • no method returns Self by value, since its size is unknown;
  • no method has generic type parameters, since they cannot be listed in a finite vtable;
  • the trait does not require Self: Sized.

Methods that break the rules can opt out with where Self: Sized; they are then unavailable on the trait object, but the rest of the trait works. Clone is the classic non-compatible trait, because clone returns Self.

does not compile
trait Shape { fn duplicate(&self) -> Self; }

fn main() {
    let _v: Vec<Box<dyn Shape>> = Vec::new(); // error[E0038]: the trait `Shape` is not dyn compatible
}

4. The state pattern with trait objects

A blog post moves through draft, pending review and published. Only published posts show their content. With the state pattern, each state is a type implementing a State trait, and the post delegates to whichever state it is in.

pub struct Post {
    state: Option<Box<dyn State>>,
    content: String,
}

impl Post {
    pub fn new() -> Post {
        Post { state: Some(Box::new(Draft {})), content: String::new() }
    }
    pub fn add_text(&mut self, text: &str) { self.content.push_str(text); }
    pub fn content(&self) -> &str {
        self.state.as_ref().unwrap().content(self)
    }
    pub fn request_review(&mut self) {
        if let Some(s) = self.state.take() { self.state = Some(s.request_review()) }
    }
    pub fn approve(&mut self) {
        if let Some(s) = self.state.take() { self.state = Some(s.approve()) }
    }
}

trait State {
    fn request_review(self: Box<Self>) -> Box<dyn State>;  // consumes the old state
    fn approve(self: Box<Self>) -> Box<dyn State>;
    fn content<'a>(&self, _post: &'a Post) -> &'a str { "" } // default: hide content
}

struct Draft {}
struct PendingReview {}
struct Published {}

impl State for Draft {
    fn request_review(self: Box<Self>) -> Box<dyn State> { Box::new(PendingReview {}) }
    fn approve(self: Box<Self>) -> Box<dyn State> { self }
}
impl State for PendingReview {
    fn request_review(self: Box<Self>) -> Box<dyn State> { self }
    fn approve(self: Box<Self>) -> Box<dyn State> { Box::new(Published {}) }
}
impl State for Published {
    fn request_review(self: Box<Self>) -> Box<dyn State> { self }
    fn approve(self: Box<Self>) -> Box<dyn State> { self }
    fn content<'a>(&self, post: &'a Post) -> &'a str { &post.content }
}

fn main() {
    let mut post = Post::new();
    post.add_text("I ate a salad for lunch today");
    assert_eq!("", post.content());
    post.request_review();
    assert_eq!("", post.content());
    post.approve();
    assert_eq!("I ate a salad for lunch today", post.content());
    println!("published: {}", post.content());
}

self: Box<Self> means the method takes ownership of the boxed state, so the old state cannot be used after a transition. Option::take moves the state out of the field and leaves None for a moment, because Rust does not allow a field to be empty otherwise.

It works, and adding a state touches only that state. But invalid calls, like approve on a draft, are silently ignored at run time, and the states repeat the same delegation boilerplate.

5. Encoding states as types

Rust offers another option: make each state its own type, and make transitions consume one type and return another. Invalid transitions then do not compile, and a draft has no content method at all.

pub struct Post { content: String }
pub struct DraftPost { content: String }
pub struct PendingReviewPost { content: String }

impl Post {
    pub fn new() -> DraftPost { DraftPost { content: String::new() } }
    pub fn content(&self) -> &str { &self.content }
}

impl DraftPost {
    pub fn add_text(&mut self, text: &str) { self.content.push_str(text); }
    pub fn request_review(self) -> PendingReviewPost {
        PendingReviewPost { content: self.content }
    }
}

impl PendingReviewPost {
    pub fn approve(self) -> Post { Post { content: self.content } }
}

fn main() {
    let mut post = Post::new();
    post.add_text("I ate a salad for lunch today");
    let post = post.request_review();  // shadowing: a new type each step
    let post = post.approve();
    assert_eq!("I ate a salad for lunch today", post.content());
    println!("{}", post.content());
}
Trait-object statesType states
Invalid transitionignored at run timecompile error
Reading a draftreturns ""method does not exist
Caller codeone variable, mutatedrebinding with let
Add a stateone new type, others unchangedmay change signatures
Store posts of mixed stateseasy: one typeneeds an enum

Object-oriented patterns are a tool, not a goal. Rust's ownership and types often let you move whole classes of bugs from run time to compile time.

6. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
trait Speak { fn hi(&self) -> String; }
struct A; struct B;
impl Speak for A { fn hi(&self) -> String { "a".into() } }
impl Speak for B { fn hi(&self) -> String { "b".into() } }
fn main() {
    let v: Vec<Box<dyn Speak>> = vec![Box::new(A), Box::new(B)];
    for s in &v { println!("{}", s.hi()); }
}

Both types implement Speak, so both box into dyn Speak.

Q2 Does this compile?
fn main() {
    let v: Vec<Box<dyn Clone>> = Vec::new();
}

Clone is not dyn compatible: clone returns Self, whose size is unknown behind dyn.

Q3 Does this compile?
trait Speak { fn hi(&self) -> String; }
struct A;
impl Speak for A { fn hi(&self) -> String { "a".into() } }
fn main() {
    let x: dyn Speak = A;
}

dyn Speak has no size known at compile time, so it cannot live in a local variable. Put it behind a pointer: Box<dyn Speak> or &dyn Speak.

Q4 Does this compile?
trait Shape {
    fn area(&self) -> f64;
    fn scaled(&self, k: f64) -> Self where Self: Sized;
}
fn total(v: &[Box<dyn Shape>]) -> f64 { v.iter().map(|s| s.area()).sum() }
fn main() {}

where Self: Sized excludes scaled from the vtable, so the rest of the trait stays dyn compatible.
