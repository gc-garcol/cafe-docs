Rust Async and Await

Threads are good when work is CPU-bound. When most of the time is spent waiting (network, disk, timers), thousands of OS threads are wasteful. Async lets one thread juggle many tasks: a Future is a value that will be ready later, .await pauses a task until it is, and a runtime decides what to run next.

#rust#async#await#futures

Step through it

Calling an async fn runs nothing. The runtime calls poll; each .await is a point where the future can return Pending and be resumed later, keeping its local variables inside the future.

1. Parallelism, concurrency and futures

Concurrency is making progress on several tasks by switching between them. Parallelism is running several tasks at the same instant on different cores. Threads give both; async mainly gives concurrency, often on few threads. A runtime may spread tasks across cores too.

A future is a value that may not be ready yet. async fn and async blocks return futures, and .await waits for one. Rust futures are lazy: like iterators, they do nothing until something polls them. That something is an executor, provided by a runtime crate rather than the standard library. The book uses its own trpl crate, a thin layer over Tokio.

$ cargo add trpl          # the book's helper crate (re-exports Tokio and futures)
$ cargo add tokio --features full   # what you would use in a real project

2. async fn and .await

use trpl::Html;

async fn page_title(url: &str) -> Option<String> {
    let text = trpl::get(url).await.text().await;   // await is postfix: chains nicely
    Html::parse(&text)
        .select_first("title")
        .map(|title| title.inner_html())
}

fn main() {
    let args: Vec<String> = std::env::args().collect();
    trpl::block_on(async {                           // main cannot be async: start a runtime
        let url = &args[1];
        match page_title(url).await {
            Some(title) => println!("The title for {url} was {title}"),
            None => println!("{url} had no title"),
        }
    })
}

The compiler turns async fn page_title(url: &str) -> Option<String> into roughly fn page_title(url: &str) -> impl Future<Output = Option<String>>, and the body into a state machine with one state per .await (Fig 1). main itself cannot be async: something has to run the outermost future. With Tokio you write #[tokio::main] async fn main(), a macro that does the same.

Not calling .await is a common mistake. The future is built and dropped, nothing happens, and the compiler warns that futures "do nothing unless you .await or poll them".

does not compile
async fn answer() -> u32 { 42 }

fn main() {
    let n: u32 = answer(); // error[E0308]: expected `u32`, found future
}

3. Racing futures

use trpl::Either;

fn main() {
    let args: Vec<String> = std::env::args().collect();
    trpl::block_on(async {
        let title_fut_1 = page_title(&args[1]);
        let title_fut_2 = page_title(&args[2]);

        let (url, maybe_title) = match trpl::select(title_fut_1, title_fut_2).await {
            Either::Left(left) => left,      // whichever finishes first wins
            Either::Right(right) => right,   // the other one is dropped, i.e. cancelled
        };
        println!("{url} returned first: {maybe_title:?}");
    })
}

Dropping a future cancels it. There is no separate cancellation API: a future that is no longer polled simply stops at its last .await.

4. Concurrency with tasks and join

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let handle = trpl::spawn_task(async {          // like thread::spawn, but a task
            for i in 1..10 {
                println!("hi number {i} from the first task!");
                trpl::sleep(Duration::from_millis(500)).await;
            }
        });

        for i in 1..5 {
            println!("hi number {i} from the second task!");
            trpl::sleep(Duration::from_millis(500)).await;
        }
        handle.await.unwrap();                         // like join()
    });
}

Spawning is not required for concurrency. trpl::join(fut1, fut2).await polls both futures in turn on the current task and waits for both; join! and join_all take more. The order in which join polls is fair and deterministic, unlike OS thread scheduling.

Message passing

use std::time::Duration;

fn main() {
    trpl::block_on(async {
        let (tx, mut rx) = trpl::channel();

        let tx_fut = async move {          // move: tx is dropped when this block ends,
            for val in ["hi", "from", "the", "future"] {
                tx.send(val.to_string()).unwrap();
                trpl::sleep(Duration::from_millis(500)).await;
            }
        };                                 // ...which closes the channel

        let rx_fut = async {
            while let Some(value) = rx.recv().await {
                println!("received '{value}'");
            }
        };

        trpl::join(tx_fut, rx_fut).await;
    });
}

Without async move, tx would live until the end of the outer block, the channel would never close, and the while let loop would wait forever. The same ownership reasoning as with threads applies.

5. Yielding and timeouts

A task only gives up the thread at an .await. A long computation with no awaits starves every other task on that thread. Insert trpl::yield_now().await (Tokio: tokio::task::yield_now) in long loops, or move CPU-heavy work to a thread with spawn_blocking.

Because futures compose, a timeout is just another future. Race the work against a sleep:

use std::{future::Future, time::Duration};
use trpl::Either;

async fn timeout<F: Future>(future_to_try: F, max_time: Duration) -> Result<F::Output, Duration> {
    match trpl::select(future_to_try, trpl::sleep(max_time)).await {
        Either::Left(output) => Ok(output),
        Either::Right(_) => Err(max_time),
    }
}

6. Streams

A stream is an async iterator: a sequence of values that arrive over time. rx.recv() in a loop is a stream in all but name. The StreamExt trait adds the familiar adapters, map, filter, timeout, throttle, merge, each returning another stream.

use trpl::StreamExt;

fn main() {
    trpl::block_on(async {
        let values = 1..101;
        let iter = values.map(|n| n * 2);
        let stream = trpl::stream_from_iter(iter);

        let mut filtered = stream.filter(|value| value % 3 == 0 || value % 5 == 0);
        while let Some(value) = filtered.next().await {
            println!("The value was: {value}");
        }
    });
}

7. The traits underneath: Future, Pin, Stream

use std::pin::Pin;
use std::task::{Context, Poll};

pub trait MyFuture {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
}

pub enum MyPoll<T> { Ready(T), Pending }

fn main() {}

poll either returns Ready(value) or Pending. When it returns Pending, the future has arranged for cx.waker() to be called once progress is possible, and the executor polls it again then. .await compiles to a loop around poll that yields to the executor on Pending.

Pin and Unpin

The state machine of an async fn may hold a reference to one of its own fields, for example a borrow of body that lives across an .await. If the future were moved in memory, that internal pointer would dangle. Pin<&mut F> is a pointer that promises the value behind it will not move again. Most types have no self-references and implement the auto trait Unpin, meaning pinning does not restrict them.

In practice you meet Pin when storing futures in a collection, for example Vec<Pin<Box<dyn Future<Output = ()>>>> passed to join_all. Box::pin(fut) or the pin! macro creates one.

use std::future::Future;
use std::pin::{pin, Pin};
use std::sync::Arc;
use std::task::{Context, Poll, Wake, Waker};

// A minimal executor, std only: poll until Ready, park while Pending.
struct ThreadWaker(std::thread::Thread);
impl Wake for ThreadWaker {
    fn wake(self: Arc<Self>) { self.0.unpark(); }
}

fn block_on<F: Future>(fut: F) -> F::Output {
    let mut fut = pin!(fut);
    let waker = Waker::from(Arc::new(ThreadWaker(std::thread::current())));
    let mut cx = Context::from_waker(&waker);
    loop {
        match fut.as_mut().poll(&mut cx) {
            Poll::Ready(v) => return v,
            Poll::Pending => std::thread::park(),
        }
    }
}

async fn add(a: u32, b: u32) -> u32 { a + b }

fn main() {
    let futures: Vec<Pin<Box<dyn Future<Output = u32>>>> =
        vec![Box::pin(add(1, 2)), Box::pin(async { 40 })];
    let total = block_on(async {
        let mut sum = 0;
        for f in futures { sum += f.await; }
        sum
    });
    println!("{total}"); // 43
}

Stream looks like Future crossed with Iterator: poll_next(self: Pin<&mut Self>, cx) -> Poll<Option<Item>>. StreamExt::next wraps it in a future you can await.

8. Threads, tasks and futures together

WorkReach for
Many waits on I/O: servers, crawlers, chatasync tasks on a runtime
CPU-heavy computation on all coresthreads, or a pool such as rayon
A blocking library call inside async codespawn_blocking or a dedicated thread
A few long-lived background jobseither; threads are simpler

They mix well: a thread can send on an async channel and an async task can await the result. Threads are the unit of the OS, tasks are the unit of the runtime, and futures are the unit of work inside a task.

9. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
async fn n() -> u8 { 1 }
fn main() {
    let x: u8 = n();
}

Calling an async fn returns a future, not the value. It must be awaited inside async code or run by an executor.

Q2 Does this compile?
async fn n() -> u8 { 1 }
async fn twice() -> u8 { n().await + n().await }
fn main() { let _f = twice(); }

It compiles, but nothing runs: _f is a future that is never polled.

Q3 Does this compile?
fn main() {
    let x = 5;
    let y = x.await;
}

.await is only allowed inside async functions and blocks, and only on futures.

Q4 Does this compile?
use std::future::Future;
fn make() -> impl Future<Output = String> {
    async { String::from("later") }
}
fn main() { let _f = make(); }

An async block is an anonymous type implementing Future, so it can be returned as impl Future.
