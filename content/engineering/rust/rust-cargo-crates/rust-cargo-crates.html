Rust Cargo and Crates.io

Cargo does more than build and run. It has profiles for development and release builds, turns doc comments into a website, publishes libraries to crates.io, manages several packages as one workspace, and installs command-line tools. This page covers the parts you meet once a project leaves your laptop.

1. Release profiles

A profile is a set of compiler settings. cargo build uses dev; cargo build --release uses release. Override any default in Cargo.toml:

[profile.dev]
opt-level = 0        # default: compile fast, run slow
debug = true

[profile.release]
opt-level = 3        # default: compile slow, run fast
lto = "thin"         # link-time optimization across crates
codegen-units = 1    # better optimization, slower build
panic = "abort"      # no unwinding: smaller binary

[profile.dev.package."*"]
opt-level = 2        # optimize dependencies even in dev builds
SettingdevreleaseEffect
opt-level030 to 3, plus "s" and "z" for size
debugtruefalsedebug info for debuggers and backtraces
overflow-checkstruefalsepanic on integer overflow
incrementaltruefalsereuse work between builds

2. Documentation comments

/// documents the item that follows, in Markdown. //! documents the enclosing item, usually the crate at the top of lib.rs. cargo doc --open builds HTML for your crate and all its dependencies.

//! # My Crate
//!
//! `my_crate` is a collection of utilities to make performing certain
//! calculations more convenient.

/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let arg = 5;
/// let answer = my_crate::add_one(arg);
///
/// assert_eq!(6, answer);
/// ```
pub fn add_one(x: i32) -> i32 {
    x + 1
}

Common section headings:

HeadingDescribe
# ExamplesHow to call it. These blocks run as tests with cargo test.
# PanicsInputs that make the function panic.
# ErrorsFor a Result: which errors and when.
# SafetyFor an unsafe fn: the invariants the caller must uphold.

3. A convenient public API with pub use

The module tree that makes sense to you may be deep. Users should not need my_crate::kinds::PrimaryColor and my_crate::utils::mix. Re-export the important items at the top level; the docs list them on the front page under "Re-exports".

pub use self::kinds::PrimaryColor;
pub use self::kinds::SecondaryColor;
pub use self::utils::mix;

pub mod kinds {
    #[derive(Debug)]
    pub enum PrimaryColor { Red, Yellow, Blue }
    #[derive(Debug)]
    pub enum SecondaryColor { Orange, Green, Purple }
}

pub mod utils {
    use crate::kinds::*;
    pub fn mix(_c1: PrimaryColor, _c2: PrimaryColor) -> SecondaryColor {
        SecondaryColor::Orange
    }
}

fn main() {
    // users write the short paths
    println!("{:?}", mix(PrimaryColor::Red, PrimaryColor::Yellow));
}

Internal organization and public API can then change independently. Moving mix to another module is not a breaking change as long as the re-export stays.

4. Publishing to crates.io

$ cargo login                 # paste the API token from crates.io/me (stored in ~/.cargo/credentials.toml)

# Cargo.toml
[package]
name = "guessing_game"        # must be unique on crates.io
version = "0.1.0"
edition = "2024"
description = "A fun game where you guess what number the computer has chosen."
license = "MIT OR Apache-2.0" # an SPDX expression
repository = "https://github.com/example/guessing_game"

$ cargo publish --dry-run     # package and verify without uploading
$ cargo publish

A publish is permanent. A version can never be overwritten or deleted, so that every build that depends on it keeps working. Keep the API token secret; anyone with it can publish as you.

Versions and yanking

Cargo uses Semantic Versioning. rand = "0.8.5" means "^0.8.5": any compatible version, here >=0.8.5, <0.9.0. Bump the major version (or the minor one below 1.0) for breaking changes. Cargo.lock records the exact versions used, so builds are reproducible until you run cargo update.

$ cargo yank --vers 1.0.1         # new projects cannot pick 1.0.1; existing lock files still can
$ cargo yank --vers 1.0.1 --undo

Yanking does not delete code. If you published a secret, revoke the secret; yanking does not hide it.

5. Cargo workspaces

A workspace is a set of packages developed together. They share one Cargo.lock, so every member uses the same version of each dependency, and one target/ directory, so shared dependencies compile once.

add/
├── Cargo.toml          # [workspace] members = ["adder", "add_one"]
├── Cargo.lock
├── target/
├── adder/              # binary crate
│   ├── Cargo.toml      # [dependencies] add_one = { path = "../add_one" }
│   └── src/main.rs
└── add_one/            # library crate
    ├── Cargo.toml
    └── src/lib.rs
# add/Cargo.toml
[workspace]
resolver = "3"
members = ["adder", "add_one"]

$ cargo new add_one --lib     # inside the workspace: added to members automatically
$ cargo build                 # builds every member
$ cargo run -p adder          # pick a package
$ cargo test -p add_one

Path dependencies between members are explicit: adder must list add_one to use it. External dependencies must be listed in each member that uses them, but they resolve to one version. Each member is published separately.

6. cargo install and custom commands

$ cargo install ripgrep       # build a binary crate from crates.io into ~/.cargo/bin
$ rg --help

# any binary named cargo-something on PATH becomes a subcommand
$ cargo install cargo-edit
$ cargo --list

cargo install is for tools for developers, not a system package manager. Only crates with a binary target can be installed, and ~/.cargo/bin must be on your PATH.

CommandDoes
cargo checktype-check without producing a binary; fastest feedback
cargo clippylints for common mistakes and non-idiomatic code
cargo fmtformat the code with rustfmt
cargo add / removeedit dependencies in Cargo.toml
cargo treeshow the dependency graph
cargo doc --openbuild and open the documentation

7. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
mod shapes {
    pub mod round { pub struct Circle; }
}
pub use shapes::round::Circle;
fn main() { let _c = Circle; }

The re-export makes Circle available at the crate root, so the short path works.

Q2 Does this compile?
mod shapes {
    mod round { pub struct Circle; }
}
pub use shapes::round::Circle;
fn main() {}

round is private to shapes, so the root module cannot reach into it. A re-export cannot expose something the re-exporting module cannot see.

Q3 Does this compile?
/// Doubles a number.
///
/// # Panics
/// Never.
pub fn double(x: i32) -> i32 { x * 2 }
fn main() { println!("{}", double(2)); }

Doc comments are ordinary attributes on the item. They compile as long as they come directly before an item.
