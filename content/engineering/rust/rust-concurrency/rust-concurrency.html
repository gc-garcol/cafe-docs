Rust Fearless Concurrency

Concurrency bugs are usually found in production, under load, and are hard to reproduce. Rust moves most of them to compile time. The same ownership and type rules that stop dangling pointers also stop data races, which is why the book calls it fearless concurrency.

#rust#concurrency#threads#channels

Step through it

Arc gives each thread an owner; Mutex makes sure only one of them touches the counter at a time. The MutexGuard unlocks when it is dropped.

1. Creating threads

thread::spawn runs a closure on a new OS thread (a 1:1 model) and returns a JoinHandle. When main returns, the process ends and all other threads are stopped, finished or not. join blocks until a thread finishes and returns its result.

use std::thread;
use std::time::Duration;

fn main() {
    let handle = thread::spawn(|| {
        for i in 1..5 {
            println!("hi number {i} from the spawned thread!");
            thread::sleep(Duration::from_millis(1));
        }
        42
    });

    for i in 1..3 {
        println!("hi number {i} from the main thread!");
        thread::sleep(Duration::from_millis(1));
    }

    let answer = handle.join().unwrap(); // Err if the thread panicked
    println!("thread returned {answer}");
}

The interleaving of the two loops changes from run to run; only the scheduler decides.

The thread might run after main has dropped v. Adding move transfers ownership into the thread, and then the drop(v) in main is the error instead: use after move. Either way the compiler catches it.

Scoped threads

thread::scope guarantees that every thread spawned inside it is joined before it returns. The threads may then borrow local data without move or Arc.

use std::thread;

fn main() {
    let mut data = vec![1, 2, 3, 4];
    let (left, right) = data.split_at_mut(2);
    thread::scope(|s| {
        s.spawn(|| left.iter_mut().for_each(|x| *x *= 10));
        s.spawn(|| right.iter_mut().for_each(|x| *x += 1));
    }); // both threads joined here
    println!("{data:?}"); // [10, 20, 4, 5]
}

2. Message passing with channels

Do not communicate by sharing memory; instead, share memory by communicating. (From the Go documentation.)

mpsc::channel returns a transmitter and a receiver: multiple producer, single consumer. Sending moves the value into the channel, so the sender cannot touch it afterwards.

use std::sync::mpsc;
use std::thread;
use std::time::Duration;

fn main() {
    let (tx, rx) = mpsc::channel();
    let tx2 = tx.clone();                    // a second producer

    thread::spawn(move || {
        for val in ["hi", "from", "the", "thread"] {
            tx.send(val.to_string()).unwrap();
            thread::sleep(Duration::from_millis(5));
        }
    });
    thread::spawn(move || {
        for val in ["more", "messages"] {
            tx2.send(val.to_string()).unwrap();
            thread::sleep(Duration::from_millis(5));
        }
    });

    for received in rx {                     // ends when every tx is dropped
        println!("Got: {received}");
    }
}
does not compile
use std::sync::mpsc;
use std::thread;
fn main() {
    let (tx, rx) = mpsc::channel();
    thread::spawn(move || {
        let val = String::from("hi");
        tx.send(val).unwrap();
        println!("val is {val}"); // error[E0382]: borrow of moved value: `val`
    });
    println!("{}", rx.recv().unwrap());
}
Receiver methodBehaviour
recv()Block until a value arrives. Err once all senders are gone.
try_recv()Return immediately: a value, Empty or Disconnected.
recv_timeout(d)Block for at most d.

mpsc::channel is unbounded. mpsc::sync_channel(n) has a capacity of n, and send blocks when it is full, which gives back-pressure.

3. Shared state with Mutex<T>

A mutex allows one thread at a time to access data. In many languages the lock and the data are separate, and nothing stops you from touching the data without the lock. In Rust the data lives inside the Mutex, and lock() returns a MutexGuard, the only way in. The guard unlocks in its Drop, so you cannot forget.

use std::sync::Mutex;

fn main() {
    let m = Mutex::new(5);
    {
        let mut num = m.lock().unwrap(); // Err if another thread panicked while holding it
        *num = 6;
    }                                    // unlocked here
    println!("m = {m:?}");
}

To share the mutex between threads it needs several owners. Rc does not work: its count is not updated atomically, so it is not Send. Arc, atomically reference counted, is the thread-safe version (Fig 1):

does not compile
use std::rc::Rc;
use std::sync::Mutex;
use std::thread;
fn main() {
    let counter = Rc::new(Mutex::new(0));
    let c = Rc::clone(&counter);
    thread::spawn(move || { // error[E0277]: `Rc<Mutex<i32>>` cannot be sent between threads safely
        *c.lock().unwrap() += 1;
    });
}
use std::sync::{Arc, Mutex};
use std::thread;

fn main() {
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];
    for _ in 0..10 {
        let counter = Arc::clone(&counter);
        handles.push(thread::spawn(move || {
            *counter.lock().unwrap() += 1;
        }));
    }
    for h in handles { h.join().unwrap(); }
    println!("Result: {}", *counter.lock().unwrap()); // 10
}

Mutex<T> provides interior mutability just like RefCell<T>, and Arc<Mutex<T>> mirrors Rc<RefCell<T>>. It shares the same weakness too: the compiler cannot stop a deadlock, where two threads each hold one lock and wait for the other. Acquire locks in a consistent order, and hold them for as short a time as possible.

ToolUse for
Mutex<T>exclusive access, short critical sections

use std::sync::atomic::{AtomicUsize, Ordering};
use std::thread;

static HITS: AtomicUsize = AtomicUsize::new(0);

fn main() {
    thread::scope(|s| {
        for _ in 0..4 {
            s.spawn(|| for _ in 0..1000 { HITS.fetch_add(1, Ordering::Relaxed); });
        }
    });
    println!("{}", HITS.load(Ordering::Relaxed)); // 4000
}

4. Send and Sync

The language itself knows almost nothing about concurrency; threads, channels and mutexes are library code. What makes them safe are two marker traits, which have no methods:

TraitMeansNot implemented by
SendOwnership of a value can move to another thread.Rc<T>, raw pointers
SyncA &T can be shared between threads. T: Sync exactly when &T: Send.Rc<T>, RefCell<T>, Cell<T>

Both are auto traits: a type made only of Send parts is Send, and the same for Sync. thread::spawn requires its closure to be Send + 'static, which is how the Rc example above was rejected. Implementing them by hand requires unsafe, because the compiler can no longer check the promise.

A data race needs shared, mutable, unsynchronized access. Ownership removes "shared and mutable"; Send and Sync remove "unsynchronized".

5. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
use std::thread;
fn main() {
    let s = String::from("hi");
    let h = thread::spawn(move || println!("{s}"));
    h.join().unwrap();
}

move gives the thread ownership of s, and String is Send.

Q2 Does this compile?
use std::cell::RefCell;
use std::sync::Arc;
use std::thread;
fn main() {
    let a = Arc::new(RefCell::new(0));
    let b = Arc::clone(&a);
    thread::spawn(move || *b.borrow_mut() += 1);
}

RefCell is not Sync, so Arc<RefCell<i32>> is not Send. Use Arc<Mutex<i32>>.

Q3 Does this compile?
use std::thread;
fn main() {
    let v = vec![1, 2, 3];
    thread::scope(|s| {
        s.spawn(|| println!("{v:?}"));
    });
    println!("{}", v.len());
}

Scoped threads are joined before scope returns, so they may borrow v without move.

Q4 Does this compile?
use std::sync::mpsc;
fn main() {
    let (tx, rx) = mpsc::channel();
    let v = vec![1];
    tx.send(v).unwrap();
    println!("{:?} {:?}", v, rx.recv());
}

send takes ownership of v. After sending, only the receiver may use it.
