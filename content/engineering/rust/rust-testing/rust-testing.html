Rust Testing

The type system proves a lot, but not that add_two(2) returns 4. Tests check behaviour. Rust has testing built in: mark a function with #[test], run cargo test, and Cargo builds a test binary that runs every test in parallel and reports the results.

#rust#testing#unit tests#integration tests

1. Writing a test

A test is a function annotated with #[test]. It passes if it returns without panicking. cargo new adder --lib generates this template:

pub fn add(left: u64, right: u64) -> u64 {
    left + right
}

#[cfg(test)]
mod tests {
    use super::*;          // bring the parent module's items into scope

    #[test]
    fn it_works() {
        let result = add(2, 2);
        assert_eq!(result, 4);
    }
}
$ cargo test
running 1 test
test tests::it_works ... ok

test result: ok. 1 passed; 0 failed; 0 ignored; 0 measured; 0 filtered out

   Doc-tests adder
running 0 tests

#[cfg(test)] compiles the module only for cargo test, so test code and test-only dependencies stay out of the release binary.

2. Assertions

assert_eq! and assert_ne! need PartialEq and Debug on the compared types; #[derive(PartialEq, Debug)] is usually enough. Any extra arguments are a format! message.

#[derive(Debug)]
struct Rectangle { width: u32, height: u32 }

impl Rectangle {
    fn can_hold(&self, other: &Rectangle) -> bool {
        self.width > other.width && self.height > other.height
    }
}

pub fn greeting(name: &str) -> String {
    format!("Hello {name}!")
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    fn larger_can_hold_smaller() {
        let larger = Rectangle { width: 8, height: 7 };
        let smaller = Rectangle { width: 5, height: 1 };
        assert!(larger.can_hold(&smaller));
        assert!(!smaller.can_hold(&larger));
    }

    #[test]
    fn greeting_contains_name() {
        let result = greeting("Carol");
        assert!(result.contains("Carol"), "greeting did not contain name, value was `{result}`");
    }
}

3. Checking panics and returning Result

#[should_panic] passes if the function panics. Add expected with a substring of the message, otherwise the test also passes when the code panics for an unrelated reason.

pub struct Guess { value: i32 }

impl Guess {
    pub fn new(value: i32) -> Guess {
        if value < 1 {
            panic!("Guess value must be greater than or equal to 1, got {value}.");
        } else if value > 100 {
            panic!("Guess value must be less than or equal to 100, got {value}.");
        }
        Guess { value }
    }
}

#[cfg(test)]
mod tests {
    use super::*;

    #[test]
    #[should_panic(expected = "less than or equal to 100")]
    fn greater_than_100() {
        Guess::new(200);
    }

    #[test]
    fn it_works() -> Result<(), String> {   // lets you use ? in the test
        let n: i32 = "4".parse().map_err(|e| format!("{e}"))?;
        if n + 0 == 4 { Ok(()) } else { Err(String::from("math broke")) }
    }
}

A test that returns Result fails on Err. You cannot combine it with #[should_panic]; to assert that an operation fails, use assert!(value.is_err()).

4. Controlling how tests run

Arguments before -- go to cargo test, arguments after go to the test binary.

CommandEffect
cargo testBuild and run every unit, integration and doc test.
cargo test addRun tests whose full name contains add.
cargo test -- --test-threads=1Run one at a time, for tests that share files, env vars or ports.
cargo test -- --show-outputShow println! output of passing tests too (captured by default).
cargo test -- --ignoredRun only tests marked #[ignore].
cargo test -- --include-ignoredRun everything.
cargo test --test integrationRun one integration test file.
cargo test --docRun only doc tests.

Tests run in parallel threads by default. Make them independent: each should create its own temporary files and state, so the order does not matter.

#[test]
#[ignore = "takes an hour"]
fn expensive_test() {
    // code that takes an hour to run
}

5. Unit tests and integration tests

Unit tests live next to the code, in a tests module inside each file. Because the module is a child, it can test private functions too. Rust leaves the debate about whether you should to you, but does not stop you.

pub fn add_two(a: u64) -> u64 { internal_adder(a, 2) }

fn internal_adder(left: u64, right: u64) -> u64 { left + right }

#[cfg(test)]
mod tests {
    use super::*;
    #[test]
    fn internal() {
        assert_eq!(internal_adder(2, 2), 4); // private, still testable
    }
}

Integration tests live in a tests/ directory next to src/. Each file is compiled as a separate crate that uses your library like any external user, through its public API only. No #[cfg(test)] is needed.

adder/
├── Cargo.toml
├── src/
│   └── lib.rs
└── tests/
    ├── common/
    │   └── mod.rs          # shared helpers, not a test crate itself
    └── integration_test.rs
// tests/integration_test.rs
use adder::add_two;

mod common;

#[test]
fn it_adds_two() {
    common::setup();
    assert_eq!(add_two(2), 4);
}

Shared helpers go in tests/common/mod.rs rather than tests/common.rs; the second form would be treated as a test file and show up in the output with zero tests. Binary-only crates (src/main.rs without src/lib.rs) cannot be integration-tested this way, which is another reason to keep logic in lib.rs.

6. Doc tests

Code blocks in /// documentation are compiled and run by cargo test. Examples in your docs therefore cannot go stale.

/// Adds one to the number given.
///
/// # Examples
///
/// ```
/// let answer = my_crate::add_one(5);
/// assert_eq!(6, answer);
/// ```
pub fn add_one(x: i32) -> i32 {
    x + 1
}

7. Check yourself

Read each snippet and decide whether the compiler accepts it. Every answer was checked with rustc (edition 2024).

Q1 Does this compile?
struct P { x: i32 }
fn main() {
    assert_eq!(P { x: 1 }, P { x: 1 });
}

assert_eq! needs PartialEq to compare and Debug to print. Derive both.

Q2 Does this compile?
#[derive(Debug, PartialEq)]
struct P { x: i32 }
fn main() {
    assert_eq!(P { x: 1 }, P { x: 1 }, "points differ");
}

With both traits derived, it compiles. The extra argument is a failure message.

Q3 Does this compile?
fn main() {
    let v: Vec<i32> = Vec::new();
    assert!(v.len(), "should be empty");
}

assert! needs a bool. v.len() is a usize; write assert!(v.is_empty()).
