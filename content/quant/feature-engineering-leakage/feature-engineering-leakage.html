Feature engineering and leakage

A feature is only useful if you could have computed it at the moment you trade. Most backtests that look too good fail this test somewhere: a full-sample average, a centered filter, a mis-dated release. Build features from the past only, and check that you did.

1. What a feature is allowed to know

  
At each decision time $t$ you know a set of facts: prices up to now, reports already published, your own positions. Call it the information set $\mathcal{F}_t$. A valid feature is any function of it:

  
$$x_t = f(\mathcal{F}_t), \qquad \mathcal{F}_s \subseteq \mathcal{F}_t \ \text{ for } s \le t$$

  
Leakage is any path by which $x_t$ depends on something outside $\mathcal{F}_t$. The label is allowed to look ahead, because that is what you predict. Features are not, and neither is anything you fit, select or tune using the period you score on.

  
For every number in a feature, ask: at what wall-clock time did I first know this?

  
Leaks rarely look like cheating. They hide in one-line conveniences: df.mean() over the whole column, rolling(center=True), fillna(method="bfill"), a join on the wrong date. The model then learns the leak, because the leak is the only real pattern in the data.






  
2. Four families of leaks

3. How each leak in the lab works

  
Full-sample z-score

  
Standardizing a price with the mean and standard deviation of the whole sample tells the model where the price will spend its time. "Buy below the full-sample mean" then wins by construction, because the path must come back to its own average. It is the quietest leak in the lab, a Sharpe ratio below 1 rather than 5, which is exactly why it survives code review. The fix is to use only the past, with an expanding or rolling window:

  
$$z_t^{\text{leak}} = \frac{P_t - \bar P_{1:T}}{s_{1:T}} \qquad\longrightarrow\qquad z_t = \frac{P_t - \bar P_{t-w+1:t}}{s_{t-w+1:t}}$$


  
Off-by-one alignment

  
A momentum feature over the last five returns, shifted one row the wrong way, includes the very return the position earns. It is the classic bug in a vectorized backtest: signal * returns where both columns are indexed by the same date. The position decided at the close of day $t$ must be multiplied by the return from $t$ to $t+1$:

  
$$\text{PnL}_{t+1} = \text{pos}_t \cdot r_{t+1}, \qquad \text{pos}_t = f(r_t, r_{t-1}, \dots) \quad\text{not}\quad f(r_{t+1}, r_t, \dots)$$


  
Centered moving average

  
A centered average, a Hodrick-Prescott filter or a two-sided wavelet smooths using points on both sides of $t$. Its slope at $t$ knows whether the next ten days go up. Every smoother used as a feature must be one-sided, such as a trailing average or an exponentially weighted average:

  
$$\text{EWMA}_t = \lambda\,\text{EWMA}_{t-1} + (1-\lambda)\,x_t$$


  
Feature selection on all data

  
Generate 200 random features and keep the one most correlated with next-day returns over the full sample. With $T$ days of noise, the best of $N$ correlations is roughly

  
$$\max_{n \le N} |\hat\rho_n| \;\approx\; \sqrt{\frac{2\ln N}{T}}$$

  
which is about 0.12 for $N = 200$ and $T = 750$: an impressive-looking IC that is pure selection. The honest version selects on the first half and is scored on the second half only. Both curves in Fig 1 cover that second half.


  
Release date vs reference date

  
A macro number "for day $t$" is often published days later, and the market moves when it is published. Joining it to prices on its reference date lets the strategy trade on news before it exists. Store two timestamps for every data point, the event time it describes and the knowledge time it became available, and join on knowledge time.






  
4. Point-in-time joins

  
The safe join attaches to each decision time the most recent value published strictly before it. In pandas that is an as-of merge on the release timestamp:

  
# prices: one row per decision time; macro: value, period, released_at
macro = macro.sort_values("released_at")
features = pd.merge_asof(
    prices.sort_values("decision_time"),
    macro[["released_at", "value"]],
    left_on="decision_time", right_on="released_at",
    direction="backward",            # only the past
    allow_exact_matches=False,        # released at 16:00 is not known at 16:00
)

  
    
    
  • Fundamentals are revised. Use point-in-time databases that keep the first-reported value and every revision with its date.
    • 
    
  • Universes must be as of each date. A stock list downloaded today contains only survivors, which quietly removes every company that went bankrupt.
    • 
    
  • Corporate actions such as splits and dividends are applied to history after the fact. Back-adjusted prices are fine for returns, but price levels and volume thresholds must use the raw values known then.
    • 
    
  • Time zones and closes. A European close at 17:30 CET is known before the US close. A "daily" bar for a US stock is not known at the start of the day it is labeled with.
    • 
  






  
5. Building features that generalize

  
Leak-free is necessary, not sufficient. Financial series drift, so a feature that means one thing in 2010 and another in 2020 is useless to a model trained across both. Most good transforms aim for stationarity: a stable distribution over time.

  

    
TransformFormulaWhy

    
      
Log return$r_t = \ln P_t - \ln P_{t-1}$Prices trend, returns roughly do not

      
Volatility scaling$r_t / \hat\sigma_{t-1}$Calm and wild periods become comparable

      
Rolling z-score$(x_t - \hat\mu_{t})/\hat\sigma_{t}$, past windowRemoves slow drift in level and scale

      
Cross-sectional rank$\text{rank}(x_{i,t}) / N_t$ across assetsUniform on $[0,1]$ every day, robust to outliers

      
Ratios and spreads$\text{price}/\text{earnings}$, $\ln P_A - \beta \ln P_B$Removes a common factor

      
Calendar and event flagsdays to expiry, earnings datesKnown in advance, so safe by design

    
  

  
Differencing makes a series stationary but throws away its memory: a return knows nothing about the price level. Fractional differencing keeps a dial between the two. With the backshift operator $B x_t = x_{t-1}$ and $0 \lt d \lt 1$:

  
$$(1-B)^d x_t = \sum_{k=0}^{\infty} w_k\, x_{t-k}, \qquad w_0 = 1, \quad w_k = -w_{k-1}\,\frac{d-k+1}{k}$$

  
$d = 0$ is the raw series and $d = 1$ the ordinary difference. Often a value around 0.3 to 0.5 already passes a unit-root test while keeping most of the correlation with the original level. The weights only use the past, so it is leak-free as long as the window is truncated causally.






  
6. Fit inside the fold

  
Any step that learns from data, such as a scaler, an imputer, PCA, a target encoder or a feature selector, is part of the model. It must be fit on the training window only, then applied to the test window. Wrapping it in a pipeline makes the mistake hard to make:

  
from sklearn.pipeline import make_pipeline
from sklearn.preprocessing import StandardScaler
from sklearn.decomposition import PCA
from sklearn.linear_model import Ridge
from sklearn.model_selection import TimeSeriesSplit, cross_val_score

model = make_pipeline(StandardScaler(), PCA(n_components=10), Ridge(alpha=1.0))
cv = TimeSeriesSplit(n_splits=5, gap=horizon)         # walk-forward with a purge gap
scores = cross_val_score(model, X, y, cv=cv)              # scaler and PCA refit per fold

  
Target encoding needs one more step: compute the encoding for each training row without that row's own label, for example out-of-fold, or the feature contains the answer.






  
7. How to catch a leak

  
    
    
  • Too good to be true. A daily strategy built from a few price features with a Sharpe ratio above 3, or an IC above 0.1, is a bug until proven otherwise.
    • 
    
  • The shift test. Lag every feature by one more period and rerun. A real signal decays a little. A leak collapses. Also try shifting features forward: if that helps a lot, your alignment is off.
    • 
    
  • Random labels. Shuffle the labels in blocks and retrain. Any remaining skill comes from the pipeline, not the data.
    • 
    
  • Feature importance. When one feature explains almost everything, read its code line by line.
    • 
    
  • Paper trading. Run the exact feature code live for a few weeks and compare with what the backtest computes for the same days. Any difference is a leak or a data revision.
    • 
  






  
8. Common mistakes

  
    
    
  • Filling gaps backward. bfill copies a future value into the past. Fill forward, or leave the gap and let the model handle it.
    • 
    
  • Dropping rows with missing future data at the end. If you drop the last $h$ rows because their labels are unknown, make sure features were not computed after the drop with a different window.
    • 
    
  • Normalizing labels with full-sample volatility. The label may use the future, but its scaling factor must not leak into features or thresholds.
    • 
    
  • Using today's index members. Survivorship bias inflates returns by a few percent a year in equity backtests.
    • 
    
  • Counting only the final model. Every feature you tried and dropped is a trial. See the selection effect in Fig 1.
    • 
  






  
9. Where it shows up

  
    
    
  • Alpha research: every signal pipeline, from simple momentum to gradient boosting on hundreds of features.
    • 
    
  • Risk models: covariance estimates and factor exposures must be as of the date they are used.
    • 
    
  • Backtests: see backtesting without look-ahead for the same discipline applied to trade execution.
    • 
    
  • Outside finance: churn models that use "account closed" flags, medical models that use tests ordered after a diagnosis, and fraud models trained on fields filled in by investigators. The pattern is always the same: information from after the decision.
