Data structures and algorithms for quants

Trading code lives on a few structures: an order book, a hash map from order ID to order, ring buffers between threads, and one-pass statistics over streams. Pick them by the operations you do most, and by the worst case, not only the average.

Try the machine first

A simulated stream of orders hits the bid side of a limit order book: new limit orders, cancels, and market sells that eat the best price. Four ways to store the price levels process exactly the same stream. Each counts its elementary steps: comparisons, element shifts, heap swaps or empty ticks scanned. Change how spread out the orders are and see which structure suffers.

Order spread is the average distance, in ticks, of a new limit order from the mid price.


  

  
Things to try. With a tight spread, everything costs a few steps per event and the tick array is cheapest. Spread orders far apart: the sorted array has more levels to shift on every cancel in the middle, and its cost grows with the book. Now raise market orders to 40%. The book drains faster than it refills, gaps of empty ticks open below the best price, and the tick array has to scan hundreds of them each time the best level is eaten. The heap pops stale entries, the tree barely notices. No structure wins everywhere, which is why real books add a bitmap to the tick array or cap the price band.






  
1. The numbers that matter

  
Big-O hides constants, but it is still the first filter. At the sizes trading systems see, the gap between classes is large:

  

    
Growth$n = 10^3$$n = 10^6$Typical operation

    
      
$O(1)$11Hash lookup, array index, ring buffer push

      
$O(\log n)$1020Heap push, tree insert, binary search

      
$O(n)$$10^3$$10^6$Scan, insert into the middle of an array

      
$O(n \log n)$$10^4$$2 \times 10^7$Sorting

      
$O(n^2)$$10^6$$10^{12}$All pairs, naive correlation matrix updates

    
  

  
Below that, memory decides. A cache miss to main memory costs around 100 ns, about as long as a few hundred simple instructions. A contiguous array that fits in cache often beats a pointer-based tree with a better Big-O. And in a trading system the tail matters more than the mean: one 50 µs pause during a burst costs more than a slightly slower average. Prefer structures with bounded worst cases and no allocation on the hot path.

  
Choose by the operation you do a million times a second, then by its worst case, then by its memory layout.






  
2. The limit order book

  
An exchange matches orders by price-time priority: the best price first, and at the same price, the oldest order first. A book therefore needs three things fast:

  
    
    
  • Best price on each side, for every incoming market order.
    • 
    
  • Insert and remove price levels as orders arrive at new prices or the last order at a price leaves.
    • 
    
  • Find an order by ID to cancel or modify it. Cancels are often more than 90% of all messages.
    • 
  

  

    
Level storageBest priceNew levelRemove levelNotes

    
      
Sorted array, best at the end$O(1)$$O(\log L + \text{shift})$$O(\log L + \text{shift})$Very cache friendly. Shifts are cheap when activity is near the top

      
Binary heap + lazy delete$O(1)$ peek, pops to clear stale$O(\log L)$$O(1)$ markSimple, but stale entries pile up

      
Balanced tree or skip list$O(1)$ with a cached pointer$O(\log L)$$O(\log L)$The textbook choice. Pointer chasing costs cache misses

      
Array indexed by tick$O(1)$$O(1)$$O(1)$, scan if it was the bestFastest for liquid instruments in a bounded price band

    
  

  
Each price level holds a FIFO queue of orders, usually an intrusive doubly linked list, so a cancel unlinks in $O(1)$. A hash map from order ID to the order's node finds it. Put together:

  
class Book {                                  // bid side, prices in integer ticks
  levels = new Array(MAX_TICKS);              // tick -> Level { qty, head, tail } or null
  orders = new Map();                        // order id -> node in its level's list
  best = -1;

  add(id, tick, qty) {
    const lvl = (this.levels[tick] ??= new Level());
    this.orders.set(id, lvl.append(id, qty));    // O(1)
    if (tick > this.best) this.best = tick;
  }
  cancel(id) {
    const node = this.orders.get(id); this.orders.delete(id);
    node.level.unlink(node);                      // O(1)
    if (node.level.empty && node.tick === this.best) this.rescanBest();
  }
  rescanBest() {                                  // only cost that grows: empty ticks skipped
    while (this.best >= 0 && !this.levels[this.best]?.qty) this.best--;
  }
}

  
The rescan can be bounded with a bitmap of non-empty ticks: one 64-bit word covers 64 ticks, and a count-leading-zeros instruction finds the next set bit, so even a wide gap costs a handful of word reads.






  
3. Statistics over streams

  
Signals are computed tick by tick, so every statistic should update in $O(1)$ or $O(\log w)$ per event, never by recomputing a window from scratch.

  
Mean and variance in one pass

  
The textbook formula $\frac1n\sum x^2 - \bar x^2$ subtracts two large, nearly equal numbers and loses precision. Welford's update is stable:

  
$$\delta = x_n - \mu_{n-1}, \qquad \mu_n = \mu_{n-1} + \frac{\delta}{n}, \qquad M_n = M_{n-1} + \delta\,(x_n - \mu_n), \qquad s_n^2 = \frac{M_n}{n-1}$$

  
For a fading memory, use an exponentially weighted mean, $\mu_t = \lambda \mu_{t-1} + (1-\lambda) x_t$, whose half-life is $\ln 2 / \ln(1/\lambda)$ steps.


  
Rolling maximum with a monotonic deque

  
Keep indexes whose values decrease from front to back. A new value pops every smaller value from the back, since they can never be the maximum again. The front is the answer. Each index is pushed and popped once, so the cost is $O(1)$ amortized:

  
function rollingMax(xs, w) {
  const dq = [], out = [];                    // indexes, values decreasing
  for (let i = 0; i < xs.length; i++) {
    while (dq.length && xs[dq[dq.length - 1]] <= xs[i]) dq.pop();
    dq.push(i);
    if (dq[0] <= i - w) dq.shift();          // use a ring buffer in real code
    if (i >= w - 1) out.push(xs[dq[0]]);
  }
  return out;
}


  
Median, quantiles and counts

  
    
    
  • Running median: two heaps, a max-heap for the lower half and a min-heap for the upper half, kept within one element of each other. $O(\log n)$ per update. For a sliding window, add lazy deletion or use an order-statistic tree.
    • 
    
  • Approximate quantiles over huge streams: t-digest or KLL sketches, in fixed memory.
    • 
    
  • Heavy hitters and distinct counts: count-min sketch for "which symbols trade most", HyperLogLog for "how many distinct accounts".
    • 
    
  • Range queries: prefix sums for static data, a segment tree or Fenwick tree when values change.
    • 
  


  
Maximum drawdown in one pass

  
The largest peak-to-trough loss of an equity curve $V_t$ only needs the running peak:

  
$$\text{MDD} = \max_{t}\left(1 - \frac{V_t}{\max_{s \le t} V_s}\right)$$

  
It is the same pattern as the classic "best time to buy and sell a stock once" interview question, which tracks the running minimum instead.






  
4. Hash maps, ring buffers and queues

  
Hash maps give $O(1)$ expected lookup from order ID, symbol or account to its record. On a hot path, prefer open addressing with linear probing in one flat array over chained buckets: probes stay in the same cache lines. Keep the load factor below about 0.7, pre-size the table so it never rehashes during the session, and use a hash function that integer IDs from the exchange cannot defeat.

  
Ring buffers pass messages between threads without locks. With a capacity that is a power of two, the slot for sequence number $s$ is $s \bmod 2^k$, computed as s & (2^k - 1). A single-producer single-consumer ring needs only two counters, each written by one thread. Pad them onto separate cache lines to avoid false sharing, and order the writes with memory fences. Aeron and the LMAX Disruptor are built on this idea.

  
Timers for order timeouts and heartbeats: a timer wheel gives $O(1)$ start and cancel, where a heap gives $O(\log n)$.

Arbitrage as a negative cycle

  
With exchange rates $r_{ij}$, a loop of trades makes money if the product of rates exceeds 1. Taking $-\ln$ turns products into sums and the condition into a negative cycle, which Bellman-Ford detects:

  
$$r_{ab}\, r_{bc}\, r_{ca} > 1 \quad\Longleftrightarrow\quad (-\ln r_{ab}) + (-\ln r_{bc}) + (-\ln r_{ca}) < 0$$


  
At most k trades

  
Let $B_j$ be the best cash after the $j$-th buy and $S_j$ after the $j$-th sell. Scanning prices $p_t$ once:

  
$$B_j \leftarrow \max\bigl(B_j,\ S_{j-1} - p_t\bigr), \qquad S_j \leftarrow \max\bigl(S_j,\ B_j + p_t\bigr), \qquad j = 1, \dots, k$$

  
With $S_0 = 0$ and $B_j = -\infty$ at the start, the answer is $S_k$. Adding a fee per trade is one more term in the sell update.






  
6. Common mistakes

  
    
    
  • Floating-point prices as keys. 0.1 + 0.2 is not 0.3. Store prices as integer ticks and quantities as integers.
    • 
    
  • Allocating on the hot path. A garbage collection or a page fault in the middle of a burst ruins the tail. Pre-allocate pools of orders and levels.
    • 
    
  • Unbounded growth. Lazy-deletion heaps, maps of cancelled orders and logs all grow until something is cleaned up. Bound or compact them.
    • 
    
  • Average-case thinking. A hash map with a bad hash, or a quicksort pivot an adversary can predict, turns $O(1)$ or $O(n \log n)$ into something much worse exactly when traffic spikes.
    • 
    
  • Recomputing windows. A 1,000-tick rolling mean recomputed from scratch is 1,000 times more work than updating it.
    • 
    
  • Benchmarking the mean only. Report the 99th and 99.9th percentile latency, with realistic message bursts.
    •
