HyperLogLog

Count how many distinct items you have seen, within a few percent, using a few kilobytes. It never stores the items. It only remembers the rarest hash pattern in each bucket.

Try the machine first

Each item is hashed to 32 bits. The first few bits choose a register. In the remaining bits, count the zeros before the first 1. Each register keeps only the largest count it has seen. Add items and watch the estimate follow the true count. Add the same word twice and nothing changes.

register value changed by last add 

  






  
1. The idea

  
Flip a fair coin until it lands heads. If you ever needed 10 flips, you probably tried about 210 times. A hash of an item looks like random coin flips, so the longest run of leading zeros in all hashes hints at how many different items there were.

  
One maximum is very noisy. A single lucky hash would wreck the estimate. HyperLogLog splits items into m buckets by their first bits, keeps one maximum per bucket, and combines them with a harmonic mean. Lucky outliers get diluted.

  
Rare patterns are evidence of many tries.






  
2. Adding an item

  
Take p bits of the hash as the register index, so m = 2p. Look at the rest of the bits and count the leading zeros, plus one. Keep the larger value.

  
function add(item) {
  const h   = hash32(item);
  const j   = h >>> (32 - p);                  // register index
  const w   = h << p;                          // the remaining bits
  const rho = w === 0 ? 32 - p + 1 : Math.clz32(w) + 1;
  M[j] = Math.max(M[j], rho);
}

  
Adding a duplicate gives the same hash, the same register and the same rho, so nothing changes. That is why it counts distinct items.






  
3. Reading the estimate

  
Combine all registers with a harmonic mean, which is dominated by small values and ignores single large outliers:

  
E = αm · m² / Σ 2-M[j]

αm ≈ 0.7213 / (1 + 1.079 / m)    // bias constant, for m ≥ 128

  
When most registers are still empty, the formula overshoots. If E ≤ 2.5m and some registers are zero, switch to linear counting: m · ln(m / V), where V is the number of zero registers. Fig 1 applies this rule. Real implementations use a 64-bit hash, so large counts need no further correction.

  
The typical error is 1.04 / √m. With 16 registers expect around 26%. Try 64 and the estimates tighten.






  
4. Merging

  
Two sketches built with the same hash and the same m merge by taking the maximum of each register pair. The result is the sketch you would get from the union of both streams. This makes it easy to count across shards or days, with no double counting of items seen on both.

  
function merge(A, B) {
  return A.map((a, j) => Math.max(a, B[j]));
}

6. Where it shows up

  
    
    
  • Analytics: unique visitors per page, per day, without keeping user ids.
    • 
    
  • Databases: Redis PFADD and PFCOUNT, and approximate distinct counts in many SQL engines.
    • 
    
  • Networking: count distinct flows or sources to spot scans and attacks.
    • 
    
  • Query planning: estimate the number of distinct values in a column.
    • 
  

  
It answers "how many?", not "is this one in?". For membership questions, use a Bloom filter instead.
